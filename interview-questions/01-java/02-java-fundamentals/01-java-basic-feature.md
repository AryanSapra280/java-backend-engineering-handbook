# A. Java Basics & Features — Answers

### 1. What are the key features of Java?

Key features include:

* **Platform-independent** — Java source is compiled to bytecode, which runs on JVMs for different platforms.
* **Object-oriented** — Supports classes, objects, inheritance, polymorphism, abstraction, and encapsulation.
* **Simple** — Removes many complex features such as explicit pointer arithmetic and multiple inheritance of classes.
* **Robust** — Strong type checking, exception handling, automatic memory management.
* **Secure** — Bytecode verification, access control, sandboxing mechanisms, etc.
* **Multithreaded** — Built-in support for threads and concurrency.
* **Portable** — Primitive types have well-defined sizes/semantics, and bytecode is portable.
* **High performance** — JIT compilation can compile frequently executed bytecode into native machine code.
* **Distributed/network-friendly** — Rich networking APIs and libraries.
* **Dynamic/extensible** — Classes can be loaded dynamically at runtime.
* **Automatic memory management** — Garbage collection manages object memory.

---

### 2. Why is Java platform-independent?

Java source code is not normally compiled directly into OS-specific machine code.

```text
Java source
    ↓ javac
Bytecode (.class)
    ↓
JVM
    ↓
Native machine instructions
```

The same bytecode can run on different operating systems as long as a compatible JVM exists.

For example:

```text
Test.java
   ↓
Test.class
   ↓
┌────────────┬────────────┬────────────┐
JVM Windows  JVM Linux    JVM macOS
```

The JVM provides the platform-specific layer.

---

### 3. What does "Write Once, Run Anywhere" mean?

It means Java code can be compiled into **platform-independent bytecode once** and that bytecode can run on different platforms that have compatible JVM implementations.

```text
Test.java
   ↓ javac
Test.class
   ↓
Windows JVM
Linux JVM
macOS JVM
```

It doesn't mean Java programs are completely independent of the operating system. Native libraries, filesystem behavior, environment variables, GUI behavior, etc. can introduce platform dependencies.

---

### 4. Is Java completely object-oriented? Why or why not?

**No.**

Java is not considered a purely object-oriented language because it supports **primitive data types**:

```java
int
long
double
char
boolean
byte
short
float
```

For example:

```java
int x = 10;
```

`x` is a primitive, not an object.

Java also has `static` members and other language features that don't fit the strict "everything is an object" model.

---

### 5. Why does Java support primitive data types if it is object-oriented?

Primarily for **performance and memory efficiency**.

Compare:

```java
int x = 10;
```

with:

```java
Integer x = 10;
```

`int` is a primitive value, whereas `Integer` is an object wrapper.

Primitives avoid object identity and object overhead when those aren't needed.

When an object is required, Java provides wrapper classes:

```text
int     → Integer
long    → Long
double  → Double
char    → Character
boolean → Boolean
```

Java also provides **autoboxing/unboxing** to move conveniently between primitives and wrappers.

---

### 6. What is bytecode?

**Bytecode is the intermediate instruction format generated by the Java compiler and stored in `.class` files.**

Example:

```text
Test.java
   ↓ javac
Test.class
   ↓
Java bytecode
   ↓ JVM
Native instructions
```

Bytecode is designed to be executed by the JVM rather than directly by a particular CPU.

---

### 7. What is the role of the Java compiler?

The Java compiler:

1. Reads Java source code.
2. Performs lexical and syntactic analysis.
3. Performs semantic/type checking.
4. Checks language rules.
5. Generates JVM bytecode if compilation succeeds.

Example:

```bash
javac Test.java
```

produces:

```text
Test.class
```

If there are compilation errors, the compiler reports them and normally does not produce a usable class file for the erroneous class.

---

### 8. What is `javac`?

`javac` is the **Java compiler executable** provided by the JDK.

Example:

```bash
javac Test.java
```

It compiles Java source code into JVM bytecode:

```text
Test.java → Test.class
```

`javac` belongs to the **JDK**, not merely the JRE.

---

### 9. What is the difference between source code, bytecode and machine code?

|                           | Source Code            | Bytecode                            | Machine Code               |
| ------------------------- | ---------------------- | ----------------------------------- | -------------------------- |
| Example                   | `Test.java`            | `Test.class`                        | CPU instructions           |
| Produced by               | Developer              | `javac`                             | JVM/JIT or native compiler |
| Executed directly by CPU? | No                     | No                                  | Yes                        |
| Platform-specific?        | Usually language-level | Designed to be platform-independent | Yes                        |
| Purpose                   | Human-readable program | JVM execution format                | CPU execution              |

Flow:

```text
Source code
    ↓ javac
Bytecode
    ↓ JVM/JIT
Machine code
    ↓
CPU
```

---

### 10. Why doesn't Java compile directly into native machine code?

Java's traditional execution model uses an intermediate **bytecode** representation so the same compiled program can run on different platforms through their respective JVMs.

If Java compiled directly to Windows x86 machine code, that executable wouldn't directly run on Linux ARM, for example.

With bytecode:

```text
Same bytecode
     ↓
┌────┼────┐
JVM  JVM  JVM
Win  Linux macOS
```

Each JVM handles the underlying platform.

Modern Java also uses **JIT compilation**, so the JVM can eventually compile frequently executed bytecode into native machine code at runtime.

### 11. What happens from `javac Test.java` until `Test.class` is produced?

Conceptually:

```text
Test.java
   ↓
Lexical analysis
   ↓
Parsing
   ↓
Symbol/type checking
   ↓
Semantic checks
   ↓
Bytecode generation
   ↓
Test.class
```

More specifically:

1. `javac` reads the source file.
2. It tokenizes/parses the Java syntax.
3. It builds internal representations of the program.
4. It resolves symbols such as classes, methods, and variables.
5. It performs type checking and other compile-time checks.
6. It reports compilation errors if the source violates Java rules.
7. If compilation succeeds, it generates JVM bytecode.
8. The bytecode is written into `.class` files.

For example:

```java
public class Test {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
```

becomes:

```text
Test.class
```

containing JVM bytecode and class metadata.

---

### 12. What happens when you execute `java Test`?

Conceptually:

```text
java Test
   ↓
JVM starts
   ↓
Class loader loads Test
   ↓
Bytecode verification/linking
   ↓
Class initialization
   ↓
main() located
   ↓
main() executes
```

More detail:

1. The `java` launcher starts a JVM.
2. The JVM locates `Test` using the classpath/module system.
3. The class loader loads the class.
4. The JVM performs linking activities such as verification, preparation and resolution as needed.
5. The class is initialized when required.
6. JVM invokes:

```java
public static void main(String[] args)
```

7. The program executes.

During execution, the JVM may interpret bytecode and/or JIT-compile frequently executed code into native machine code.

---

### 13. What happens if the JVM cannot find the requested class?

You generally get:

```text
Error: Could not find or load main class Test
Caused by: java.lang.ClassNotFoundException: Test
```

The exact message can vary depending on how the class is launched and what failed.

For:

```bash
java Test
```

the launcher needs to locate `Test` according to the applicable classpath/module configuration.

A common cause is:

```text
Test.class
```

not being in the expected classpath location.

---

### 14. What happens if the class file was compiled with a newer Java version than the JVM supports?

The JVM rejects the class because its **class-file version is newer than the JVM understands**.

You typically get:

```text
UnsupportedClassVersionError
```

For example:

```text
Compiled with Java 25
        ↓
Run on older JVM
        ↓
UnsupportedClassVersionError
```

The solution is generally to:

* Run it with a sufficiently new JVM, or
* Compile for the older target version using the appropriate compiler options.

Example:

```bash
javac --release 17 Test.java
```

---

### 15. What is the classpath?

The **classpath is a set of locations from which the JVM and Java tools can locate classes and resources** when using the traditional classpath mechanism.

It can contain:

* Directories
* JAR files
* Other supported classpath entries

Example:

```bash
java -cp lib/*:. Test
```

Conceptually:

```text
classpath
├── .
├── lib/a.jar
└── lib/b.jar
```

The JVM searches the configured locations when resolving classes.

---

### 16. How does the JVM locate a class using the classpath?

Suppose:

```bash
java -cp classes Test
```

The JVM needs:

```text
Test.class
```

It maps the binary class name to its expected path:

```text
Test
 ↓
Test.class
```

For:

```java
com.example.Test
```

it looks for:

```text
com/example/Test.class
```

inside the classpath entries.

For example:

```text
classes/
└── com/
    └── example/
        └── Test.class
```

If the class isn't found through the applicable class-loading mechanism, class loading fails, commonly resulting in `ClassNotFoundException` or `NoClassDefFoundError`, depending on the situation.

### 17. What is the difference between compile-time errors and runtime errors?

### Compile-time error

Detected while compiling the source code.

Example:

```java
int x = "hello";
```

The compiler reports a type error.

Another example:

```java
System.out.println(unknownVariable);
```

The variable cannot be resolved.

The program doesn't successfully compile.

---

### Runtime error

The program compiles but encounters a problem during execution.

Example:

```java
int x = 10 / 0;
```

This results in:

```text
ArithmeticException
```

Another example:

```java
String s = null;
s.length();
```

results in:

```text
NullPointerException
```

So:

```text
Compile-time
    ↓
javac detects problem

Runtime
    ↓
JVM/program execution encounters problem
```

Some runtime failures are represented by exceptions/errors, while other failures can be incorrect behavior without any exception.

---

### 18. Why can the same Java bytecode behave differently on different operating systems?

The bytecode itself is designed to be portable, but the **JVM and underlying operating system provide platform-dependent behavior**.

Differences can arise from:

* JVM implementation/version.
* CPU architecture.
* Native libraries.
* File-system behavior.
* File/path conventions.
* Character encoding/environment configuration.
* OS-level networking behavior.
* Environment variables.
* Time-zone configuration.
* Available system resources.

For example:

```java
Path.of("C:\\temp\\file.txt")
```

contains a Windows-specific path assumption even though the Java bytecode can technically run on Linux.

Similarly, code that calls native libraries through JNI can depend heavily on the target OS/architecture.

Therefore:

> **Java bytecode is portable, but the complete application's behavior is not guaranteed to be identical across every environment.**

### Key revision flow

```text
.java
  │
  │ javac
  ▼
.class (bytecode)
  │
  │ Class Loader
  ▼
JVM
  │
  ├── Verification
  ├── Linking
  ├── Initialization
  │
  ▼
Interpreter / JIT
  │
  ▼
Native machine code
  │
  ▼
CPU
```

**Remember the distinction:**

> **JDK → development tools (`javac`, etc.)**
> **JVM → executes bytecode**
> **Bytecode → platform-independent intermediate representation**
> **Machine code → platform/CPU-specific instructions**
