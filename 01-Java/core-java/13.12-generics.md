# 13.12 — Java Generics

## Core purpose

Generics provide compile-time type safety.

Before Java 5, Java had no generics. Collections commonly used `Object` and required manual casts.

```java
List list = new ArrayList();
list.add("Aryan");
list.add(10);

String name = (String) list.get(0);
```

With generics:

```java
List<String> names = new ArrayList<>();
names.add("Aryan");
// names.add(10); // compile-time error
```

> Generics move many type errors from runtime to compile time.

---

## Generic class

```java
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

Usage:

```java
Box<String> box = new Box<>();
box.set("Hello");

String value = box.get();
```

`T` is supplied when the generic type is used.

---

## Generic method

```java
public static <T> T getFirst(List<T> list) {
    return list.get(0);
}
```

`<T>` before the return type declares the method's type parameter.

Generic class:

```java
class Box<T>
```

Generic method:

```java
<T> T getFirst(...)
```

---

## Raw types

```java
List list = new ArrayList();
```

A raw type bypasses generic type checking and is mainly encountered for compatibility with pre-generics Java.

Prefer:

```java
List<String> names = new ArrayList<>();
```

---

# Wildcards

## `<?>`

```java
List<?>
```

means a List of some unknown type.

It can refer to:

```java
List<String>
List<Integer>
List<Double>
```

You can safely read values as `Object`.

---

## `<? extends T>`

```java
List<? extends Number>
```

means a List of some unknown type that is `Number` or a subclass.

Possible types:

```text
List<Integer>
List<Double>
List<Float>
```

You can safely read:

```java
Number n = numbers.get(0);
```

But you generally cannot add a Number because the actual list might be `List<Integer>` or `List<Double>`.

Think:

> `extends` → producer/read source.

---

## `<? super T>`

```java
List<? super Integer>
```

can represent:

```text
List<Integer>
List<Number>
List<Object>
```

You can safely add an Integer:

```java
numbers.add(10);
```

But when reading, only `Object` is guaranteed:

```java
Object value = numbers.get(0);
```

Think:

> `super` → consumer/write destination.

---

# PECS ⭐

> **Producer Extends, Consumer Super**

```text
Producer → ? extends T
Consumer → ? super T
```

Mental shortcut:

```text
I GET values → extends
I PUT values → super
```

Classic example:

```java
static <T> void copy(
    List<? extends T> source,
    List<? super T> destination
) {
    for (T value : source) {
        destination.add(value);
    }
}
```

---

# Generic invariance

Even though:

```text
Integer extends Number
```

this is NOT true:

```text
List<Integer> extends List<Number>
```

If it were allowed:

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers;
numbers.add(10.5);
```

A `Double` could enter a `List<Integer>`.

Therefore:

> Generic types are invariant.

Use:

```java
List<? extends Number>
```

when you need a read-only/producer view across numeric subtypes.

---

# `<T extends Number>` vs `<? extends Number>` ⭐

At first glance, these look almost identical because **both restrict the type to `Number` or a subclass**.

The difference is:

> **`T` gives the type a name so we can reuse it. `?` deliberately leaves the type unnamed because we don't need to refer to that exact type.**

## `<T extends Number>` — name the type

```java
<T extends Number>
```

means:

> "There is a type that is `Number` or a subclass, and I am going to call that type `T`."

Because `T` has a name, we can reuse it:

```java
static <T extends Number> T process(T value) {
    return value;
}
```

Here the same `T` connects the input and output:

```text
input        T        output
  │          │          │
Integer → Integer → Integer
Double  → Double  → Double
```

If we call:

```java
Integer result = process(10);
```

then:

```text
T = Integer
```

If we call:

```java
Double result = process(10.5);
```

then:

```text
T = Double
```

So `T` is useful when we need to **preserve or establish a relationship involving the exact type**.

---

## `<? extends Number>` — don't name the type

```java
List<? extends Number>
```

means:

> "There is some unknown type here that is `Number` or a subclass. I don't need to know its exact type."

The actual list could be:

```java
List<Integer>
List<Double>
List<Long>
```

For example:

```java
void printNumbers(List<? extends Number> numbers) {
    Number n = numbers.get(0);
}
```

We don't care whether the actual type is:

```text
Integer
Double
Long
```

We only care that it is a `Number`.

The unknown type does **not** get a reusable name such as `T`.

---

## The easiest mental shortcut

```text
<T extends Number>
    ↓
"Number/subclass"
    ↓
"Give that type a NAME: T"
    ↓
"I can reuse T"

<? extends Number>
    ↓
"Number/subclass"
    ↓
"I DON'T need to name the exact type"
    ↓
"I only care that it is a Number subtype"
```

### Remember:

> **`T` = name the type so I can reuse it.**  
> **`?` = I don't need to name the type.**

---

## Why this matters

Compare:

```java
<T extends Number> T process(T value)
```

with:

```java
void process(List<? extends Number> values)
```

The first needs `T` because the exact type is relevant to the method's relationship:

```text
input type → T → output type
```

The second uses `?` because the method doesn't need to know whether the list contains `Integer`, `Double`, etc.:

```text
Integer ─┐
Double  ─┼→ List<? extends Number>
Long    ─┘
```

---

## Important: the allowed types are NOT the main difference

You correctly observed:

> "`T extends Number` says something will come but it will be Number or subclass. `? extends Number` says I don't know but it will be Number or subclass."

**Yes. Exactly.**

Both impose essentially the same upper-bound restriction.

The difference is what we do with that type:

```text
T
→ named type parameter
→ can reuse it

?
→ unnamed wildcard
→ don't need to refer to the exact type
```

This is the key distinction to remember for interviews.

---

## Interview answer

If asked:

> What is the difference between `<T extends Number>` and `<? extends Number>`?

A strong answer is:

> "`<T extends Number>` declares a bounded type parameter named T. Because T has a name, I can reuse it to establish a relationship between different parts of a class or method, such as connecting an input and return type. `<? extends Number>` is a wildcard representing some unknown subtype of Number. I use it when I don't need to know or preserve the exact subtype, commonly when reading from a producer."

# Bounded generic class

```java
class Calculator<T extends Number> {
    private T value;

    public double calculate() {
        return value.doubleValue();
    }
}
```

Valid:

```java
Calculator<Integer>
Calculator<Double>
```

Invalid:

```java
Calculator<String>
```

Multiple bounds:

```java
<T extends SomeClass & InterfaceA & InterfaceB>
```

If there is a class bound, it comes first.

# Type Erasure ⭐⭐⭐

## Historical context

Before Java 5:

```text
No generics
    ↓
Collections commonly used Object
    ↓
Manual casts
```

Java 5 introduced generics.

The design goal was to add compile-time type safety while preserving compatibility with existing Java code and the JVM.

Therefore Java implemented generics primarily through **type erasure**.

Do not say:

> "Old Java supported type erasure."

More accurate:

> "Old Java did not have generics. Java 5 introduced generics and used type erasure so existing Java code and bytecode could remain compatible."

---

## What gets erased?

For:

```java
class Box<T> {
    T value;
    T get() {
        return value;
    }
}
```

an unbounded `T` is erased approximately to `Object`:

```java
class Box {
    Object value;
    Object get() {
        return value;
    }
}
```

Mental model:

```text
<T>
 ↓
Object
```

The compiler still uses generic information for compile-time type checking and handles the necessary casts.

---

## Bounded type erasure

If:

```java
class Box<T extends Number> {
    T value;
}
```

then:

```text
T extends Number
       ↓
erasure → Number
```

So:

```text
<T>
    → Object

<T extends Number>
    → Number
```

With multiple bounds, erasure is based on the leftmost bound.

---

# Consequences of type erasure

## `instanceof`

You cannot generally write:

```java
value instanceof List<String>
```

because the runtime cannot distinguish parameterized `List<String>` from another parameterized List in that way.

You can use:

```java
value instanceof List<?>
```

---

## Generic array creation

Generally invalid:

```java
T[] array = new T[10];
```

because the runtime does not know the concrete T needed to create the array.

---

## Static generic fields

Invalid:

```java
class Box<T> {
    static T value;
}
```

A static member belongs to the class, while T belongs to a particular generic parameterization.

---

# Generics and primitives

Generics require reference types:

```java
List<int>       // invalid
List<Integer>   // valid
```

Autoboxing handles convenient usage:

```java
List<Integer> numbers = new ArrayList<>();
numbers.add(10);
```

Conceptually:

```text
int
 ↓ boxing
Integer
 ↓
List<Integer>
```

Retrieval can involve unboxing:

```java
int value = numbers.get(0);
```

# Production scenarios

## Generic Repository

```java
interface Repository<T, ID> {
    T findById(ID id);
    void save(T entity);
}
```

Examples:

```text
Repository<User, Long>
Repository<Payment, UUID>
Repository<Order, String>
```

---

## Generic numeric API

```java
double sum(List<? extends Number> numbers) {
    double total = 0;

    for (Number number : numbers) {
        total += number.doubleValue();
    }

    return total;
}
```

Accepts:

```text
List<Integer>
List<Double>
List<Long>
```

---

## PECS copy operation

```java
static <T> void copy(
    List<? extends T> source,
    List<? super T> destination
) {
    for (T value : source) {
        destination.add(value);
    }
}
```

Source produces T → `extends`.

Destination consumes T → `super`.

# Common interview mistakes

### Mistake 1

`List<Integer>` is a `List<Number`.

**Wrong.**

Generic types are invariant.

### Mistake 2

You can add to `List<? extends Number>`.

**Wrong.**

The actual list could be `List<Double>`.

### Mistake 3

You can safely read Integer from `List<? super Integer>`.

**Wrong.**

The safe read type is `Object`.

### Mistake 4

`<T extends Number>` and `<? extends Number>` are identical.

**Wrong.**

One declares a bounded type parameter; the other is a wildcard.

### Mistake 5

"Old Java supported type erasure."

**Wrong wording.**

Old Java had no generics. Type erasure was used when generics were introduced in Java 5.
