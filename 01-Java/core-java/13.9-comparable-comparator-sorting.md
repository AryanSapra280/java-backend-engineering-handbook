# 13.9 — Comparable vs Comparator vs Sorting APIs

## 1. Core distinction

```text
Comparable
    → "How should objects of this class naturally be ordered?"

Comparator
    → "How should I order these objects for this particular use case?"
```

---

## 2. Comparable

The class itself defines its natural ordering:

```java
class Employee implements Comparable<Employee> {

    int salary;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.salary, other.salary);
    }
}
```

Mental model:

```text
Employee
   ↓
implements Comparable
   ↓
compareTo()
   ↓
natural ordering
```

---

## 3. What does `compareTo()` return?

Only the sign matters:

```text
< 0 → this comes BEFORE other
= 0 → equivalent in ordering
> 0 → this comes AFTER other
```

Prefer:

```java
return Integer.compare(this.salary, other.salary);
```

over:

```java
return this.salary - other.salary;
```

because subtraction can overflow.

For `long`:

```java
return Long.compare(this.timestamp, other.timestamp);
```

---

## 4. Comparator

Use Comparator when ordering is external/custom or there are multiple valid orderings.

```java
Comparator<Employee> byName =
    Comparator.comparing(Employee::getName);

employees.sort(byName);
```

Mental model:

```text
Comparable
    → ordering belongs to the class

Comparator
    → ordering is supplied externally
```

---

## 5. `compareTo()` vs `compare()`

Comparable:

```java
e1.compareTo(e2);
```

Method:

```text
compareTo()
```

Comparator:

```java
comparator.compare(e1, e2);
```

Method:

```text
compare()
```

---

## 6. Comparable vs Comparator

| | Comparable | Comparator |
|---|---|---|
| Method | `compareTo()` | `compare()` |
| Interface | `Comparable<T>` | `Comparator<T>` |
| Ordering | Natural/default | Custom/external |
| Defined | Inside class | Outside class |
| Multiple orderings | Awkward | Easy |
| Modify domain class? | Usually yes | No |

Interview answer:

> Use Comparable when the class has a clear natural/default ordering. Use Comparator when ordering is contextual, custom, or when multiple orderings are required without changing the domain class.

---

## 7. Multiple Comparator Orders

```java
Comparator<Employee> byName =
    Comparator.comparing(Employee::getName);

Comparator<Employee> bySalary =
    Comparator.comparing(Employee::getSalary);

Comparator<Employee> byJoiningDate =
    Comparator.comparing(Employee::getJoiningDate);
```

Then:

```java
employees.sort(byName);
employees.sort(bySalary);
employees.sort(byJoiningDate);
```

without changing Employee.

---

## 8. Descending Order

```java
Comparator<Employee> bySalary =
    Comparator.comparing(Employee::getSalary);
```

Ascending:

```text
50K
70K
90K
```

Descending:

```java
employees.sort(bySalary.reversed());
```

Result:

```text
90K
70K
50K
```

---

## 9. Comparator Chaining

Requirement:

> Sort by department, then salary, then name.

```java
Comparator<Employee> comparator =
    Comparator.comparing(Employee::getDepartment)
              .thenComparing(Employee::getSalary)
              .thenComparing(Employee::getName);
```

Mental model:

```text
department
    ↓
same department?
    ↓ yes
salary
    ↓
same salary?
    ↓ yes
name
```

`thenComparing()` is used only when the previous comparison considers the objects equivalent in ordering.

---

## 10. Production Example — Payments

Requirement:

1. highest amount first
2. same amount → newest first
3. same timestamp → paymentId ascending

```java
Comparator<Payment> comparator =
    Comparator.comparing(
        Payment::getAmount,
        Comparator.reverseOrder()
    ).thenComparing(
        Payment::getTimestamp,
        Comparator.reverseOrder()
    ).thenComparing(
        Payment::getPaymentId
    );

payments.sort(comparator);
```

This is a realistic backend scenario.

---

## 11. Comparable + TreeSet / TreeMap

A class implementing Comparable can provide natural ordering to sorted collections.

```java
class Employee implements Comparable<Employee> {
    ...
}
```

Then:

```java
TreeSet<Employee> employees = new TreeSet<>();
```

can use `compareTo()`.

Similarly:

```java
TreeMap<Employee, String> employees =
    new TreeMap<>();
```

can use the key's natural ordering.

Alternatively, provide a Comparator:

```java
TreeSet<Employee> employees =
    new TreeSet<>(bySalary);

TreeMap<Employee, String> employees =
    new TreeMap<>(bySalary);
```

---

## 12. Important TreeSet / TreeMap Trap

Suppose:

```java
Comparator<Employee> bySalary =
    Comparator.comparing(Employee::getSalary);
```

If:

```text
Employee A → salary 10L
Employee B → salary 10L
```

then:

```java
bySalary.compare(A, B) == 0
```

A TreeSet can treat them as equivalent for set membership.

A TreeMap can treat them as equivalent keys for its ordering.

If salary alone isn't enough, use a tie-breaker:

```java
Comparator<Employee> comparator =
    Comparator.comparing(Employee::getSalary)
              .thenComparing(Employee::getId);
```

Now employees with equal salary can still be distinguished by ID.

---

## 13. `equals()` vs `compareTo()`

They answer different questions.

```text
equals()
    → Are these objects logically equal?

compareTo()
    → How are these objects ordered relative to each other?
```

It is possible to have:

```text
equals() → false
compareTo() → 0
```

For example, two employees can have different IDs but the natural ordering compares only salary.

This can cause surprising behavior in TreeSet/TreeMap.

For sorted collections, comparison should ideally be consistent with the intended equality/identity semantics.

---

## 14. Sorting APIs

### List

Modern direct API:

```java
employees.sort(comparator);
```

or:

```java
employees.sort(
    Comparator.comparing(Employee::getSalary)
);
```

### Collections

You may also see:

```java
Collections.sort(employees);
```

or:

```java
Collections.sort(employees, comparator);
```

For modern code, `List.sort()` is generally the direct API when you already have a List.

### Array

```java
Arrays.sort(employees);
```

or:

```java
Arrays.sort(employees, comparator);
```

Mental model:

```text
List
 ↓
list.sort()

Array
 ↓
Arrays.sort()
```

---

## 15. Natural Ordering vs Custom Ordering

```text
One obvious natural ordering?
    ↓
Comparable

Multiple/custom/contextual orderings?
    ↓
Comparator
```

Examples of classes with natural ordering include:

```text
String
Integer
LocalDate
```

Business classes such as:

```text
Employee
Payment
Transaction
```

may have several legitimate orderings, making Comparator particularly useful.

---

## 16. Sorting Complexity

For interview purposes:

```text
general-purpose sorting
    → typically O(n log n)
```

Do not spend preparation time memorizing every current JDK sorting implementation unless the interviewer specifically asks.

More important:

```text
n elements
 ↓
sorting
 ↓
typically O(n log n)
```

---

## 17. Stable Sorting

A stable sort preserves the relative order of elements that compare as equal.

Original:

```text
A, salary 10
B, salary 20
C, salary 10
```

Sort by salary.

A stable result keeps:

```text
A, salary 10
C, salary 10
B, salary 20
```

because A originally appeared before C.

Know the concept; don't spend time memorizing every internal algorithm unless asked.

---

## 18. Production Scenario — Payment API

Suppose a REST endpoint returns payments.

Requirement:

```text
1. amount descending
2. timestamp descending
3. paymentId ascending
```

A comparator chain gives a clean implementation:

```java
Comparator<Payment> comparator =
    Comparator.comparing(
        Payment::getAmount,
        Comparator.reverseOrder()
    ).thenComparing(
        Payment::getTimestamp,
        Comparator.reverseOrder()
    ).thenComparing(
        Payment::getPaymentId
    );

payments.sort(comparator);
```

This is exactly the kind of scenario/judgment question worth practicing.

# Final Mental Model

```text
             ORDERING
                │
       ┌────────┴────────┐
       ↓                 ↓
 Comparable          Comparator
       │                 │
 compareTo()          compare()
       │                 │
 natural             custom
 ordering            ordering
       │                 │
       └────────┬────────┘
                ↓
          Collections
                │
      ┌─────────┴─────────┐
      ↓                   ↓
   TreeSet             TreeMap
      │                   │
 sorted elements      sorted keys
```

## One sentence to remember

> **Comparable says "this class has a natural order"; Comparator says "use this particular ordering for these objects."**
