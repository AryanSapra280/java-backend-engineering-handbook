# 13.5 — TreeSet

> Collections learning note. Focus: TreeSet internals, sorted ordering, comparison logic, `compareTo()` / `Comparator`, uniqueness semantics, Red-Black Tree, complexity, range/navigation operations, production scenarios, and HashSet comparison.

---

# 1. What Problem Does TreeSet Solve?

We already have:

```text
HashSet
    → uniqueness

LinkedHashSet
    → uniqueness + insertion order

TreeSet
    → uniqueness + sorted order
```

Example:

```java
Set<Integer> numbers = new TreeSet<>();

numbers.add(50);
numbers.add(10);
numbers.add(30);
numbers.add(20);
```

Iteration:

```text
10
20
30
50
```

The important requirement is:

> **Keep unique elements in sorted order and support ordered operations.**

---

# 2. TreeSet Internal Structure

`TreeSet` is backed by a `TreeMap`.

Conceptually:

```text
TreeSet
   ↓
TreeMap
   ↓
Red-Black Tree
```

A Red-Black Tree is a self-balancing Binary Search Tree.

Conceptually:

```text
             50
           /             30      80
        /  \    /        20   40  70   90
```

The tree maintains ordering while remaining approximately balanced.

Therefore:

```text
add()       → O(log n)
contains()  → O(log n)
remove()    → O(log n)
```

---

# 3. TreeSet Does NOT Use Hashing

This is one of the most important differences from HashSet.

## HashSet

```text
element
   ↓
hashCode()
   ↓
bucket
   ↓
candidate(s)
   ↓
equals()
```

## TreeSet

```text
element
   ↓
compareTo()
   OR
Comparator
   ↓
left / right decision
   ↓
Red-Black Tree
```

So:

```text
HashSet → hash-based
TreeSet → comparison/tree-based
```

Do not think of TreeSet as a "sorted HashSet." The underlying data structures and lookup mechanisms are fundamentally different.

---

# 4. How Does TreeSet Know the Order?

TreeSet needs an ordering rule.

There are two common ways:

### Natural ordering

The element implements `Comparable`:

```java
class Payment implements Comparable<Payment> {

    @Override
    public int compareTo(Payment other) {
        return this.amount.compareTo(other.amount);
    }
}
```

Then:

```java
TreeSet<Payment> payments = new TreeSet<>();
```

uses:

```text
payment.compareTo(otherPayment)
```

### Custom ordering

Provide a `Comparator`:

```java
TreeSet<Payment> payments =
    new TreeSet<>(Comparator.comparing(Payment::getAmount));
```

Now the TreeSet uses the supplied comparator.

---

# 5. How Comparison Navigates the Tree

Suppose the TreeSet contains:

```text
             50
           /             30      80
```

We insert:

```text
40
```

The tree compares:

```text
40 vs 50
```

Since:

```text
40 < 50
```

go left.

Then:

```text
40 vs 30
```

Since:

```text
40 > 30
```

go right.

Conceptually:

```text
             50
           /
         30
                       40
```

The important idea:

> **Each comparison tells the tree which direction to search.**

This is why TreeSet does not need to scan every element.

---

# 6. TreeSet Uniqueness Is Different From HashSet

This is a major interview point.

### HashSet uniqueness

HashSet uses:

```text
hashCode()
   ↓
candidate bucket
   ↓
equals()
   ↓
duplicate?
```

### TreeSet uniqueness

TreeSet uses comparison:

```text
compareTo()
   OR
Comparator.compare()
   ↓
compare result
```

If:

```text
compare(a, b) == 0
```

TreeSet treats the elements as equivalent for the Set's ordering.

Therefore:

> **TreeSet's notion of duplicate/equivalent elements is determined by its ordering comparison.**

---

# 7. The `compare() == 0` Trap

Suppose:

```java
class Payment {
    String paymentId;
    BigDecimal amount;
}
```

And:

```java
TreeSet<Payment> payments =
    new TreeSet<>(Comparator.comparing(Payment::getAmount));
```

Now:

```text
P1 → amount = 500
P2 → amount = 500
```

The comparator produces:

```text
compare(P1, P2) == 0
```

TreeSet can therefore treat P1 and P2 as equivalent.

But perhaps:

```text
P1.equals(P2) == false
```

because their payment IDs are different.

One payment can therefore effectively disappear from the Set.

This is a **comparator design problem**.

---

# 8. Fixing the Comparator

If business identity is:

```text
amount + paymentId
```

you can use a tie-breaker:

```java
Comparator<Payment> comparator =
    Comparator.comparing(Payment::getAmount)
              .thenComparing(Payment::getPaymentId);

TreeSet<Payment> payments =
    new TreeSet<>(comparator);
```

Now:

```text
amount
   ↓
same?
   ↓
compare paymentId
   ↓
distinguish elements
```

This is an important production-level TreeSet consideration.

---

# 9. Consistency With `equals()`

Ideally:

```text
compare(a, b) == 0
```

should correspond to:

```text
a.equals(b) == true
```

for the logical identity represented by the Set.

If that relationship is broken, TreeSet can behave in surprising ways.

This differs from HashSet, where the critical contract is:

```text
a.equals(b) == true
        ↓
a.hashCode() == b.hashCode()
```

So remember:

```text
HashSet:
equals ↔ hashCode contract

TreeSet:
comparison defines ordering/equivalence
```

---

# 10. Why Red-Black Tree?

A normal Binary Search Tree can become badly unbalanced.

For sorted insertion:

```text
10
20
30
40
50
```

a naive BST could become:

```text
10
     20
           30
                 40
                       50
```

This behaves like a linked list:

```text
search → O(n)
```

A Red-Black Tree maintains balance:

```text
        30
       /       20    40
    /           10         50
```

Therefore TreeSet keeps its core operations at:

```text
O(log n)
```

---

# 11. Ordered Navigation Operations

This is one of the biggest reasons to use TreeSet.

Suppose:

```java
TreeSet<Integer> scores = new TreeSet<>();

scores.add(10);
scores.add(20);
scores.add(30);
scores.add(40);
scores.add(50);
```

You can ask:

### `floor(x)`

Largest element `<= x`.

```java
scores.floor(35);
```

Result:

```text
30
```

### `ceiling(x)`

Smallest element `>= x`.

```java
scores.ceiling(35);
```

Result:

```text
40
```

### `lower(x)`

Largest element `< x`.

```java
scores.lower(30);
```

Result:

```text
20
```

### `higher(x)`

Smallest element `> x`.

```java
scores.higher(30);
```

Result:

```text
40
```

Mental model:

```text
floor(x)    → <= x
ceiling(x)  → >= x
lower(x)    → < x
higher(x)   → > x
```

These are extremely useful ordered-set operations.

---

# 12. `first()` and `last()`

Because TreeSet is sorted:

```java
scores.first();
scores.last();
```

return:

```text
smallest
largest
```

respectively.

This is fundamentally different from HashSet because HashSet does not maintain sorted ordering.

# 13. Production Scenario 1 — Find Next Available Capacity

Suppose a system has available capacities:

```text
100
200
500
1000
2000
```

A request asks:

> Give me the smallest capacity that can handle at least 750.

With TreeSet:

```java
capacities.ceiling(750);
```

Result:

```text
1000
```

Why TreeSet?

Because the business operation is:

```text
find smallest value >= X
```

which is directly supported.

# 14. Production Scenario 2 — Find Previous/Next Timestamp

Suppose you maintain sorted timestamps:

```text
10:00
10:15
10:30
11:00
11:30
```

Requirement:

> Find the next scheduled event after time T.

You can use:

```java
timestamps.higher(T);
```

For the previous event:

```java
timestamps.lower(T);
```

The TreeSet naturally expresses the requirement:

```text
sorted timestamps
+
nearest previous/next lookup
```

# 15. Production Scenario 3 — Price / Threshold Lookup

Suppose available price tiers are:

```text
100

500

```

A request has a budget of:

```text
700
```

Requirement:

> Find the highest tier that does not exceed the budget.


# 16. Production Scenario 4 — Dynamic Sorted Data

Suppose values are continuously:

```text
inserted
removed
queried
```

and the system frequently needs:

```text
smallest
largest
next greater
next smaller
range navigation
```

TreeSet can be a strong fit because the tree maintains sorted structure dynamically:

```text
add       → O(log n)
remove    → O(log n)
lookup    → O(log n)
navigation → O(log n)
```

You don't have to repeatedly sort the entire collection after every modification.

---

# 17. TreeSet vs Sorted ArrayList

An alternative is:

```text
ArrayList
   ↓
keep sorted
   ↓
binary search
```

This can be excellent when data is relatively static.

For example:

```text
load data once
sort once
perform many reads
```

ArrayList + binary search can be very efficient.

But if the workload is:

```text
frequent insertions
+
frequent removals
+
frequent ordered queries
```

TreeSet can be more natural because it maintains sorted ordering dynamically.

The right choice depends on the workload.

# 18. TreeSet vs HashSet

| Property | HashSet | TreeSet |
|---|---:|---:|
| Internal structure | Hash-based | Red-Black Tree |
| Uniqueness | Yes | Yes |
| `add()` | Expected O(1) | O(log n) |
| `contains()` | Expected O(1) | O(log n) |
| `remove()` | Expected O(1) | O(log n) |
| Ordering | None guaranteed | Sorted |
| `floor()` | No | Yes |
| `ceiling()` | No | Yes |
| `lower()` | No | Yes |
| `higher()` | No | Yes |
| Main advantage | Fast membership | Sorted/range operations |

Decision:

```text
Need:
"Does this exist?"
        ↓
HashSet

Need:
"Give me the smallest value >= X"
        ↓
TreeSet
```

# 20. Memory Trade-Off

TreeSet stores tree nodes and balancing information.

Conceptually:

```text
TreeSet
   ↓
tree nodes
   ↓
ordering relationships
   +
balancing metadata
```

Therefore TreeSet is not chosen for lower memory usage.

You choose it because you need:

```text
sorted ordering
+
ordered navigation
```

# 21. Mutable Elements — Important Caution

Just like HashSet, be careful with mutable objects.

If the fields used by the TreeSet's comparator change after insertion, the object's correct position in the tree may no longer correspond to its current comparison value.

Example:

```java
TreeSet<Payment> payments =
    new TreeSet<>(Comparator.comparing(Payment::getAmount));
```

Insert:

```text
P1 → amount 500
```

Then mutate:

```text
P1 → amount 1000
```

The tree was organized based on the old ordering.

Changing the comparison-relevant state while the object is inside the TreeSet can lead to incorrect/unexpected behavior.

### Production rule

> Do not mutate fields that participate in the TreeSet's ordering while the element is stored in the set.

Prefer immutable ordering/key fields.

---

# 22. Null

With natural ordering, TreeSet generally cannot handle `null` because `null` cannot be compared with normal elements.

For interview purposes:

> TreeSet with natural ordering should not be treated as a collection that accepts null elements.

---

# 23. Thread Safety

TreeSet is not inherently thread-safe.

That means:

```text
multiple threads
      ↓
shared TreeSet
      ↓
concurrent modification/access
```

does not automatically receive the synchronization/concurrency guarantees needed for safe shared use.

This is the same broader concept we discussed for LinkedHashSet:

```text
thread safety
≠
"another thread sees my change"
```

Thread safety involves appropriate guarantees around:

```text
visibility
+
atomicity
+
safe concurrent access
+
internal consistency
```

We'll handle concurrent collections separately.

# 24. SDE-2 Interview Answer

If asked:

> **"Explain TreeSet."**

A strong answer:

> "`TreeSet` is a sorted Set backed by a `TreeMap`, which uses a self-balancing Red-Black Tree. Unlike HashSet, it doesn't use hashing; it uses natural ordering or a Comparator to navigate the tree. Its add, remove, and lookup operations are O(log n). Its main advantage is that it supports sorted iteration and navigation operations such as `floor`, `ceiling`, `lower`, and `higher`. A key consideration is that comparison returning zero defines equivalence in the TreeSet, so the Comparator should be designed carefully."

# 25. Set Decision Framework

This is the final Set mental model:

```text
Need uniqueness?
       │
       ↓
      Set
       │
       ├── Don't care about order
       │       ↓
       │    HashSet
       │
       ├── Need insertion order
       │       ↓
       │    LinkedHashSet
       │
       └── Need sorted order / range queries
               ↓
            TreeSet
```

Performance:

```text
HashSet
    → expected O(1)

LinkedHashSet
    → expected O(1)

TreeSet
    → O(log n)
```

# 26. Important Interview Traps

### Trap 1

> "TreeSet is just a sorted HashSet."

No.

```text
HashSet → hashing + buckets
TreeSet → Red-Black Tree + comparison
```

---

### Trap 2

> "TreeSet uses equals() to determine duplicates."

Not in the same way as HashSet.

TreeSet's ordering comparison determines equivalence:

```text
compare(a, b) == 0
```

---

### Trap 3

> "Same comparator result means objects are necessarily equal."

No.

Two objects can have:

```text
compare(a, b) == 0
```

while:

```text
a.equals(b) == false
```

TreeSet can nevertheless treat them as equivalent.

---

### Trap 4

> "TreeSet is slower, so HashSet is always better."

No.

If the requirement is:

```text
next greater value
previous value
smallest >= X
largest <= X
sorted iteration
```

HashSet doesn't provide those semantics.

Choose based on operations, not just raw complexity.

---

### Trap 5

> "TreeSet keeps elements in insertion order."

No.

It keeps them in **sorted order**.
