# 13.2 — LinkedList

> Collections learning note from our discussion. We kept this section focused and quick, covering the important LinkedList mechanics, the complexity reasoning, production trade-offs, and the ArrayList comparison.

---

# 1. LinkedList — Core Idea

Unlike ArrayList, which is backed by an array, LinkedList is based on linked nodes.

Java's `LinkedList` is a **doubly linked list**.

Conceptually:

```text
null ← P1 ↔ P2 ↔ P3 ↔ P4 → null
```

Each node conceptually contains:

```text
┌────────┬─────────┬────────┐
│ prev   │ Payment │ next   │
└────────┴─────────┴────────┘
```

So every node knows its previous and next node.

---

# 2. Insertion When the Node Is Already Known

Suppose:

```text
P1 ↔ P2 ↔ P3 ↔ P4 ↔ P5
```

and we want:

```text
P3 ↔ P_NEW ↔ P4
```

We do not shift P4 and P5 as ArrayList would.

We update the relevant links:

```text
P3.next    = P_NEW
P_NEW.prev = P3

P_NEW.next = P4
P4.prev    = P_NEW
```

The link modification itself is:

```text
O(1)
```

This is the fundamental advantage of a linked list.

---

# 3. The Most Important LinkedList Trap

Do NOT simply say:

> "LinkedList insertion is O(1)."

The correct statement is:

> **Insertion/removal is O(1) once the target node/position is already known.**

If we first need to find the node:

```text
find node
   ↓
O(n)
   ↓
modify links
   ↓
O(1)
```

Overall:

```text
O(n)
```

This distinction is very important in interviews.

---

# 4. Insertion at the Beginning

```java
payments.add(0, newPayment);
```

At the beginning, LinkedList already has access to its first node.

Conceptually:

```text
Before:

head
 ↓
P1 ↔ P2 ↔ P3


After:

head
 ↓
NEW ↔ P1 ↔ P2 ↔ P3
```

Only the relevant links need updating.

Therefore:

```text
add at beginning → O(1)
```

---

# 5. Insertion at an Arbitrary Index

Suppose:

```java
payments.add(5_000_000, newPayment);
```

The list must first locate the insertion position.

Conceptually:

```text
head
 ↓
P1 → P2 → P3 → ... → P5,000,000
                         ↓
                    insertion point
                         ↓
                    update links
```

Therefore:

```text
find position → O(n)
link update   → O(1)
-----------------------
overall       → O(n)
```

Java's LinkedList can traverse from the closer end (head or tail), so the traversal is optimized conceptually to:

```text
O(min(index, size - index))
```

but the worst case is still:

```text
O(n)
```

---

# 6. Indexed Access

```java
payments.get(5_000_000);
```

LinkedList cannot directly jump to that position like ArrayList.

It must traverse nodes.

Therefore:

```text
get(index) → O(n) worst case
```

The important mental model:

```text
ArrayList
   ↓
direct indexed access

LinkedList
   ↓
node traversal
```

---

# 7. Why LinkedList Is Not Automatically Faster

A common misconception is:

> "LinkedList has O(1) insertion, so it must be faster than ArrayList."

Not necessarily.

LinkedList has:

- one node per element
- previous reference
- next reference
- more object/reference overhead
- more allocations
- more pointer/reference chasing
- poorer cache locality

ArrayList has:

```text
[P1][P2][P3][P4][P5]
```

through an array-backed structure, which generally provides better locality and lower per-element overhead.

So an operation with a better theoretical complexity can still be slower in a real workload.

---

# 8. Memory Locality

ArrayList:

```text
[P1][P2][P3][P4][P5][P6]
```

The backing array provides good locality.

LinkedList:

```text
[P1 | prev | next]
        ↓
[P2 | prev | next]
        ↓
[P3 | prev | next]
```

Nodes can be located in different memory locations.

This means traversal involves following references and can have poorer CPU cache locality.

Therefore:

> Both can be O(n) for sequential iteration, but ArrayList generally performs better for iteration because of better memory locality and lower per-element overhead.

---

# 9. LinkedList and Removal

Removal at a known node is O(1).

Suppose:

```text
P1 ↔ P2 ↔ P3 ↔ P4
```

Remove P3:

```text
P1 ↔ P2 ↔ P4
```

The relevant links are changed:

```text
P2.next = P4
P4.prev = P2
```

The link update itself is:

```text
O(1)
```

But if we only have an index:

```java
payments.remove(5_000_000);
```

we must first locate the node.

Therefore:

```text
find node   → O(n) worst case
unlink node → O(1)
-------------------
overall     → O(n)
```

---

# 10. ArrayList vs LinkedList

## Core Comparison

| Operation / Property | ArrayList | LinkedList |
|---|---:|---:|
| Backing structure | Array | Doubly linked nodes |
| `get(index)` | O(1) | O(n) worst case |
| `set(index)` | O(1) | O(n) |
| Append at end | Amortized O(1) | O(1) |
| Add at beginning | O(n) | O(1) |
| Remove at beginning | O(n) | O(1) |
| Arbitrary indexed insert | O(n) | O(n) overall |
| Arbitrary indexed remove | O(n) | O(n) overall |
| Sequential iteration | O(n) | O(n) |
| Memory overhead | Lower | Higher |
| Cache locality | Better | Worse |
| Random access | Excellent | Poor |

---

# 11. Why Both Have O(n) Arbitrary Indexed Insertion

This is a useful interview comparison.

### ArrayList

```text
find index → O(1)
shift elements → O(n)
--------------------
total → O(n)
```

### LinkedList

```text
find node → O(n)
change links → O(1)
-------------------
total → O(n)
```

So both can be:

```text
O(n)
```

but for completely different reasons.

This is a stronger answer than simply memorizing the complexity.

---

# 12. Production Scenario

Suppose:

```text
10 million payments

Workload:
- mostly append
- frequent sequential iteration
- occasional random access
- very few middle insertions/removals
```

ArrayList is generally the stronger choice because:

```text
append
    ↓
amortized O(1)

random access
    ↓
O(1)

iteration
    ↓
good locality

middle insertion/removal
    ↓
rare
```

LinkedList's theoretical insertion advantage does not compensate automatically for its memory and locality costs.

---

# 13. Production Decision Rule

Do not ask:

> "Which is faster: ArrayList or LinkedList?"

Ask:

> **"What is my workload and access pattern?"**

For example:

```text
Need frequent index access?
        ↓
ArrayList

Need mostly append?
        ↓
ArrayList is usually a strong default

Need frequent arbitrary insertion/removal?
        ↓
Investigate whether the node is already known
        ↓
If position lookup is still required, LinkedList may not provide
the expected O(1) end-to-end benefit.

Need FIFO / deque semantics?
        ↓
That is a Queue/Deque discussion, which we will cover later.
```

We deliberately do not jump into Queue/Deque implementation details here.

---

# 14. Thread Safety

`LinkedList` is not inherently thread-safe.

If multiple threads share and structurally modify the same LinkedList, synchronization/concurrency concerns arise.

Do not automatically conclude:

> "Use LinkedList + synchronization."

First determine the actual workload and concurrency requirement.

Dedicated concurrent collections will be covered later.

# 15. Mistakes / Corrections From Our Discussion

### Mistake 1

Initial thought:

> "LinkedList won't be accessible through index."

Correction:

> LinkedList supports indexed access, but it is O(n) because it requires traversal.

### Mistake 2

Initial thought:

> "LinkedList insertion is O(1)."

Correction:

> Link modification is O(1) once the target node is known. Finding an arbitrary position can make the overall operation O(n).

### Mistake 3

Initial thought:

> "LinkedList should be faster because insertion/removal is O(1)."

Correction:

> Big-O alone does not determine real-world performance. Memory locality, object overhead, allocations, and reference chasing matter.

# 16. LinkedList Mental Model

```text
                 LinkedList
                     │
              doubly linked nodes
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
     known node/end        arbitrary index
          │                     │
     modify links            find node
          │                     │
        O(1)                  O(n)
                                │
                                ↓
                         modify links O(1)
                                │
                                ↓
                           overall O(n)
```

The most important sentence:

> **LinkedList's O(1) insertion/removal advantage applies when the target node is already known; locating an arbitrary position can still cost O(n).**
