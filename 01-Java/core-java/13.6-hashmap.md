# 13.6 — HashMap

> Interview-focused notes from our HashMap discussion: hashing, buckets, collisions, treeification, resizing, load factor, key equality, mutable keys, null behavior, useful APIs, production scenarios, and interview traps.

## 1. Core idea

HashMap stores:

```text
Key → Value
```

Example:

```java
Map<String, Payment> payments = new HashMap<>();
payments.put("P101", payment);
Payment p = payments.get("P101");
```

The goal is fast lookup by key.

## 2. HashMap vs HashSet

Conceptually:

```text
HashSet
    ↓
HashMap internally
    ↓
element → dummy value
```

HashMap explicitly stores:

```text
key → value
```

Their hashing/collision mechanics are closely related.

## 3. `put()` mental model

```text
key
 ↓
hashCode()
 ↓
hash spreading
 ↓
bucket index
 ↓
bucket contents
 ↓
existing key?
 ↓
equals()
```

If the key is new, insert the mapping. If the logical key already exists, the value is replaced.

```java
map.put(k1, v1);
map.put(k2, v2);
```

If `k1.equals(k2)` is true, there is one logical mapping after the second put, associated with the new value.

## 4. `equals()` and `hashCode()`

If:

```java
k1.equals(k2) == true
```

then:

```java
k1.hashCode() == k2.hashCode()
```

is required.

But:

```text
same hash
    ⇏
same key
```

Different keys can have the same hash; that is a collision.

## 5. Bucket calculation

HashMap uses a power-of-two table capacity. Conceptually, for table size `n`:

```java
index = (n - 1) & hash;
```

after hash spreading.

For capacity 16:

```text
n - 1 = 15
15 = 01111
```

so masking produces an index from 0 to 15.

Power-of-two capacity also makes resizing efficient.

## 6. Hash spreading

The raw `hashCode()` is not simply used directly. HashMap spreads the hash so higher-bit information can influence bucket selection.

Mental model:

```text
key
 ↓
hashCode()
 ↓
hash spreading
 ↓
bucket index
```

For interview purposes, understand the purpose rather than memorizing exact JDK source.

## 7. Collisions

Different keys can map to the same bucket:

```text
P1 → bucket 5
P2 → bucket 5
P3 → bucket 5
```

Conceptually:

```text
bucket 5

[P1 → V1] → [P2 → V2] → [P3 → V3]
```

Multiple entries in one bucket are normal.

## 8. `get()` with a collision

Conceptually:

```text
P2
 ↓
hashCode()
 ↓
spread hash
 ↓
bucket 5
 ↓
candidate entries
 ↓
hash/key checks
 ↓
equals()
 ↓
P2 found
 ↓
return V2
```

HashMap narrows the search to a bucket rather than scanning the whole map.

## 9. `put()` with a collision

If the bucket already contains other keys, HashMap checks whether one is the same logical key.

If no existing key is equal, the new mapping is inserted.

If an existing key is equal, its value is updated.

## 10. Why hash distribution matters

A few collisions are normal. A pathological implementation such as:

```java
@Override
public int hashCode() {
    return 1;
}
```

for every key can put many keys in one bucket.

That destroys the normal performance benefit of hashing.

## 11. Treeification

Modern Java HashMap can convert a heavily-colliding bucket from a collision chain into a tree when the implementation's treeification conditions are met.

Conceptually:

```text
Before:
K1 → K2 → K3 → K4 → ...

After:
       K3
      /  \
    K1    K5
     \   /
      K2 K4
```

The tree is a Red-Black Tree.

Important:

> Do not say normal HashMap lookup is O(log n). Normal basic operations are expected O(1) under good hashing; treeification is a mitigation for pathological collisions.

## 12. Resize vs treeification

Resizing gives the map more buckets:

```text
16 → 32 → 64 → ...
```

which can reduce collisions.

Treeification handles a bucket that remains heavily populated.

Think:

```text
collision pressure
       ↓
   resize / treeify
```

Exact JDK thresholds are implementation details; don't spend interview-prep time memorizing them unless specifically asked.

## 13. Capacity

Capacity is the number of buckets.

Example:

```text
capacity = 16
```

means bucket positions 0 through 15.

Capacity is different from the number of entries.

## 14. Load factor and threshold

A commonly used default load factor is:

```text
0.75
```

For example:

```text
capacity = 16
load factor = 0.75
```

gives an approximate resize threshold:

```text
16 × 0.75 = 12
```

The threshold is not a hard maximum number of entries. Reaching the threshold causes growth rather than preventing additional entries.

Load factor is a trade-off:

```text
lower load factor
 → more memory
 → generally fewer collisions

higher load factor
 → less memory
 → potentially more collisions
```

## 15. Resizing

When the relevant threshold is reached, the table grows, typically doubling:

```text
16 → 32
32 → 64
64 → 128
```

Existing entries must be redistributed according to the new table size.

That resize work is expensive:

```text
resize → O(n)
```

for the entries processed.

## 16. Does resize make `put()` O(n)?

No.

Most puts do not resize. Occasionally a put triggers an expensive resize.

Therefore normal HashMap insertion is described as:

```text
expected / amortized O(1)
```

under normal assumptions.

This is similar to the amortized reasoning we used for ArrayList.

## 17. Why can entries stay or move by old capacity?

Suppose:

```text
old capacity = 16
new capacity = 32
```

The old mask is:

```text
01111
```

and the new mask is:

```text
11111
```

One additional hash bit becomes relevant.

Therefore an entry can generally:

```text
stay in the old bucket
```

or:

```text
move to old bucket + old capacity
```

Example:

```text
old bucket = 5
old capacity = 16

new bucket = 5
or
new bucket = 21
```

because:

```text
5 + 16 = 21
```

Mental model:

```text
old bucket
   |
   +-- new bit = 0 → same bucket
   |
   +-- new bit = 1 → old bucket + old capacity
```

## 18. Initial capacity

If you know approximately how many entries will be stored, an appropriate initial capacity can reduce unnecessary resize operations:

```java
Map<String, Payment> payments = new HashMap<>(expectedCapacity);
```

Don't blindly allocate a huge map because that wastes memory.

## 19. Complexity

Under good hash distribution:

```text
put()         → expected O(1)
get()         → expected O(1)
remove()      → expected O(1)
containsKey() → expected O(1)
```

Do not say:

> HashMap is always O(1).

Better:

> HashMap provides expected O(1) basic operations under good hash distribution.

## 20. Ordering

HashMap does not guarantee insertion order or sorted order.

Use:

```text
LinkedHashMap → insertion order
TreeMap       → sorted keys
```

Do not rely on whatever iteration order happens to appear.

## 21. `null` and `get()`

HashMap permits a null key and null values.

Therefore:

```java
map.put("A", null);
map.get("A"); // null
```

But:

```java
map.get("B"); // also null if B is absent
```

So:

```java
map.get(key) == null
```

does not by itself distinguish an absent key from a key mapped to null.

## 22. `containsKey()` vs `get()`

If the question is:

> Does this key exist?

use:

```java
map.containsKey(key)
```

rather than relying on:

```java
map.get(key) != null
```

when null values are valid.

## 23. Mutable key problem

This is one of the most important production traps.

```java
Map<Employee, String> map = new HashMap<>();

Employee e = new Employee("E101");
map.put(e, "Employee Data");

// Dangerous if id participates in equals/hashCode
e.setId("E999");
```

The key's equality/hash identity has changed after insertion.

Conceptually:

```text
At insertion:
E101 → hash → bucket 5

After mutation:
E999 → different hash → possibly bucket 12
```

The entry is still associated with its old bucket structure, so subsequent lookup can fail.

Production rule:

> Keys should ideally be immutable with respect to fields used by `equals()` and `hashCode()`.

## 24. Thread safety

HashMap is not inherently thread-safe.

If multiple threads share a HashMap and concurrently modify it, use an appropriate concurrency strategy.

Do not reduce thread safety to only:

> "Another thread won't see my update."

Thread safety is broader and includes concerns such as:

```text
visibility
atomicity
safe concurrent access
internal consistency
```

`ConcurrentHashMap` is the concurrency-oriented map we will study later in the Multithreading section.

## 25. `computeIfAbsent()`

A useful Java 8+ API:

```java
map.computeIfAbsent(key, k -> createValue());
```

If the key is absent (or mapped to null), the mapping function is used to compute a value and the value is associated with the key.

The Java API documents `computeIfAbsent` specifically for constructing an initial mapped value and for multi-value maps. citeturn0search0

## 26. What is `k`?

In:

```java
map.computeIfAbsent(userId, k -> new ArrayList<>());
```

`k` is simply the lambda parameter.

It represents the key passed to the mapping function.

If:

```text
userId = "U101"
```

then conceptually:

```text
k = "U101"
```

`k` has no special Java meaning. You can rename it:

```java
map.computeIfAbsent(
    userId,
    userIdKey -> new ArrayList<>()
);
```

Both mean the same thing.

## 27. Why is `k` unused?

This:

```java
k -> new ArrayList<>()
```

accepts the key parameter but doesn't need it.

If the key were needed:

```java
map.computeIfAbsent(
    userId,
    key -> createListForUser(key)
);
```

then:

```text
userId = "U101"
   ↓
key = "U101"
   ↓
createListForUser("U101")
```

## 28. Production scenario — Multi-value Map

Suppose:

```java
Map<String, List<String>> userPayments =
    new HashMap<>();
```

Desired structure:

```text
U101 → [P1, P2, P3]
U102 → [P4, P5]
```

Without `computeIfAbsent()`:

```java
if (!userPayments.containsKey(userId)) {
    userPayments.put(userId, new ArrayList<>());
}

userPayments.get(userId).add(paymentId);
```

With it:

```java
userPayments
    .computeIfAbsent(userId, k -> new ArrayList<>())
    .add(paymentId);
```

This is a useful backend pattern.

## 29. `computeIfAbsent()` does not make HashMap thread-safe

Using:

```java
computeIfAbsent()
```

does not turn a normal HashMap into a concurrent collection.

The general `Map` contract does not provide synchronization or atomicity guarantees for the default implementation. Concurrent implementations can provide stronger concurrency guarantees. citeturn0search6

We will cover concurrent-map behavior later with `ConcurrentHashMap`.

## 30. Production scenario — Lookup table

Example:

```text
accountId → AccountConfig
```

If the map is local/non-concurrent and the requirement is fast key lookup:

```java
Map<String, AccountConfig> configs =
    new HashMap<>();
```

is a natural choice.

## 31. Production scenario — Counting

Classic example:

```java
Map<String, Integer> counts = new HashMap<>();
```

For:

```text
P101
P102
P101
P103
P102
P101
```

you can maintain:

```text
P101 → 3
P102 → 2
P103 → 1
```

## 32. Production scenario — Deduplication / indexing

Suppose records have an `accountId` and you need fast lookup of records already processed:

```java
Map<String, Record> processed =
    new HashMap<>();
```

Then:

```java
processed.containsKey(accountId)
```

or:

```java
processed.get(accountId)
```

provides expected O(1) lookup under normal hashing assumptions.

# Interview Answers

## "Explain HashMap"

> HashMap stores key-value mappings and uses the key's hash to locate a bucket. It then uses key equality to identify the matching key within that bucket. Under good hash distribution, basic operations such as get and put are expected O(1). Collisions are handled within buckets, and heavily-colliding buckets can be treeified in modern Java. The map grows when its resize threshold based on capacity and load factor is reached. During a doubling resize, entries generally either stay in the same bucket or move by the old capacity.

## "Why both hashCode() and equals()?"

> hashCode helps locate the candidate bucket efficiently; equals determines whether a candidate key is actually the same logical key.

## "Why should keys be immutable?"

> If fields used by equals/hashCode change after insertion, the key's hash location can no longer match its current hash, causing lookups to fail. Immutable keys avoid this class of bug.

# Interview Traps

1. **HashMap is always O(1).**  
   Better: expected O(1) under good hash distribution.

2. **HashMap uses only hashCode().**  
   No. Hashing narrows the search; equality identifies the logical key.

3. **Same hash means same key.**  
   No. Different keys can collide.

4. **`get(key) == null` means the key doesn't exist.**  
   Not necessarily; the key can be mapped to null.

5. **HashMap maintains insertion order.**  
   No.

6. **Every bucket is a LinkedList.**  
   Too simplistic. Modern buckets can be treeified under heavy collisions.

7. **Treeification means HashMap is normally O(log n).**  
   No. Normal expected lookup is O(1); treeification mitigates pathological collisions.

8. **`computeIfAbsent()` is thread-safe.**  
   Not for an ordinary HashMap.

9. **Mutable objects are safe HashMap keys.**  
   Not if fields used by equals/hashCode are changed while the key is stored.
