# 13.7 — LinkedHashMap

> Interview-focused notes. Keep this topic lighter than HashMap. The key idea is **HashMap-like lookup + predictable encounter order**.

---

# 1. Core Idea

The simplest mental model:

```text
HashMap
   +
doubly-linked ordering structure
   ↓
LinkedHashMap
```

LinkedHashMap maintains a linked structure through its entries so that iteration has a predictable encounter order.

Therefore:

```text
HashMap
→ fast key lookup
→ no guaranteed iteration order

LinkedHashMap
→ fast key lookup
→ predictable encounter order
```

---

# 2. Basic Example

```java
Map<String, Integer> map = new LinkedHashMap<>();

map.put("A", 10);
map.put("B", 20);
map.put("C", 30);
```

Iteration is:

```text
A
B
C
```

by default.

Conceptually, there are two aspects:

```text
Hash structure:
A → 10
B → 20
C → 30

Linked ordering:
A ↔ B ↔ C
```

The linked structure is for ordering; it is not used as the primary key lookup mechanism.

---

# 3. Complexity

Assuming good hash distribution:

```text
put()      → expected O(1)
get()      → expected O(1)
remove()   → expected O(1)
```

The linked ordering adds some maintenance/memory overhead compared with HashMap.

Important:

> Do not say LinkedHashMap lookup is O(n) because it has a linked list.

The linked structure maintains order; hashing is still used for lookup.

---

# 4. Default Order = Insertion Order

Example:

```java
map.put(30, "A");
map.put(10, "B");
map.put(20, "C");
```

Iteration:

```text
30
10
20
```

It is **not sorted**.

Mental model:

```text
HashMap
    → no guaranteed order

LinkedHashMap
    → insertion order by default

TreeMap
    → sorted key order
```

---

# 5. What Happens When an Existing Key Is Reinserted?

Example:

```java
map.put("A", 10);
map.put("B", 20);
map.put("C", 30);

map.put("A", 100);
```

With the normal insertion-order configuration, the order remains:

```text
A
B
C
```

The value for A becomes:

```text
A → 100
```

Reinserting an existing key does not by itself move it to the end in normal insertion-order mode.

---

# 6. Access-Order

LinkedHashMap can be configured for access-order:

```java
LinkedHashMap<String, Integer> map =
    new LinkedHashMap<>(16, 0.75f, true);
```

The third argument:

```text
true
```

means:

```text
accessOrder = true
```

Now the order reflects recent access.

Start:

```text
A → B → C
```

Then:

```java
map.get("A");
```

The order becomes:

```text
B → C → A
```

This is different from insertion order.

---

# 7. Why Is Access-Order Useful?

The major production use case is:

> **LRU — Least Recently Used caching.**

Suppose the cache holds only 3 entries.

Current order:

```text
A → B → C
```

Then:

```java
cache.get("A");
```

Access order becomes:

```text
B → C → A
```

Now B is the least recently used entry.

If another entry must be inserted, B is a candidate for eviction.

---

# 8. `removeEldestEntry()` and LRU-Style Cache

LinkedHashMap provides `removeEldestEntry()` so a subclass can impose an eviction policy.

Example:

```java
LinkedHashMap<String, Data> cache =
    new LinkedHashMap<>(16, 0.75f, true) {

        @Override
        protected boolean removeEldestEntry(
                Map.Entry<String, Data> eldest) {
            return size() > 1000;
        }
    };
```

Conceptually:

```text
accessOrder = true
        +
removeEldestEntry()
        ↓
LRU-style bounded cache
```

This is one of the most valuable LinkedHashMap scenarios to remember for interviews.

---

# 9. LinkedHashMap vs HashMap

| Requirement | HashMap | LinkedHashMap |
|---|---:|---:|
| Key → value | Yes | Yes |
| Expected O(1) lookup | Yes | Yes |
| Predictable insertion order | No | Yes |
| Access-order mode | No | Yes |
| LRU-style building block | No | Yes |
| Extra ordering overhead | No | Yes |

Decision:

```text
Need only fast lookup?
        ↓
HashMap

Need fast lookup + insertion order?
        ↓
LinkedHashMap

Need fast lookup + access order / LRU-style behavior?
        ↓
LinkedHashMap(accessOrder = true)
```

---

# 10. LinkedHashMap vs TreeMap

Do not confuse insertion order with sorted order.

Suppose keys are inserted:

```text
30
10
20
```

LinkedHashMap:

```text
30
10
20
```

TreeMap:

```text
10
20
30
```

Mental model:

```text
LinkedHashMap
    → encounter/insertion order

TreeMap
    → sorted key order
```

# 11. Production Scenario — Preserve Input Order

Suppose records arrive:

```text
P103
P101
P105
P102
```

and you want a Map while preserving the original encounter order.

Use:

```java
LinkedHashMap
```

The output can retain:

```text
P103
P101
P105
P102
```

For the same requirement when you only need a Set:

```java
LinkedHashSet
```

This connects directly to the Set topic.

# 12. Production Scenario — API / Processing Order

Suppose a processing pipeline wants to retain the order in which keys/items were encountered:

```text
customer
account
payment
transaction
```

A LinkedHashMap can preserve that predictable encounter order while still providing hash-based key lookup.

# 13. Production Scenario — LRU Cache

This is the most important scenario:

```text
LinkedHashMap
      ↓
accessOrder = true
      ↓
recently accessed item moves toward the newest end
      ↓
eldest item represents least-recently-used candidate
      ↓
removeEldestEntry()
      ↓
bounded LRU-style cache
```

For an interview, be able to explain this flow.

---

# 14. Thread Safety

LinkedHashMap is not inherently thread-safe.

Do not assume:

```text
LinkedHashMap
    ↓
safe shared concurrent cache
```

No.

For concurrent access, an appropriate concurrency design is required.

We will study concurrent collections, including `ConcurrentHashMap`, later in the **Multithreading** section.

# 17. Interview Answer — "Explain LinkedHashMap"

> "`LinkedHashMap` is a HashMap-based Map implementation that additionally maintains a linked ordering structure for predictable iteration. By default it preserves insertion order. It can also be configured for access-order, which makes it useful as a building block for LRU-style caches when combined with an eviction policy such as `removeEldestEntry()`. Its basic operations remain expected O(1) under good hash distribution, with some additional memory and maintenance overhead for ordering."

# 18. Interview Traps

### Trap 1

> LinkedHashMap sorts keys.

No.

It preserves encounter order; it does not sort keys.

### Trap 2

> LinkedHashMap searches using the linked list.

No.

Hashing is still used for key lookup. The linked structure maintains order.

### Trap 3

> Updating an existing key moves it to the end.

Not in normal insertion-order mode.

Access-order is a separate configuration.

### Trap 4

> `accessOrder = true` means sorted by key.

No.

It means order is based on access, not key sorting.

### Trap 5

> LinkedHashMap is thread-safe.

No.

### Trap 6

> LinkedHashMap is just HashMap with no meaningful overhead.

It maintains additional ordering links, so it has additional memory/maintenance overhead.

# Final Mental Model

```text
                    Map
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
    HashMap    LinkedHashMap    TreeMap
        │            │            │
        ↓            ↓            ↓
     hashing      hashing      tree
        │            │            │
        ↓            ↓            ↓
   fast lookup   fast lookup   O(log n)
                    +
              predictable order
```

The most important decision rule:

```text
Fast lookup only
    → HashMap

Fast lookup + insertion/access order
    → LinkedHashMap

Sorted keys / range navigation
    → TreeMap
```
