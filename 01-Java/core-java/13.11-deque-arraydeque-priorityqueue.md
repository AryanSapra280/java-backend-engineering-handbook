# 13.11 — Deque, ArrayDeque & PriorityQueue

> Interview-focused notes. This completes the main Queue family for our current Collections phase. After this, move to **Generics**. Concurrent queue variants are intentionally parked for the Multithreading phase.

---

# 1. Deque

`Deque` means:

> **Double-Ended Queue**

Unlike a normal FIFO Queue, a Deque allows insertion and removal from **both ends**.

```text
        front
          ↓
[A] [B] [C] [D]
          ↑
         back
```

You can:

```text
add/remove from front
add/remove from back
```

Therefore a Deque can behave as either:

```text
FIFO Queue
```

or:

```text
LIFO Stack
```

---

# 2. Important Deque Methods

There are three useful groups of methods.

## Add

```java
deque.addFirst(x);
deque.addLast(x);
```

or non-exception-style:

```java
deque.offerFirst(x);
deque.offerLast(x);
```

Mental model:

```text
addFirst / offerFirst
    → front

addLast / offerLast
    → back
```

---

## Remove

```java
deque.removeFirst();
deque.removeLast();
```

or:

```java
deque.pollFirst();
deque.pollLast();
```

Mental model:

```text
pollFirst()
    → remove front

pollLast()
    → remove back
```

---

## Examine

```java
deque.getFirst();
deque.getLast();
```

or:

```java
deque.peekFirst();
deque.peekLast();
```

Mental model:

```text
peekFirst()
    → look at front

peekLast()
    → look at back
```

---

# 3. Deque Method Cheat Sheet

| Purpose | First/front | Last/back |
|---|---|---|
| Insert | `offerFirst()` | `offerLast()` |
| Remove | `pollFirst()` | `pollLast()` |
| Examine | `peekFirst()` | `peekLast()` |

Exception-style alternatives:

```text
addFirst() / addLast()
removeFirst() / removeLast()
getFirst() / getLast()
```

For normal application code, the `offer*`, `poll*`, and `peek*` family is often convenient because failure/empty behavior is represented without exceptions.

---

# 4. Deque as a Queue

Use only one direction:

```java
Deque<String> deque = new ArrayDeque<>();

deque.offerLast("A");
deque.offerLast("B");
deque.offerLast("C");
```

Conceptually:

```text
A → B → C
```

Remove from the front:

```java
deque.pollFirst();
```

Result:

```text
A
```

This gives normal FIFO behavior:

```text
offerLast()
     ↓
  [A][B][C]
     ↓
pollFirst()
```

So:

> **Deque can implement Queue behavior.**

---

# 5. Deque as a Stack ⭐

A Deque can also implement LIFO behavior.

Use the same end for both insertion and removal:

```java
Deque<String> stack = new ArrayDeque<>();

stack.push("A");
stack.push("B");
stack.push("C");
```

Conceptually:

```text
C ← top
B
A
```

Then:

```java
stack.pop();
```

returns:

```text
C
```

So:

```text
push() → add to front
pop()  → remove from front
peek() → inspect front
```

This gives:

```text
Last In → First Out
```

---

# 6. Why Deque Instead of `Stack`?

Java's legacy:

```java
Stack
```

is an older class.

For a normal non-concurrent stack use:

```java
Deque<T> stack = new ArrayDeque<>();
```

This is generally preferred.

Interview answer:

> "I would generally use Deque, usually ArrayDeque, for stack behavior rather than the legacy Stack class."

Do not turn this into a long discussion about legacy APIs unless asked.

---

# 7. ArrayDeque

For our purposes, ArrayDeque is the important general-purpose Deque implementation.

```java
Deque<String> deque = new ArrayDeque<>();
```

It is array-backed and designed for efficient operations at both ends.

Conceptually:

```text
       circular array

    [ ][ ][ ][ ][ ][ ]
      ↑             ↑
    head           tail
```

The circular structure allows the implementation to reuse positions at the beginning/end without shifting all elements.

---

# 8. ArrayDeque Complexity

Typical end operations are:

```text
offerFirst() → O(1) amortized
offerLast()  → O(1) amortized

pollFirst()  → O(1)
pollLast()   → O(1)

peekFirst()  → O(1)
peekLast()   → O(1)
```

Like ArrayList, occasional resizing can make an individual insertion more expensive, which is why insertion is described as **amortized O(1)**.

The important interview point:

> ArrayDeque provides efficient operations at both ends.

---

# 9. Why ArrayDeque Instead of LinkedList?

Both can implement Deque:

```text
LinkedList
    → node-based

ArrayDeque
    → array-backed
```

LinkedList has per-node overhead:

```text
previous
element
next
```

ArrayDeque avoids a separate node object for every element and generally has better memory locality.

Therefore:

> For a normal non-concurrent Queue/Deque workload, ArrayDeque is generally the preferred implementation.

Don't say:

> ArrayDeque is always faster.

Better:

> "For a normal non-concurrent FIFO/LIFO workload, I'd generally prefer ArrayDeque because it is array-backed, has good locality, and avoids LinkedList's per-node overhead while supporting efficient operations at both ends."

---

# 10. ArrayDeque vs ArrayList

ArrayList is optimized around:

```text
index-based access
```

ArrayDeque is optimized around:

```text
front/back operations
```

Therefore:

```text
Need random access?
    → ArrayList

Need FIFO/LIFO operations at the ends?
    → ArrayDeque
```

Do not use:

```java
list.remove(0);
```

as your normal queue implementation because front removal can require shifting elements.

---

# 11. ArrayDeque vs LinkedList

| Requirement | LinkedList | ArrayDeque |
|---|---|---|
| Queue behavior | Yes | Yes |
| Deque behavior | Yes | Yes |
| Stack behavior | Yes | Yes |
| Array-backed | No | Yes |
| Per-node overhead | Yes | No separate node per element |
| Good memory locality | Generally worse | Generally better |
| General non-concurrent Queue/Deque choice | Valid | Usually preferred |

---

# 12. Important ArrayDeque Limitation

ArrayDeque does **not permit null elements**.

This is useful to remember because some other collections have different null behavior.

For interview preparation:

```text
ArrayDeque
    → no null elements
```

This also makes `null` available as an unambiguous sentinel for operations such as `poll()`/`peek()` when appropriate.

---

# 13. ArrayDeque Is Not Thread-Safe

Just because it supports efficient operations at both ends does not mean it supports concurrent access.

```text
ArrayDeque
    ↓
not inherently thread-safe
```

If multiple threads need a shared queue/deque, use an appropriate concurrent collection.

We will cover:

```text
BlockingQueue
ConcurrentLinkedQueue
ConcurrentLinkedDeque
```

later under **Multithreading**.

Do not go deeper now.

# 14. Production Scenario — Browser History / Undo

Deque is useful when work can be manipulated from both ends.

Examples:

```text
undo / redo style structures
work queues with front/back insertion
sliding-window algorithms
double-ended processing
```

For simple LIFO behavior, use it as a stack:

```java
Deque<Action> actions = new ArrayDeque<>();

actions.push(action);
Action latest = actions.pop();
```

---

# 15. Production Scenario — Sliding Window

A Deque is a classic data structure for sliding-window algorithms.

Conceptually:

```text
window
[A][B][C][D]
 ↑         ↑
front     back
```

You may:

```text
remove obsolete elements from front
add new elements at back
```

This is especially important for DSA.

A common example is:

> Sliding Window Maximum.

You maintain a monotonic Deque so that the maximum candidate stays at one end.

You don't need to learn the full algorithm here; just remember:

```text
Deque
    → very useful for sliding-window problems
```

# 16. PriorityQueue

Now the important distinction:

> PriorityQueue is **not a FIFO queue**.

A normal Queue:

```text
A → B → C
```

removes:

```text
A
B
C
```

A PriorityQueue removes according to priority/order.

Example:

```text
C → priority 3
A → priority 1
B → priority 2
```

Removal order:

```text
A
B
C
```

---

# 17. PriorityQueue Internal Structure

PriorityQueue is implemented using a **heap**, specifically a priority heap.

For the normal natural-order PriorityQueue, the smallest element has the highest priority.

Conceptually:

```text
             1
           /   \
          3     2
         / \
        7   5
```

The exact internal array representation is implementation detail, but the important interview concept is:

```text
PriorityQueue
    ↓
heap
    ↓
highest-priority element at the head
```

---

# 18. PriorityQueue Complexity

For a standard PriorityQueue:

```text
offer() / add() → O(log n)
poll()           → O(log n)
peek()           → O(1)
```

Why?

### `peek()`

The highest-priority element is at the heap root:

```text
O(1)
```

### `offer()`

New element may need to move upward:

```text
O(log n)
```

### `poll()`

Removing the root requires heap reorganization:

```text
O(log n)
```

This is an important interview distinction from ArrayDeque:

```text
ArrayDeque
    → O(1) end operations

PriorityQueue
    → O(log n) insertion/removal
    → O(1) peek
```

---

# 19. PriorityQueue Ordering

Natural ordering:

```java
PriorityQueue<Integer> pq = new PriorityQueue<>();
```

Then:

```java
pq.offer(30);
pq.offer(10);
pq.offer(20);
```

`peek()` gives:

```text
10
```

and repeated `poll()` gives:

```text
10
20
30
```

---

# 20. Max-Heap / Reverse Priority

By default:

```text
smallest element first
```

For largest-first behavior:

```java
PriorityQueue<Integer> pq =
    new PriorityQueue<>(Comparator.reverseOrder());
```

Now:

```text
30
20
10
```

comes out in descending priority.

This connects directly to the Comparator topic we just completed.

---

# 21. PriorityQueue with Custom Objects

Suppose:

```java
class Job {
    int priority;
}
```

You can provide a Comparator:

```java
PriorityQueue<Job> jobs =
    new PriorityQueue<>(
        Comparator.comparing(Job::getPriority)
    );
```

Now the queue is ordered according to the priority field.

For highest numeric priority first:

```java
PriorityQueue<Job> jobs =
    new PriorityQueue<>(
        Comparator.comparing(
            Job::getPriority,
            Comparator.reverseOrder()
        )
    );
```

---

# 22. Production Scenario — Job Scheduler

Suppose jobs have:

```text
priority
timestamp
jobId
```

Requirement:

```text
highest priority first
same priority → oldest job first
same timestamp → jobId
```

A PriorityQueue is a natural fit:

```java
Comparator<Job> comparator =
    Comparator.comparing(
        Job::getPriority,
        Comparator.reverseOrder()
    ).thenComparing(Job::getTimestamp)
     .thenComparing(Job::getJobId);

PriorityQueue<Job> queue =
    new PriorityQueue<>(comparator);
```

This combines our Comparator knowledge with PriorityQueue.

# 23. Production Scenario — Top K Problems

PriorityQueue is extremely useful for:

```text
Top K largest
Top K smallest
Kth largest
Kth smallest
```

Example:

> Find the 10 largest transactions from millions of transactions.

You don't necessarily need to sort all millions.

You can maintain a small heap of size 10.

Conceptually:

```text
millions of records
       ↓
small PriorityQueue
       ↓
keep only top 10
```

This is a very important DSA + backend interview pattern.

---

# 24. Production Scenario — Scheduling / Next Best Work

If work has different priorities:

```text
Critical
High
Medium
Low
```

FIFO is no longer enough.

Use:

```text
PriorityQueue
```

when the requirement is:

> Always process the highest-priority eligible item next.

---

# 25. PriorityQueue Is NOT Fully Sorted

This is a classic interview trap.

If you put:

```text
30
10
20
40
```

into a PriorityQueue, the internal structure is **not a fully sorted list**.

The important guarantee is:

```text
peek()
    → highest-priority element
```

and repeated:

```text
poll()
```

will remove elements in priority order.

Do not say:

> PriorityQueue maintains all elements in sorted order.

It maintains heap ordering, not complete sorted iteration order.

---

# 26. PriorityQueue Iteration Trap

This:

```java
for (Integer x : pq) {
    System.out.println(x);
}
```

should **not** be used as a way to get sorted output.

If you need priority order:

```java
while (!pq.isEmpty()) {
    System.out.println(pq.poll());
}
```

But remember:

> Polling consumes/removes the elements.

---

# 27. PriorityQueue vs TreeSet

Both can involve ordering, but they solve different problems.

```text
PriorityQueue
    → repeatedly get highest/lowest priority
    → duplicates allowed
    → heap
```

```text
TreeSet
    → unique sorted elements
    → ordered set operations
    → tree
```

If you need:

> "Give me the smallest element repeatedly."

PriorityQueue is often a better fit.

If you need:

> "Maintain a sorted set with navigation and uniqueness."

TreeSet is more appropriate.

---

# 28. PriorityQueue vs TreeMap

Similarly:

```text
PriorityQueue
    → priority-based retrieval
```

while:

```text
TreeMap
    → key → value
    → sorted keys
    → navigation/range operations
```

Use the abstraction that matches the requirement.

---

# 29. Null and PriorityQueue

PriorityQueue does not permit null elements.

```text
PriorityQueue
    → no null elements
```

It needs to compare/order elements, so `null` is not a valid normal queue element.

---

# 30. Thread Safety

PriorityQueue is not inherently thread-safe.

```text
PriorityQueue
    ↓
not thread-safe
```

For concurrent priority-based producer/consumer behavior, later learn:

```text
PriorityBlockingQueue
```

under Multithreading.

```text

    → indexed access

    → priority-based retrieval
```

# 35. Interview Traps

### Trap 1

> PriorityQueue is FIFO.

No.

```text
PriorityQueue → priority
Queue → FIFO
```

### Trap 2

> PriorityQueue is fully sorted internally.

No.

It maintains heap ordering sufficient to expose the highest-priority element.

### Trap 3

> Iterating PriorityQueue gives sorted order.

Don't rely on it.

Use repeated `poll()` when priority order is required.

### Trap 4

> ArrayDeque is thread-safe.

No.

### Trap 5

> LinkedList is always better because insertion/removal is O(1).

Not a good conclusion.

For a normal Queue/Deque workload, ArrayDeque is generally preferred because of its array-backed representation, locality, and lower per-element overhead.

### Trap 6

> Deque is only a Queue.

No.

Deque can behave as:

```text
FIFO Queue
+
LIFO Stack
```

### Trap 7

> PriorityQueue gives O(log n) peek.

No.

```text
peek → O(1)
poll → O(log n)
```
