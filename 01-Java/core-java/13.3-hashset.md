# 13.3 — HashSet

> Collections learning note from our discussion. Focus: HashSet internals, hashing, buckets, collisions, `equals()`/`hashCode()`, load factor, resizing, complexity, mutable elements, ordering, and production scenarios.

---

# 1. Set — The Abstraction

A Set is appropriate when the primary requirement is:

> **Uniqueness.**

Example:

```java
Set<String> ids = new HashSet<>();

ids.add("P101");
ids.add("P102");
ids.add("P101");
```

Logically:

```text
P101
P102
```

The duplicate `P101` is not added as a separate logical element.

---

# 2. HashSet — Core Idea

`HashSet` is the first Set implementation we study.

Its key property is:

```text
uniqueness
+
expected fast membership operations
```

Under normal/good hashing:

```text
add()       → expected O(1)
contains()  → expected O(1)
remove()    → expected O(1)
```

Do not say:

> "HashSet is always O(1)."

Better:

> **HashSet provides expected O(1) insertion, lookup, and removal under good hash distribution.**

---

# 3. HashSet Is Implemented Using HashMap

One of the most important facts:

> **HashSet is implemented using a HashMap internally.**

Conceptually:

```text
HashSet
   ↓
HashMap
   ↓
hash table / buckets
```

The Set element is effectively stored as a key in an internal map with a dummy/shared value.

Conceptually:

```text
HashSet:

P1
P2
P3
```

is represented internally along the lines of:

```text
HashMap:

P1 → dummy
P2 → dummy
P3 → dummy
```

The exact implementation details are JDK internals, but the HashSet → HashMap relationship is the key mental model.

---

# 4. What Happens During `add()`?

Suppose:

```java
set.add(payment);
```

Conceptually:

```text
payment
   ↓
hashCode()
   ↓
hash
   ↓
bucket index
   ↓
bucket
```

If the bucket is empty:

```text
bucket
   ↓
payment
```

The element can be inserted.

If the bucket already contains candidates, equality checking is required.

---

# 5. What Is a Bucket?

Conceptually, the underlying hash table contains an array of buckets:

```text
index
  0    1    2    3    4    5    6    7
 ┌──┬──┬──┬──┬──┬──┬──┬──┐
 │  │  │  │  │  │  │  │  │
 └──┴──┴──┴──┴──┴──┴──┴──┘
```

An object's hash is used to determine which bucket should be examined.

Conceptually:

```text
object
   ↓
hashCode()
   ↓
hash
   ↓
bucket index
```

The actual JDK calculation includes implementation details such as hash spreading and table sizing. For interviews, understand the flow rather than memorizing the exact bit operations.

---

# 6. Duplicate Detection

Suppose:

```java
set.add("Aryan");
```

and later:

```java
set.add("Aryan");
```

Conceptually:

```text
"Aryan"
   ↓
hashCode()
   ↓
same relevant bucket
   ↓
existing candidate
   ↓
equals()
   ↓
equal
   ↓
do not insert another element
```

The fundamental lookup flow is:

```text
hashCode()
    ↓
candidate bucket
    ↓
equals()
    ↓
duplicate or new element
```

---

# 7. Why `hashCode()` and `equals()` Both Matter

Hashing is used to quickly narrow down the possible location.

Equality is used to confirm logical equality.

So:

```text
hashCode()
    ↓
where should I look?
    ↓
equals()
    ↓
is this actually the same logical element?
```

This directly connects to the `equals()` / `hashCode()` concepts studied before Collections.

---

# 8. The `equals()` / `hashCode()` Contract

For objects used in HashSet:

> If `a.equals(b)` is `true`, then `a.hashCode()` must equal `b.hashCode()`.

Formally:

```text
a.equals(b) == true
        ↓
a.hashCode() == b.hashCode()
```

The reverse is NOT required.

You can have:

```text
a.hashCode() == b.hashCode()
```

while:

```text
a.equals(b) == false
```

That situation is a hash collision.

---

# 9. Why Same Hash Does Not Mean Same Object

Suppose:

```text
P1 → hash 12345
P2 → hash 12345
```

but:

```text
P1.equals(P2) == false
```

Both may map to the same bucket.

Therefore:

```text
same hash
    ↓
candidate collision
    ↓
equals()
    ↓
different objects
```

HashSet must keep both.

This is why `hashCode()` alone cannot determine uniqueness.

---

# 10. Hash Collision

A collision occurs when multiple different elements map to the same bucket.

Conceptually:

```text
bucket 3

P1 → P2 → P3
```

When looking for an element in that bucket, HashSet compares candidates using equality.

Conceptually:

```text
P_NEW.equals(P1)?
    ↓
false

P_NEW.equals(P2)?
    ↓
false

P_NEW.equals(P3)?
    ↓
false

insert P_NEW
```

The exact node/tree representation is an implementation detail, but the important model is:

```text
hash
 ↓
bucket
 ↓
candidate(s)
 ↓
equals()
```

---

# 11. Bad `hashCode()` — Production Impact

Suppose someone writes:

```java
@Override
public int hashCode() {
    return 1;
}
```

for every object.

Then:

```text
P1 → bucket 1
P2 → bucket 1
P3 → bucket 1
P4 → bucket 1
...
```

The hash table loses its ability to distribute elements effectively.

The expected O(1) advantage can degrade significantly because operations have to examine many candidates in the same bucket.

### Production lesson

> A good hash function should distribute objects reasonably across buckets.

---

# 12. Modern Collision Handling

Modern Java implementations can transform a heavily populated bucket into a balanced tree structure under specific conditions.

Conceptually:

```text
Normal bucket:

P1 → P2 → P3 → P4


Heavy collision bucket:

       P2
      /      P1    P4
          /
         P3
```

This can improve lookup behavior in heavily-colliding buckets.

For SDE-2 interviews:

> Modern HashMap/HashSet implementations can treeify heavily populated buckets under certain conditions.

Do not memorize exact threshold values unless specifically asked about JDK internals.

---

# 13. Load Factor

Load factor describes how full the hash table is relative to its bucket-array capacity.

Conceptually:

```text
load factor
=
number of entries / table capacity
```

Example:

```text
capacity = 16
entries  = 12

load factor = 12 / 16
            = 0.75
```

A higher load factor generally means:

```text
more entries per table
      ↓
potentially more collisions
      ↓
less empty space
      ↓
lower memory usage
```

A lower load factor generally means:

```text
more empty buckets
      ↓
fewer collisions
      ↓
more memory usage
```

Therefore load factor is a trade-off between:

```text
memory
   ↕
collision probability / lookup behavior
```

---

# 14. Resizing

A HashSet does not keep using the same bucket array forever.

When the table crosses its resize threshold, it grows.

Conceptually:

```text
current capacity
       ↓
threshold reached
       ↓
larger bucket array
       ↓
entries redistributed
```

The resize operation is expensive because entries have to be reorganized according to the new table size.

But this does not make every `add()` O(n).

Under normal conditions:

```text
add() → expected O(1)
```

with occasional expensive resizing.

---

# 15. Why HashSet `add()` Is Expected O(1)

Most insertions:

```text
hash
 ↓
bucket
 ↓
small number of candidates
 ↓
equals()
 ↓
insert
```

are constant-ish work under good hashing.

Occasionally:

```text
resize
 ↓
redistribute entries
 ↓
O(n)-scale work
```

So we describe normal HashSet insertion as:

> **Expected/amortized O(1)** under typical good hashing assumptions.

For interview wording, **expected O(1)** is usually the safest phrase.

# 18. Overall Deduplication Complexity

Suppose we have:

```text
n transaction IDs
```

and want unique IDs.

```java
Set<String> uniqueIds = new HashSet<>();

for (String id : transactionIds) {
    uniqueIds.add(id);
}
```

Each insertion is expected O(1).

But there are `n` elements.

Therefore:

```text
n × expected O(1)
=
expected O(n)
```

Space:

```text
O(n)
```

in the worst case when all IDs are unique.

Important distinction:

```text
one HashSet.add()       → expected O(1)
deduplicating n values  → expected O(n)
```

---

# 19. HashSet vs ArrayList for Membership

Suppose:

```text
10 million transaction IDs
```

Requirement:

> Does this ID already exist?

### ArrayList

```java
ids.contains(id);
```

Worst case:

```text
O(n)
```

### HashSet

```java
ids.contains(id);
```

Expected:

```text
O(1)
```

Therefore:

```text
membership testing
        ↓
HashSet
```

is the natural choice when ordering/index access is not required.

# 20. Mutable Element Trap

This is a major production-level HashSet issue.

Suppose:

```java
Set<Payment> payments = new HashSet<>();

Payment p = new Payment("P100", 500);
payments.add(p);
```

Suppose `equals()` and `hashCode()` depend on:

```text
paymentId
amount
```

Then:

```java
p.setAmount(1000);
```

changes the hash-related state.

Conceptually:

```text
At insertion:

hash(P100, 500)
      ↓
bucket 5
```

After mutation:

```text
hash(P100, 1000)
      ↓
bucket 9
```

But the actual object is still physically located where it was inserted.

Now:

```java
payments.contains(p);
```

may fail unexpectedly.

### Production rule

> Do not mutate fields that participate in `equals()` / `hashCode()` while the object is being used as a HashSet element or HashMap key.

Prefer immutable key/identity fields.

---

# 21. HashSet Ordering

HashSet does **not guarantee insertion order**.

Example:

```java
Set<String> ids = new HashSet<>();

ids.add("P3");
ids.add("P1");
ids.add("P2");
```

Do not write business logic that assumes the iteration order will be:

```text
P3
P1
P2
```

or:

```text
P1
P2
P3
```

The Set contract does not guarantee insertion order.

If order becomes a requirement, choose the appropriate Set implementation.

# 24. ArrayList vs HashSet

| Requirement | ArrayList | HashSet |
|---|---|---|
| Duplicates | Allowed | Not allowed |
| Preserve index | Yes | No |
| `get(index)` | O(1) | Not applicable |
| `contains()` | O(n) worst case | Expected O(1) |
| Add | Amortized O(1) at end | Expected O(1) |
| Ordering guarantee | Yes | No insertion-order guarantee |
| Best for | Ordered/indexed sequence | Uniqueness + membership |

# 25. SDE-2 Interview Answer: "Explain HashSet Internally"

A strong concise answer:

> "`HashSet` is implemented using a `HashMap` internally. When an element is added, its `hashCode()` is used to determine the candidate bucket. If there are existing entries in that bucket, `equals()` is used to determine whether the element is already present. Hash collisions are handled within the bucket, and modern Java implementations can treeify heavily-colliding buckets under certain conditions. Under good hash distribution, `add`, `contains`, and `remove` are expected O(1). The table grows when its load-factor threshold is crossed, which causes resizing and redistribution."

If pushed deeper, discuss:

```text
load factor
resizing
collisions
treeification
mutable keys/elements
equals/hashCode contract
```

# 26. Mistakes / Important Corrections

### Mistake 1

> "HashSet is O(1)."

Better:

> HashSet operations are **expected O(1)** under good hashing.

---

### Mistake 2

> "Same hash means same object."

Wrong.

Correct:

```text
same hash
   ↓
possible collision
   ↓
equals()
   ↓
actual equality
```

---

### Mistake 3

> "If equals() is true, hashCode can be different."

Wrong.

Correct:

```text
a.equals(b) == true
        ↓
a.hashCode() == b.hashCode()
```

---

### Mistake 4

> "Deduplicating n elements with HashSet is O(1)."

Wrong.

One insertion is expected O(1).

Processing `n` elements is:

```text
expected O(n)
```

---

### Mistake 5

> "HashSet preserves insertion order."

Wrong.

HashSet provides no insertion-order guarantee.

---

### Mistake 6

> "ConcurrentModificationException means multiple threads."

Not necessarily. It can occur during single-threaded iteration if the collection is structurally modified outside the iterator's expected mechanism.

# 27. HashSet Mental Model

```text
                   HashSet
                      │
                      ↓
               HashMap internally
                      │
                      ↓
                  hashCode()
                      │
                      ↓
                   bucket
                      │
              ┌───────┴───────┐
              ↓               ↓
          empty bucket     candidates
              ↓               ↓
            insert          equals()
                              │
                       ┌──────┴──────┐
                       ↓             ↓
                    equal         different
                       ↓             ↓
                    reject         insert
```

Performance:

```text
Good hash distribution
        ↓
few collisions
        ↓
expected O(1)


Poor hash distribution
        ↓
many collisions
        ↓
more work
        ↓
performance degradation
```
