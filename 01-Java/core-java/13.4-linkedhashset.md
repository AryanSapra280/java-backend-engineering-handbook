# 13.4 — LinkedHashSet

> Collections learning note from our discussion. Focus: what LinkedHashSet adds over HashSet, insertion-order maintenance, memory trade-offs, production scenarios, and the meaning of "not thread-safe."

---

# 1. What Problem Does LinkedHashSet Solve?

We already know:

```text
HashSet
    ↓
uniqueness
+
expected O(1) hash-based operations
```

Now add one requirement:

> **I need uniqueness AND insertion-order iteration.**

Use:

```java
Set<String> ids = new LinkedHashSet<>();
```

Example:

```java
ids.add("P3");
ids.add("P1");
ids.add("P2");
ids.add("P1");
```

Iteration gives:

```text
P3
P1
P2
```

The duplicate `P1` does not create another element or move the original `P1`.

---

# 2. What Does LinkedHashSet Add to HashSet?

Mental model:

```text
HashSet
    ↓
uniqueness

LinkedHashSet
    ↓
uniqueness
+
insertion-order iteration
```

LinkedHashSet maintains the hash-based structure needed for fast lookup and an additional linked ordering structure.

Conceptually:

```text
Hash structure:

buckets
  ↓
P1 / P2 / P3


Insertion-order links:

P3 ↔ P1 ↔ P2
```

So it has two important responsibilities:

```text
hash structure
    ↓
fast membership / uniqueness

linked order structure
    ↓
predictable insertion-order iteration
```

---

# 3. Why Is an Additional Linked Structure Needed?

Hashing determines bucket placement.

Suppose:

```text
add P3
add P1
add P2
```

Their hash values determine where they live in the hash table.

The bucket arrangement is not designed to represent:

```text
P3 → P1 → P2
```

as insertion order.

Therefore LinkedHashSet maintains ordering information separately.

Mental model:

```text
Hashing
   ↓
where the element belongs

Linked ordering
   ↓
when the element was inserted
```

---

# 4. Complexity

For normal hash-based operations:

```text
add()       → expected O(1)
contains()  → expected O(1)
remove()    → expected O(1)
```

Maintaining insertion order does not fundamentally change the expected complexity of these operations.

However, LinkedHashSet requires additional memory for its ordering links.

So:

```text
HashSet
    ↓
less memory

LinkedHashSet
    ↓
more memory
    +
insertion-order guarantee
```

---

# 5. Insertion Order

Consider:

```java
Set<String> ids = new LinkedHashSet<>();

ids.add("A");
ids.add("B");
ids.add("C");
ids.add("A");
```

Iteration:

```text
A
B
C
```

The second `A` does not move `A` to the end.

Why?

Because `A` was already present.

The ordering represents:

> **The first successful insertion of each unique element.**

---

# 6. Remove and Reinsert

Suppose:

```text
A
B
C
```

Then:

```java
set.remove("B");
```

gives:

```text
A
C
```

Now:

```java
set.add("B");
```

gives:

```text
A
C
B
```

Because B has been inserted again after it was removed.

---

# 7. LinkedHashSet Is NOT Sorted

This is an important distinction.

If:

```java
ids.add("C");
ids.add("A");
ids.add("B");
```

iteration is:

```text
C
A
B
```

not:

```text
A
B
C
```

Therefore:

```text
LinkedHashSet
    ↓
insertion order

TreeSet
    ↓
sorted order
```

TreeSet will be covered separately.

---

# 8. HashSet vs LinkedHashSet

| Property | HashSet | LinkedHashSet |
|---|---|---|
| Uniqueness | Yes | Yes |
| Expected `add()` | O(1) | O(1) |
| Expected `contains()` | O(1) | O(1) |
| Expected `remove()` | O(1) | O(1) |
| Insertion-order guarantee | No | Yes |
| Memory overhead | Lower | Higher |
| Primary use | Uniqueness | Uniqueness + insertion order |

Decision:

```text
Need uniqueness only?
        ↓
HashSet

Need uniqueness + insertion order?
        ↓
LinkedHashSet
```

---

# 9. Memory Trade-Off

HashSet needs its hash-table structure.

LinkedHashSet additionally maintains links that connect entries in insertion order.

Conceptually:

```text
HashSet:

P1
P2
P3


LinkedHashSet:

P1 ↔ P2 ↔ P3
```

Therefore:

```text
LinkedHashSet
    ↓
additional ordering metadata
    ↓
higher memory overhead
```

The trade-off is:

> **Pay additional memory to get deterministic insertion-order iteration.**

---

# 10. Production Scenario

Suppose an API receives:

```text
P101
P103
P101
P105
P103
P107
```

Requirement:

> Return unique IDs in the order they were first encountered.

Expected result:

```text
P101
P103
P105
P107
```

Use:

```java
Set<String> uniqueIds = new LinkedHashSet<>();

for (String id : incomingIds) {
    uniqueIds.add(id);
}
```

This directly expresses the business requirement:

```text
unique
+
first-seen order
```

---

# 11. Don't Use LinkedHashSet Just Because Order Looks Nice

Suppose the requirement is only:

> "Does this ID exist?"

and iteration order has no business meaning.

Then:

```java
HashSet
```

is sufficient.

Using LinkedHashSet unnecessarily adds ordering overhead.

Collection choice should follow the actual requirement.

---

# 12. Thread Safety — Important Clarification

`LinkedHashSet` is **not inherently thread-safe**.

But this statement needs to be understood correctly.

It does **NOT** simply mean:

> "If Thread A deletes an element, Thread B won't see the deletion."

That is not the definition of thread safety.

There are several separate concepts.

---

# 13. Visibility vs Thread Safety

Suppose:

```text
Thread A
    ↓
shared LinkedHashSet
    ↓
remove(element)

Thread B
    ↓
same LinkedHashSet
    ↓
contains(element)
```

There are multiple concerns.

### Concern 1 — Visibility

Does Thread B reliably observe Thread A's latest write?

Without the appropriate **happens-before / synchronization / concurrency mechanism**, you cannot rely on ordinary unsynchronized shared-memory access to provide the visibility guarantees your program needs.

So:

> "The deletion may not be visible immediately" is related to **memory visibility**, not the complete definition of thread safety.

---

### Concern 2 — Atomicity / Race Conditions

Suppose two threads do:

```java
if (!set.contains(id)) {
    set.add(id);
}
```

Even if each individual operation appeared to work, the **compound operation** is not automatically atomic.

Possible interleaving:

```text
Thread A                 Thread B

contains(id) → false
                         contains(id) → false

add(id)
                         add(id)
```

Both threads may observe the element as absent.

So:

> Thread safety also concerns whether operations and sequences of operations behave correctly when executed concurrently.

---

### Concern 3 — Internal Data Structure Consistency

A collection such as LinkedHashSet has internal state:

```text
hash structure
+
ordering links
+
size
+
other bookkeeping
```

Concurrent structural modifications without proper coordination can cause race conditions and invalid/inconsistent behavior.

The collection itself does not provide the synchronization needed to make shared concurrent modification safe.

---

# 14. What Does "Thread-Safe Collection" Actually Mean?

A useful interview definition:

> **A thread-safe collection provides the necessary synchronization/concurrency guarantees so that its supported operations remain correct when accessed concurrently by multiple threads.**

This is broader than:

```text
"Thread B sees Thread A's update."
```

It involves:

```text
visibility
+
atomicity
+
safe interaction with shared internal state
+
correct behavior under concurrent access
```

The exact guarantees depend on the collection/API.

---

# 15. Important Interview Correction

If an interviewer asks:

> "Is LinkedHashSet thread-safe?"

Answer:

> **"No. LinkedHashSet is not inherently thread-safe. If multiple threads share and modify the same instance, external synchronization or an appropriate concurrent design is required."**

Do NOT answer:

> "No, because changes aren't visible to other threads."

That answer is too narrow and potentially misleading.

A better explanation is:

```text
not thread-safe
      ↓
no built-in concurrency guarantees
      ↓
shared concurrent access/modification
      ↓
must provide appropriate synchronization/coordination
```

We'll cover the actual concurrent collection choices later when we reach concurrency.

# 16. LinkedHashSet vs ArrayList

This comparison is useful when uniqueness is involved.

| Requirement | ArrayList | LinkedHashSet |
|---|---|---|
| Duplicates | Allowed | Not allowed |
| Insertion order | Yes | Yes |
| `contains()` | O(n) worst case | Expected O(1) |
| Index access | O(1) | Not applicable |
| Unique elements | Manual handling | Built in |
| Typical use | Ordered sequence | Unique elements + insertion order |

Example:

```text
Need:
unique IDs
+
first-seen order
+
fast membership checks
```

LinkedHashSet is a natural fit.

---

# 17. SDE-2 Interview Answer

If asked:

> **"What's the difference between HashSet and LinkedHashSet?"**

A strong answer:

> "`HashSet` provides uniqueness with expected O(1) insertion, lookup, and removal under good hashing, but doesn't guarantee iteration order. `LinkedHashSet` maintains an additional linked ordering structure so iteration follows insertion order while retaining expected O(1) hash-based operations. The trade-off is additional memory overhead."

If asked about thread safety:

> "`LinkedHashSet` is not inherently thread-safe. Shared concurrent access or modification requires appropriate synchronization or a concurrency-oriented design. Thread safety is broader than just whether another thread sees a particular update."
