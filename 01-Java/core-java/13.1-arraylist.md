# 13.1 — ArrayList

> Collections learning note from our discussion. Captures the reasoning, questions, mistakes/corrections, production considerations, complexity, amortized analysis, iterator behavior, and interview scenarios.

## 1. Collections Learning Philosophy

For every collection:

```text
How does it work?
→ Why choose it?
→ Operations?
→ Complexity?
→ Memory?
→ Ordering?
→ Duplicates?
→ Thread safety?
→ Production scenario?
→ Alternatives?
```

The goal is to choose a collection because its characteristics match the workload, not because we memorized its name.

---

# 2. What Is a List?

A List represents an ordered sequence and permits duplicates.

```java
List<Payment> payments;
```

Example:

```text
P1
P2
P1
P3
```

Requirements:

```text
duplicates        → allowed
ordering/position → important
key → value        → not required
```

---

# 3. ArrayList — Core Idea

`ArrayList` is an array-backed implementation of `List`.

Conceptually:

```text
index:   0    1    2    3    4
        [P1] [P2] [P3] [P4] [P5]
```

Therefore:

```java
payments.get(4);
```

is `O(1)`.

---

# 4. ArrayList vs LinkedList — First Derivation

For:

```text
10 million payments
95% → random index reads
5%  → append
```

ArrayList is the natural choice because:

```text
ArrayList.get(index)  → O(1)
LinkedList.get(index) → O(n)
```

Important correction:

> LinkedList **does support** indexed access. It is simply inefficient because it must traverse nodes to reach the requested position.

---

# 5. ArrayList Internal Representation

Conceptually:

```text
ArrayList
    ↓
backing array
    ↓
references to elements
```

The backing array stores references, not the actual object contents.

```text
[ref][ref][ref][ref][ref]
  ↓    ↓    ↓
 P1   P2   P3
```

Therefore:

```java
new ArrayList<>(1_000_000);
```

does **not** create one million Payment objects. It reserves capacity for references.

---

# 6. Size vs Capacity

```java
ArrayList<Payment> payments = new ArrayList<>(100);
```

Initially:

```text
size     = 0
capacity = 100
```

After adding three elements:

```text
size     = 3
capacity = 100
```

Mental model:

```text
size     → number of actual elements
capacity → space currently available in backing storage
```

---

# 7. What Happens When Capacity Is Full?

If:

```text
[P1][P2][P3][P4]
```

is full and we do:

```java
list.add(P5);
```

conceptually:

```text
old array
   ↓
allocate larger array
   ↓
copy existing references
   ↓
add P5
```

The resize itself can require copying `n` elements:

```text
resize → O(n)
```

---

# 8. Why Doesn't ArrayList Grow by Exactly One Slot?

If it grew:

```text
5 → 6 → 7 → 8 → 9 → ...
```

every append after capacity exhaustion could cause allocation and copying.

Instead, it grows by a larger amount:

```text
old capacity
      ↓
larger capacity
      ↓
many future appends
```

This reduces resize frequency.

Do **not** say:

> ArrayList always doubles its capacity.

Interview-safe wording:

> ArrayList grows its capacity according to its implementation's growth policy, allowing multiple future appends before another resize.

The exact growth policy is an implementation detail, not a language guarantee.

---

# 9. Why Is `add(element)` Amortized O(1)?

Most appends are cheap:

```text
add → O(1)
```

Occasionally:

```text
add
 ↓
resize
 ↓
copy n elements
 ↓
O(n)
```

So a sequence can look like:

```text
add 1 → O(1)
add 2 → O(1)
add 3 → O(1)
add 4 → O(1)
add 5 → O(n)  ← resize
add 6 → O(1)
...
```

Therefore:

> Appending to ArrayList is **amortized O(1)**.

---

# 10. What Does O(1) Mean?

`O(1)` means the operation's asymptotic cost does not grow with collection size.

For example:

```java
list.get(500000);
```

is:

```text
O(1)
```

because indexed access is direct.

`O(1)` does not mean "instant"; it means the cost does not scale with `n`.

---

# 11. What Does O(n) Mean?

`O(n)` means the amount of work can grow linearly with the number of elements.

For example, a search through:

```text
10 elements
1,000 elements
1,000,000 elements
```

may inspect a corresponding number of elements.

---

# 12. What Does Amortized O(1) Mean?

For intuition, amortized cost can be thought of as average cost over a sequence.

But technically:

> Amortized analysis is **not statistical average-case analysis**.

It reasons about the total cost of a sequence of operations and spreads occasional expensive operations across many cheap operations.

For ArrayList:

```text
many cheap appends
+
occasional expensive resize
```

So:

```text
individual append:
sometimes O(n)

long sequence:
amortized O(1) per append
```

Do not confuse:

```text
average-case analysis
```

with:

```text
amortized analysis
```

---

# 13. ArrayList Append

```java
list.add(element);
```

At the end:

```text
amortized O(1)
```

Most operations are O(1), with occasional O(n) resizing.

---

# 14. Random Access

```java
list.get(index);
```

is:

```text
O(1)
```

Likewise:

```java
list.set(index, value);
```

is:

```text
O(1)
```

assuming a valid index.

---

# 15. Insertion at an Arbitrary Index

Suppose:

```text
[P1][P2][P3][P4][P5]
```

and:

```java
list.add(2, P_NEW);
```

Elements after the insertion point must shift:

```text
[P1][P2][P_NEW][P3][P4][P5]
```

Worst case:

```java
list.add(0, element);
```

requires shifting almost all elements.

Therefore:

```text
add(index, element) → O(n)
```

### Why amortized analysis does not apply

Even if spare capacity exists:

```text
[P1][P2][P3][P4][P5][ ][ ][ ]
```

inserting at the front still requires shifting existing elements.

So it remains `O(n)`.

---

# 16. Removal at an Arbitrary Index

```text
[P1][P2][P3][P4][P5]

remove(2)

[P1][P2][P4][P5]
```

P4 and P5 shift left.

Therefore:

```text
remove(index) → O(n)
```

in the general/worst case.

---

# 17. Removing from the End

```java
list.remove(list.size() - 1);
```

requires no shifting.

Therefore:

```text
remove(last) → O(1)
```

Mental model:

```text
get(index)         → O(1)
set(index, value)  → O(1)

add(end)           → amortized O(1)
remove(end)        → O(1)

add(index)         → O(n)
remove(index)      → O(n)

contains()         → O(n)
```

---

# 18. `contains()`

```java
list.contains(target);
```

ArrayList generally performs a linear search.

Conceptually:

```text
P1 → match?
P2 → match?
P3 → match?
...
```

Best case can be `O(1)` if the first element matches.

Worst case:

```text
O(n)
```

For interview complexity, state:

> `contains()` is O(n) in the worst case.

Object comparison relies on equality semantics, so `equals()` matters.

---

# 19. Choosing the Right Data Structure

Suppose:

```text
5 million payments
```

and we repeatedly need:

```java
payments.contains(target);
```

This can require scanning millions of elements.

Instead ask:

> Is ArrayList the right data structure for this access pattern?

If the requirement is:

```text
paymentId → Payment
```

use:

```java
Map<String, Payment> paymentsById = new HashMap<>();
```

Then:

```java
paymentsById.get(paymentId);
```

has expected `O(1)` lookup.

Core Phase-2 principle:

```text
Requirement
    ↓
Access pattern
    ↓
Choose data structure
    ↓
Complexity
```

---

# 20. Memory Locality

Both ArrayList and LinkedList can have `O(n)` sequential iteration, but ArrayList is generally faster.

ArrayList:

```text
[P1][P2][P3][P4][P5][P6]
```

Its backing array gives good memory locality and benefits from CPU caching/prefetching.

LinkedList:

```text
[P1 | next] → [P2 | next] → [P3 | next]
```

uses separately allocated nodes that do not have to be adjacent in memory.

LinkedList also has greater per-element memory overhead because nodes contain additional links/references.

Strong interview wording:

> Both are O(n) for sequential iteration, but ArrayList generally performs better because its backing array provides better memory locality and lower per-element overhead, whereas LinkedList requires traversing separately allocated nodes.

---

# 21. Big-O Doesn't Tell the Whole Performance Story

Two operations can both be:

```text
O(n)
```

but have different real performance because of:

- memory locality
- CPU cache behavior
- hardware prefetching
- allocation overhead
- pointer/reference chasing
- constant factors

Therefore:

> Big-O describes asymptotic growth; it does not fully describe real-world performance.

---

# 22. Initial Capacity and Over-Allocation

Suppose:

```java
ArrayList<Payment> payments = new ArrayList<>(1_000_000);
```

but only 10 elements are stored.

Conceptually:

```text
capacity = 1,000,000
size     = 10
```

Most reserved reference slots are unused.

Important:

```java
new ArrayList<>(1_000_000);
```

does not create one million Payment objects.

It reserves capacity for references.

### Production trade-off

Too small:

```text
small initial capacity
      ↓
more resizing
      ↓
more copying
```

Too large:

```text
huge initial capacity
      ↓
unnecessary reserved memory
      ↓
memory pressure
```

Best principle:

> If you have a reliable estimate, choose a reasonable initial capacity. Don't massively over-allocate.

---

# 23. List vs Queue — Important Design Decision

We considered:

```text
add to end
remove from beginning
FIFO processing
```

It is tempting to compare:

```text
ArrayList vs LinkedList
```

But the better question is:

> Is `List` even the correct abstraction?

If the semantics are:

```text
append at end
+
remove from beginning
+
FIFO
```

a Queue/Deque may be more appropriate:

```java
Deque<Payment> payments = new ArrayDeque<>();
```

Important Phase-2 lesson:

> Sometimes the answer isn't "ArrayList vs LinkedList." Step back and ask whether List is the correct abstraction.

We parked Queue/concurrency details for the later Queue section.

# 24. Modifying ArrayList During Enhanced `for`

Problematic code:

```java
for (Payment payment : payments) {
    if (payment.getStatus() == FAILED) {
        payments.remove(payment);
    }
}
```

The enhanced `for` loop uses an Iterator internally.

Directly modifying the list while the iterator is traversing can result in:

```text
ConcurrentModificationException
```

---

# 25. `ConcurrentModificationException` Does Not Necessarily Mean Multiple Threads

This can happen in a single thread:

```java
for (Payment p : payments) {
    payments.remove(p);
}
```

"Concurrent" here refers to structural modification occurring while an iterator is in use, outside the iterator's expected modification mechanism.

It does not necessarily mean multiple threads.

---

# 26. Iterator

Safe iterator-based removal:

```java
Iterator<Payment> iterator = payments.iterator();

while (iterator.hasNext()) {
    Payment payment = iterator.next();

    if (payment.getStatus() == FAILED) {
        iterator.remove();
    }
}
```

---

# 27. `hasNext()`

```java
iterator.hasNext();
```

asks:

> Is another element available?

It does not advance the iterator.

```text
hasNext()
 ↓
check
 ↓
position unchanged
```

---

# 28. `next()`

```java
iterator.next();
```

conceptually:

1. returns the next element
2. advances the iterator

Example:

```text
[P1][P2][P3][P4]

next() → P1
next() → P2
next() → P3
```

The iterator also remembers the element most recently returned by `next()`.

---

# 29. `Iterator.remove()`

After:

```java
Payment payment = iterator.next();
```

the iterator knows the element most recently returned.

Therefore:

```java
iterator.remove();
```

means:

> Remove the element most recently returned by `next()`.

Conceptually:

```text
next()
 ↓
returns P3
 ↓
iterator remembers P3
 ↓
remove()
 ↓
remove P3
```

You don't pass the object to `remove()`.

---

# 30. How Does Iterator Detect Modification?

Common fail-fast implementations use modification-count bookkeeping.

Conceptually:

```text
ArrayList
 └── modification count

Iterator
 └── expected modification count
```

Example:

```text
ArrayList modification count = 5
Iterator expected count       = 5
```

Direct structural modification:

```text
ArrayList modification count = 6
Iterator expected count       = 5
```

The iterator can detect the mismatch and fail fast.

This is conceptual implementation reasoning; exact private field names should not be treated as Java language guarantees.

---

# 31. Why `iterator.remove()` Works

When:

```java
iterator.remove();
```

performs the modification, the iterator can keep its bookkeeping consistent with the collection.

Mental model:

```text
Direct list modification
        ↓
iterator not updated through expected mechanism
        ↓
fail-fast detection

iterator.remove()
        ↓
iterator-aware modification
        ↓
traversal remains consistent
```

---

# 32. `removeIf()`

When the requirement is simply:

> Remove every element matching a condition.

Use:

```java
payments.removeIf(
    payment -> payment.getStatus() == FAILED
);
```

Conceptually:

```text
iterate
   ↓
test predicate
   ↓
true → remove
false → keep
```

Example:

```text
P1 → SUCCESS
P2 → FAILED
P3 → SUCCESS
P4 → FAILED
P5 → FAILED
```

After:

```java
payments.removeIf(p -> p.getStatus() == FAILED);
```

the list contains:

```text
P1
P3
```

---

# 33. Iterator vs `removeIf()`

### Iterator

You control traversal:

```java
while (iterator.hasNext()) {
    Payment p = iterator.next();

    if (...) {
        iterator.remove();
    }
}
```

Use when you need custom traversal logic.

### `removeIf()`

You provide the condition:

```java
payments.removeIf(p -> ...);
```

Use when you simply want to remove every matching element.

Mental model:

```text
Iterator
    ↓
I control traversal + removal

removeIf()
    ↓
I provide the condition
    ↓
Java handles traversal/removal mechanics
```

`removeIf()` mutates the existing collection.

---

# 34. Iterator Rule

`Iterator.remove()` applies to the element most recently returned by `next()`.

Therefore:

```text
next()
 ↓
remove()
```

is valid.

But:

```text
remove()
remove()
```

without another `next()` is invalid iterator usage.

Calling `remove()` before the first `next()` is also invalid.

---

# 35. Production Scenario — ArrayList

Workload:

```text
10 million payments
- mostly append
- frequent sequential iteration
- occasional random index access
- very few middle insertions/removals
- no FIFO requirement
```

Reasoning:

```text
append
   ↓
ArrayList → amortized O(1)

random access
   ↓
ArrayList → O(1)

iteration
   ↓
excellent locality

middle insertion/removal
   ↓
rare
```

ArrayList is a strong choice.

---

# 36. Production Scenario — Wrong Data Structure

Workload:

```text
5 million payments
Repeated lookup by paymentId
```

Bad fit:

```java
payments.contains(target);
```

because it is O(n).

Better:

```java
Map<String, Payment> paymentsById = new HashMap<>();
```

because the access pattern is key-based lookup.

---

# 37. Concurrency Note

ArrayList is not designed as a thread-safe collection for concurrent structural modification.

But:

> "The application is multithreaded" does not automatically mean ArrayList cannot be used.

Thread confinement is valid:

```text
Request 1 → its own ArrayList
Request 2 → its own ArrayList
```

The real question is whether the same collection is shared and concurrently modified, and what synchronization guarantees are required.

Dedicated concurrency discussion will come later.

# 38. ArrayList vs LinkedList — Mental Model

```text
                    List
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
      ArrayList             LinkedList
          │                     │
   backing array             nodes
          │                     │
   index access O(1)       index access O(n)
          │
 append amortized O(1)
          │
 insertion/removal
 at arbitrary index O(n)
          │
 good locality
          │
 lower per-element
 memory overhead
```

Important:

> LinkedList is not automatically better just because insertion/removal can be O(1). The cost of reaching the position, memory overhead, cache locality, and actual workload all matter.

# 39. Mistakes / Corrections From Our Discussion

### Mistake 1

> "LinkedList won't be accessible through index."

Correction:

> LinkedList supports indexed access, but it is O(n) because traversal is required.

### Mistake 2

> "ArrayList usually doubles capacity."

Correction:

> ArrayList grows according to its implementation's growth policy. Do not treat doubling as a Java language guarantee.

### Mistake 3

> "Amortized means average."

Correction:

> It is useful to think of amortized cost as average cost over a sequence, but technically amortized analysis is not statistical average-case analysis.

### Mistake 4

> "`ArrayList.add()` is O(1)."

Correction:

> Append is **amortized O(1)** because occasional resizing is O(n).

### Mistake 5

> "If there is spare capacity, middle insertion is O(1)."

Correction:

> Existing elements still need to shift, so arbitrary-index insertion remains O(n).

### Mistake 6

> "`ConcurrentModificationException` means multiple threads."

Correction:

> It can occur in a single thread when a collection is structurally modified during iterator-based traversal outside the iterator's expected mechanism.

### Mistake 7

> "LinkedList is better because insertion/removal is O(1)."

Correction:

> The link update can be O(1) once the position is known, but reaching an arbitrary position can be O(n). Memory overhead and locality also matter.

# 40. Complexity Cheat Sheet

| Operation | Complexity | Why |
|---|---:|---|
| `get(index)` | O(1) | Direct indexed access |
| `set(index, value)` | O(1) | Direct indexed access |
| `add(element)` at end | Amortized O(1) | Occasional resize |
| `add(index, element)` | O(n) | Shift elements |
| `remove(index)` | O(n) | Shift elements |
| `remove(last)` | O(1) | No shifting |
| `contains()` | O(n) | Linear search |
| Sequential iteration | O(n) | Visit each element |
| Resize | O(n) | Copy references |
