# 13.8 — TreeMap

> Interview-focused notes. Core idea: **sorted keys + tree-based lookup/navigation**. Keep implementation details focused; advanced `Comparable`/`Comparator` and sorting are parked for a dedicated topic.

---

# 1. Core Idea

The Map family:

```text
HashMap
    → fast key lookup

LinkedHashMap
    → fast key lookup + predictable encounter order

TreeMap
    → sorted keys + navigation
```

The fundamental difference:

> **TreeMap is tree-based, not hash-based.**

TreeMap is backed by a self-balancing Red-Black Tree.

---

# 2. Internal Structure

Conceptually:

```text
             50
           /    \
         30      80
        /  \    /  \
      20   40  70   90
```

Keys remain ordered:

```text
20
30
40
50
70
80
90
```

Therefore:

```text
put()         → O(log n)
get()         → O(log n)
remove()      → O(log n)
containsKey() → O(log n)
```

Unlike HashMap:

```text
HashMap → expected O(1)
TreeMap → O(log n)
```

---

# 3. How Does TreeMap Find a Key?

Suppose:

```java
map.get(40);
```

The tree compares:

```text
40 vs 50
    ↓
40 < 50 → go left

40 vs 30
    ↓
40 > 30 → go right

40 found
```

Mental model:

```text
key
 ↓
comparison
 ↓
left / right
 ↓
comparison
 ↓
...
 ↓
found
```

This is the same comparison-based idea used by TreeSet.

---

# 4. How Does TreeMap Know the Ordering?

There are two main possibilities.

## Natural ordering

Keys implement `Comparable`.

```java
TreeMap<Integer, Payment> map = new TreeMap<>();
```

`Integer` already has natural ordering.

## Custom ordering

Provide a `Comparator`:

```java
TreeMap<Payment, String> map =
    new TreeMap<>(Comparator.comparing(Payment::getAmount));
```

The comparator determines the ordering.

We will cover `Comparable` vs `Comparator` and sorting as a separate short topic later.

---

# 5. TreeMap vs HashMap

| Property | HashMap | TreeMap |
|---|---|---|
| Structure | Hash table | Red-Black Tree |
| Lookup | Expected O(1) | O(log n) |
| Ordering | None guaranteed | Sorted |
| Comparator | No ordering comparator | Yes |
| `floorKey()` | No | Yes |
| `ceilingKey()` | No | Yes |
| `lowerKey()` | No | Yes |
| `higherKey()` | No | Yes |
| Range operations | No sorted-range semantics | Yes |

Decision:

```text
Need:
"Find value for ID"
        ↓
HashMap

Need:
"Find smallest key >= X"
        ↓
TreeMap
```

---

# 6. Navigation Operations

This is one of TreeMap's biggest advantages.

Suppose:

```java
TreeMap<Integer, String> map = new TreeMap<>();

map.put(10, "A");
map.put(20, "B");
map.put(30, "C");
map.put(40, "D");
map.put(50, "E");
```

## `floorKey(x)`

Largest key `<= x`:

```java
map.floorKey(35);
```

Result:

```text
30
```

## `ceilingKey(x)`

Smallest key `>= x`:

```java
map.ceilingKey(35);
```

Result:

```text
40
```

## `lowerKey(x)`

Largest key `< x`:

```java
map.lowerKey(30);
```

Result:

```text
20
```

## `higherKey(x)`

Smallest key `> x`:

```java
map.higherKey(30);
```

Result:

```text
40
```

Mental model:

```text
floor    → <=
ceiling  → >=
lower    → <
higher   → >
```

---

# 7. `firstKey()` / `lastKey()`

Because TreeMap keeps keys sorted:

```java
map.firstKey();
map.lastKey();
```

return:

```text
smallest key
largest key
```

This is a natural operation for TreeMap but not for HashMap.

---

# 8. Range Queries

TreeMap supports ordered range views such as:

```java
subMap()
headMap()
tailMap()
```

Suppose keys are:

```text
10
20
30
40
50
60
```

Then:

```java
map.subMap(20, 50);
```

provides the portion in the requested range according to the method's boundary semantics.

Conceptually:

```text
20
30
40
```

This is useful when the requirement is based on a key range rather than an exact key.

# 9. Production Scenario — Price Tiers

Suppose pricing tiers are:

```text
100  → Basic
500  → Standard
1000 → Premium
5000 → Enterprise
```

Customer budget:

```text
750
```

Requirement:

> Find the largest tier that does not exceed the budget.

Use:

```java
pricing.floorEntry(750);
```

Result:

```text
500 → Standard
```

This is a strong TreeMap scenario because the business requirement is inherently ordered.

---

# 10. Production Scenario — Scheduling

Suppose scheduled events are keyed by timestamp:

```text
10:00 → Event A
10:30 → Event B
11:00 → Event C
12:00 → Event D
```

Requirement:

> Find the next event after 10:40.

Use the appropriate higher-key/entry operation:

```java
events.higherEntry(10:40);
```

Result:

```text
11:00 → Event C
```

TreeMap is useful because the timestamps remain ordered dynamically.

---

# 11. Production Scenario — Time-Based Data

Imagine:

```text
timestamp → state
```

and you need:

```text
previous state
next state
state at/before timestamp
state at/after timestamp
```

TreeMap provides natural operations for this:

```text
floorEntry(timestamp)
ceilingEntry(timestamp)
lowerEntry(timestamp)
higherEntry(timestamp)
```

This is a useful backend pattern for ordered time-based lookups.

---

# 12. Production Scenario — Dynamic Ordered Data

TreeMap is a good candidate when the workload contains:

```text
frequent insertion
+
frequent deletion
+
ordered lookup/navigation
```

because the tree maintains ordering dynamically.

Compare that with a sorted ArrayList:

```text
mostly static data
+
many reads
```

where keeping an array/list sorted can be a good alternative.

The correct data structure depends on the workload.

# 13. TreeMap vs LinkedHashMap

This distinction must be clear.

## LinkedHashMap

Preserves encounter/insertion order.

If insertion is:

```text
30
10
20
```

iteration is:

```text
30
10
20
```

## TreeMap

Orders by key.

Iteration is:

```text
10
20
30
```

Mental model:

```text
LinkedHashMap
    → insertion/access encounter order

TreeMap
    → key ordering
```

---

# 14. TreeMap and Comparator Equivalence

Suppose:

```java
TreeMap<Payment, String> map =
    new TreeMap<>(
        Comparator.comparing(Payment::getAmount)
    );
```

If:

```text
P1.amount = 500
P2.amount = 500
```

then:

```text
compare(P1, P2) == 0
```

TreeMap treats them as equivalent keys for the map's ordering.

This is the same important concept we discussed with TreeSet:

> **The comparison used by the TreeMap defines key equivalence for map operations.**

If business identity needs more than amount, use a tie-breaker:

```java
Comparator<Payment> comparator =
    Comparator.comparing(Payment::getAmount)
              .thenComparing(Payment::getPaymentId);
```

We will cover Comparator design properly later.

# 15. Null Keys

With natural ordering, TreeMap should not be treated as supporting a `null` key because it needs to compare keys.

For interview preparation:

> **Do not rely on null keys with natural-order TreeMap.**

Null values are a separate issue.

# 16. Thread Safety

TreeMap is not inherently thread-safe.

```text
TreeMap
   ↓
not designed for unsynchronized concurrent modification
```

If multiple threads share and modify it concurrently, an appropriate concurrency strategy is required.

We will cover concurrent collections later in the Multithreading section.

# 17. Why Red-Black Tree?

A normal Binary Search Tree can become badly unbalanced:

```text
10
  \
   20
     \
      30
        \
         40
```

Then search can degrade toward:

```text
O(n)
```

A Red-Black Tree keeps the tree approximately balanced.

Therefore:

```text
get    → O(log n)
put    → O(log n)
remove → O(log n)
```

This is the same reason TreeSet provides logarithmic operations.

---

# 18. TreeMap vs TreeSet

Both use tree-based ordering.

```text
TreeSet
    ↓
unique sorted elements

TreeMap
    ↓
sorted keys + values
```

Conceptually:

```text
TreeSet:

10
20
30
```

TreeMap:

```text
10 → A
20 → B
30 → C
```

# 19. Final Map Decision Framework

```text
                 MAP
                  │
       ┌──────────┼───────────┐
       ↓          ↓           ↓
   HashMap   LinkedHashMap  TreeMap
       │          │           │
       ↓          ↓           ↓
   Hashing    Hashing       Tree
       │          │           │
       ↓          ↓           ↓
 Expected     Expected       O(log n)
 O(1)         O(1)
              +
           encounter
            order
                              +
                         sorted keys
                              +
                          navigation
```

### Decision rule

```text
Fast key lookup?
    → HashMap

Fast lookup + predictable encounter order?
    → LinkedHashMap

Sorted keys / floor / ceiling / range queries?
    → TreeMap
```

# 20. Interview Answer — "Explain TreeMap"

> "`TreeMap` is a sorted Map implementation backed by a self-balancing Red-Black Tree. Unlike HashMap, it doesn't use hashing; it uses natural ordering or a Comparator to navigate the tree. Its basic operations are O(log n), and its major advantage is ordered navigation through operations such as floorKey, ceilingKey, lowerKey, higherKey, and range views such as subMap. I would choose it when the requirement is dynamic sorted data or ordered/range-based key lookup rather than just exact-key lookup."

---

# 21. Interview Traps

### Trap 1

> TreeMap is a sorted HashMap.

No.

```text
HashMap → hashing
TreeMap → Red-Black Tree
```

### Trap 2

> TreeMap has O(1) lookup.

No.

```text
TreeMap → O(log n)
```

### Trap 3

> LinkedHashMap and TreeMap both maintain order in the same way.

No.

```text
LinkedHashMap → encounter/insertion/access order
TreeMap       → key ordering
```

### Trap 4

> TreeMap uses equals() exactly like HashMap to determine key identity.

Be careful. TreeMap's ordering comparison determines equivalence for tree operations. If comparison returns zero, the keys are treated as equivalent according to the map's ordering.

### Trap 5

> TreeMap is always better when data needs ordering.

Not necessarily.

If the data is mostly static, a sorted array/list with binary search may be more appropriate depending on the workload.

# 24. Final Mental Model

```text
HashMap
    → hash table
    → expected O(1)
    → exact key lookup

LinkedHashMap
    → hash table + linked ordering
    → expected O(1)
    → predictable encounter order

TreeMap
    → Red-Black Tree
    → O(log n)
    → sorted keys
    → floor / ceiling / lower / higher
    → range queries
```

**TreeMap's killer feature is not merely "sorted iteration."**

It is:

> **Maintaining sorted data dynamically while supporting efficient ordered navigation.**
