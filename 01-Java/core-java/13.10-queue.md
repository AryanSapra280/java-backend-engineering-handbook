# 13.10 — Queue

> Interview-focused notes. Core idea: **Queue represents elements waiting to be processed**. For a normal FIFO workload, prefer a suitable Queue implementation rather than using a List as a queue.

---

# 1. Core Idea

A normal Queue follows:

```text
First In → First Out
```

Conceptually:

```text
Producer
   ↓
[A] [B] [C] [D]
 ↑           ↑
head        tail
 ↓           ↓
consume     add
```

If:

```text
A enters
B enters
C enters
```

then:

```text
A leaves first
B leaves second
C leaves third
```

---

# 2. Queue Is an Interface

Common implementations include:

```text
Queue
 ├── LinkedList
 ├── ArrayDeque
 └── PriorityQueue
```

But they have different semantics.

Important:

> Don't choose an implementation just because it implements Queue. Choose based on the workload and required behavior.

---

# 3. Important Queue Methods

Java Queue provides paired methods for insertion, removal, and examination.

## Insert

```java
queue.add(element);
```

vs

```java
queue.offer(element);
```

## Remove

```java
queue.remove();
```

vs

```java
queue.poll();
```

## Examine without removing

```java
queue.element();
```

vs

```java
queue.peek();
```

---

# 4. `add()` vs `offer()`

```java
queue.add(element);
```

Attempts to insert and may throw an exception if the queue cannot accept the element.

```java
queue.offer(element);
```

Attempts to insert and returns:

```text
true  → inserted
false → could not insert
```

For normal queue-processing code, `offer()` is often convenient because failure is represented without an exception.

---

# 5. `remove()` vs `poll()`

```java
queue.remove();
```

Removes and returns the head.

If the queue is empty:

```text
exception
```

Whereas:

```java
queue.poll();
```

removes and returns the head.

If empty:

```text
null
```

Mental model:

```text
remove() → strict
poll()   → safe empty-result handling
```

---

# 6. `element()` vs `peek()`

Both examine the head without removing it.

```java
queue.element();
```

If empty:

```text
exception
```

Whereas:

```java
queue.peek();
```

If empty:

```text
null
```

Mental model:

```text
peek()
    → look at head

poll()
    → take/remove head
```

---

# 7. Method Cheat Sheet

| Purpose | Exception-style | Non-exception-style |
|---|---|---|
| Insert | `add()` | `offer()` |
| Remove head | `remove()` | `poll()` |
| Examine head | `element()` | `peek()` |

For interview/code readability, remember the common trio:

```java
offer()
poll()
peek()
```

---

# 8. Production Scenario — Payment Processing

Suppose payments arrive:

```text
P1
P2
P3
P4
```

Requirement:

> Process payments in the order received.

A FIFO Queue is a natural representation:

```text
P1 → P2 → P3 → P4
```

Consumer:

```java
Payment payment = queue.poll();
```

returns:

```text
P1
```

then:

```text
P2
```

and so on.

---

# 9. Consumption Order vs Completion Order

A Queue can guarantee the order in which elements are removed.

It does **not automatically guarantee processing completion order** when multiple consumers work concurrently.

Example:

```text
Queue:
P1 → P2 → P3
```

Two consumers:

```text
Consumer 1 → P1
Consumer 2 → P2
```

Consumption:

```text
P1 → P2
```

But if Consumer 2 finishes first:

```text
Completion:
P2 → P1
```

This is a concurrency/system-design issue rather than a Queue-interface issue.

Important mental model:

```text
consumption order
      ≠
completion order
```

---

# 10. Queue vs List

If the requirement is:

> Repeatedly process the oldest element.

A Queue communicates that intent directly:

```java
queue.poll();
```

instead of:

```java
list.get(0);
list.remove(0);
```

A Queue is semantically clearer for work waiting to be processed.

---

# 11. Why Not ArrayList as a Queue?

With:

```java
list.remove(0);
```

the remaining elements may need to shift.

Worst case:

```text
O(n)
```

If you repeatedly remove from the front, this can become expensive.

A proper queue implementation can provide efficient head/tail operations.

---

# 12. LinkedList as a Queue

`LinkedList` implements both:

```text
Queue
Deque
```

So:

```java
Queue<Payment> queue = new LinkedList<>();
```

is valid.

Head/tail operations can be efficient:

```text
offer → O(1)
poll  → O(1)
peek  → O(1)
```

But:

> This does not mean LinkedList is automatically the best Queue implementation.

For a normal non-concurrent queue/deque workload, ArrayDeque is generally the better default.

---

# 13. ArrayDeque — Important

For a normal FIFO queue, prefer:

```java
Queue<Payment> queue = new ArrayDeque<>();
```

when you don't need concurrency.

ArrayDeque is array-backed and uses a circular-buffer style structure to efficiently manage both ends.

Conceptually:

```text
          circular array

       [ ] [ ] [ ] [ ]
      ↑             ↑
    head           tail
```

You can:

```text
add at tail
remove from head
```

without shifting the entire array.

Typical queue operations:

```text
offer → O(1) amortized
poll  → O(1)
peek  → O(1)
```

---

# 14. Why ArrayDeque Often Beats LinkedList

LinkedList uses nodes.

Conceptually each node contains:

```text
previous
element
next
```

This creates:

```text
node/object overhead
pointer/reference overhead
less favorable memory locality
```

ArrayDeque is array-backed and avoids per-element linked-node overhead.

Therefore:

```text
LinkedList
    → node-based

ArrayDeque
    → array-backed
```

For a normal non-concurrent FIFO/LIFO workload:

> Prefer ArrayDeque over LinkedList in most cases.

Don't claim:

> ArrayDeque is always faster.

Better interview wording:

> "For a normal non-concurrent FIFO/deque workload, I'd generally prefer ArrayDeque because it is array-backed, has good memory locality, avoids per-node overhead, and provides efficient operations at both ends."

---

# 15. Queue Implementation Decision

```text
Normal single-threaded FIFO?
        ↓
    ArrayDeque
```

If you specifically need a linked-node structure:

```text
LinkedList
```

If you need priority-based processing:

```text
PriorityQueue
```

If you need concurrent producer/consumer behavior with blocking semantics:

```text
BlockingQueue
```

`BlockingQueue` belongs in the Multithreading section.

---

# 16. Queue vs PriorityQueue

This distinction is critical.

Normal Queue:

```text
A → B → C
```

consumes:

```text
A
B
C
```

PriorityQueue:

```text
C (priority 3)
A (priority 1)
B (priority 2)
```

consumes according to priority:

```text
A
B
C
```

Therefore:

```text
Queue
    → FIFO

PriorityQueue
    → priority-based removal
```

PriorityQueue is **not FIFO**.

We will cover PriorityQueue separately.

---

# 17. `peek()` vs `poll()`

Example:

```java
Queue<String> queue = new ArrayDeque<>();

queue.offer("A");
queue.offer("B");
```

Then:

```java
queue.peek();
```

returns:

```text
A
```

but leaves the queue:

```text
A → B
```

Whereas:

```java
queue.poll();
```

returns:

```text
A
```

and leaves:

```text
B
```

Mental model:

```text
peek() → look
poll() → take
```

---

# 18. Empty Queue Behavior

```java
queue.poll();
```

on an empty queue:

```text
null
```

while:

```java
queue.remove();
```

throws an exception.

Likewise:

```java
queue.peek();
```

returns:

```text
null
```

while:

```java
queue.element();
```

throws an exception.

This is why `poll()` and `peek()` are convenient when an empty queue is a normal possibility.

---

# 19. Production Scenario — Job Processing

Suppose a service receives jobs:

```text
Job1
Job2
Job3
Job4
```

and they need FIFO processing.

```java
Queue<Job> jobs = new ArrayDeque<>();

jobs.offer(job);
```

Worker:

```java
Job job = jobs.poll();

if (job != null) {
    process(job);
}
```

This clearly represents:

> Jobs waiting to be processed.

However, if multiple threads need to safely share the queue and wait for work, ArrayDeque alone is not enough.

Use an appropriate `BlockingQueue` implementation in that situation.

# 21. Queue vs ArrayList — Interview Scenario

Interviewer:

> "You need to process incoming requests in FIFO order. Would you use ArrayList?"

Strong answer:

> "I'd use a Queue rather than ArrayList because FIFO processing is the semantic requirement. With ArrayList, removing from the front can require shifting elements and is O(n). For a normal non-concurrent FIFO queue, I'd typically use ArrayDeque."

---

# 22. Queue vs LinkedList — Interview Scenario

Interviewer:

> "LinkedList supports O(1) insertion/removal at the ends. Why not always use it as a Queue?"

Strong answer:

> "Although LinkedList can provide efficient end operations, it has per-node memory overhead and poorer memory locality. For a normal non-concurrent Queue/Deque workload, I'd generally prefer ArrayDeque because it is array-backed and designed for efficient operations at both ends."
