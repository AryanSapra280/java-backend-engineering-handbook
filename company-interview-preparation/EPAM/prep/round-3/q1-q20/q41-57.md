# Q42. What are Checked and Unchecked Exceptions?

This is **very important**.

### Checked exceptions

Checked exceptions are exceptions that the compiler **forces you to handle or declare**.

They generally extend `Exception` but **not** `RuntimeException`.

Example:

```java
public void readFile() throws IOException {
    // ...
}
```

You must either:

```java
try {
    readFile();
} catch (IOException e) {
    // handle
}
```

or:

```java
public void process() throws IOException {
    readFile();
}
```

Common examples:

```text
IOException
SQLException
ClassNotFoundException
```

---

### Unchecked exceptions

Unchecked exceptions extend `RuntimeException`.

The compiler **doesn't force you to catch or declare them**.

Examples:

```text
NullPointerException
IllegalArgumentException
IndexOutOfBoundsException
ArithmeticException
```

For example:

```java
public void process(String name) {
    System.out.println(name.length());
}
```

If `name == null`, you can get:

```text
NullPointerException
```

You aren't required to write:

```java
throws NullPointerException
```

---

### The hierarchy

Remember this:

```text
Throwable
 ├── Error
 │
 └── Exception
      ├── RuntimeException
      │     ├── NullPointerException
      │     ├── IllegalArgumentException
      │     └── ...
      │
      └── Other checked exceptions
            ├── IOException
            ├── SQLException
            └── ...
```

### Interview answer

> **"Checked exceptions are exceptions that the compiler requires us to either handle with catch or declare using throws. Examples include IOException and SQLException. Unchecked exceptions extend RuntimeException and aren't enforced by the compiler; examples include NullPointerException and IllegalArgumentException. Checked exceptions are generally used for conditions that the application may reasonably recover from, while unchecked exceptions commonly represent programming errors or invalid state."**

### One common trap

Don't say:

> "`Exception` means checked exception."

Because:

```text
RuntimeException extends Exception
```

and RuntimeException is **unchecked**.

## Q43. What are custom checked and unchecked exceptions?

You can create your own exceptions by extending the appropriate base class.

### Custom checked exception

Extend `Exception`:

```java
class PaymentException extends Exception {

    public PaymentException(String message) {
        super(message);
    }
}
```

Then Java requires handling/declaring it:

```java
void process() throws PaymentException {
    throw new PaymentException("Payment failed");
}
```

### Custom unchecked exception

Extend `RuntimeException`:

```java
class PaymentProcessingException
        extends RuntimeException {

    public PaymentProcessingException(String message) {
        super(message);
    }
}
```

No compiler requirement to catch or declare it.

### Interview answer

> **"For a custom checked exception, I extend `Exception`, so callers must either handle it or declare it. For a custom unchecked exception, I extend `RuntimeException`, so handling it isn't enforced by the compiler. I would choose between them based on whether the caller is expected to explicitly recover from the condition or whether it's better treated as an unchecked application or programming error."**

For Spring Boot REST APIs, you'll commonly see custom exceptions extending `RuntimeException`, followed by centralized handling with `@RestControllerAdvice`.

## Q44. How do `try`, `catch`, and `finally` work?

These three blocks work together for **handling exceptions and cleanup**.

### 1. `try`

Contains code that might throw an exception:

```java
try {
    int result = 10 / 0;
}
```

### 2. `catch`

Handles an exception thrown from the `try` block:

```java
try {
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
}
```

Flow:

```text
try
 ↓
exception occurs
 ↓
matching catch
 ↓
handle exception
```

If no exception occurs:

```text
try
 ↓
successful
 ↓
skip catch
```

### 3. `finally`

`finally` is used for **cleanup code that should normally execute regardless of whether an exception occurred**.

```java
try {
    // operation
} catch (Exception e) {
    // handle exception
} finally {
    // cleanup
}
```

For example:

```java
try {
    connection = getConnection();
    // use connection
} catch (SQLException e) {
    // handle
} finally {
    connection.close();
}
```

Although in modern Java, for resources like database connections/files, **try-with-resources** is generally preferred.

---

### Interview answer

> **"`try` contains code that may throw an exception. If an exception occurs, Java looks for a matching `catch` block to handle it. The `finally` block is used for cleanup and normally executes whether an exception occurs or not. It is commonly used for releasing resources, although try-with-resources is preferred for AutoCloseable resources."**

### Important follow-up

The interviewer may now ask:

**"Is `finally` guaranteed to execute?"**

Don't answer simply **"always."**

There are exceptional cases, such as:

```java
System.exit(0);
```

or the JVM terminating abruptly.

So the safer statement is:

> **"`finally` normally executes whether an exception occurs or not, unless the JVM terminates before it can execute."**

### Q50 next: **How can runtime issues occur even when using Generics?**

This one connects **Generics + type erasure + runtime type safety**, so it's a little more interesting.

## Q50. How can runtime issues occur even when using Generics?

The key idea is:

> **Generics provide compile-time type safety, but Java's type erasure and some legacy/raw-type operations can still allow type-related problems to surface at runtime.**

### Normal Generics

```java
List<String> names = new ArrayList<>();

names.add("Aryan");
names.add("Rahul");

String name = names.get(0);
```

The compiler knows this is a `List<String>`, so:

```java
names.add(123);   // ❌ compile-time error
```

So normally Generics protect us.

---

### But consider a raw type

```java
List<String> names = new ArrayList<>();

List rawList = names;       // raw type
rawList.add(100);           // allowed, compiler warning
```

Now:

```java
String name = names.get(0);
```

At runtime, Java may attempt to treat the `Integer` as a `String`, resulting in:

```text
ClassCastException
```

Conceptually:

```text
Generic List<String>
       ↓
Raw List
       ↓
Integer inserted
       ↓
String expected
       ↓
ClassCastException at runtime
```

### Why can this happen?

Because Java Generics use **type erasure**. Generic type information isn't retained in the same way at runtime as it is during compilation.

That's why mixing:

- Raw types
- Legacy APIs
- Unchecked casts
- Unsafe operations

can bypass some of the compile-time protection.

### Another example: unchecked cast

```java
Object obj = 123;

String value = (String) obj;
```

This isn't really a Generics example, but it demonstrates the broader point: **compile-time guarantees don't eliminate every possible runtime type problem.**

### Interview answer

> **"Generics provide type safety primarily at compile time. However, runtime issues can still occur if we bypass those guarantees, for example by using raw types, unchecked casts, or legacy APIs. Due to type erasure, generic type information isn't fully available at runtime, and an invalid value can eventually result in a `ClassCastException`."**

### Important distinction

Don't say:

> ❌ "Generics are not type-safe."

Say:

> ✅ **"Generics provide compile-time type safety, but that safety can be bypassed through raw types, unchecked operations, or casts, which can lead to runtime exceptions."**

Without it:

With `@ControllerAdvice`:

Controller B ─┼──> Global Exception Handler
Controller C ─┘
```

So you centralize common controller concerns.

### Interview answer

                        "PAYMENT_NOT_FOUND",
                        ex.getMessage());

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGeneric(
            Exception ex) {

        ErrorResponse response =
                new ErrorResponse(
                        "INTERNAL_ERROR",
                        "Unexpected error");

        return ResponseEntity
                .status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(response);
    }
}
```

Then anywhere in your service:

```java
if (payment == null) {
    throw new PaymentNotFoundException(
            "Payment not found");
}
```

Spring handles the exception centrally.

### Interview answer

> **"I would create a `@RestControllerAdvice` class and define `@ExceptionHandler` methods for the application's custom exceptions and relevant framework exceptions. Each handler would map the exception to the appropriate HTTP status and a consistent error-response structure. Controllers and services can then throw meaningful exceptions without duplicating try-catch logic. I would also have a generic fallback handler for unexpected exceptions, while avoiding exposing internal implementation details in the response."**

### ⭐ Senior-level follow-up

If they ask:

I'd use local try-catch when I can actually recover from the exception or when I need to add specific contextual handling."**
