## Q7. What are Virtual Threads?

This is a **Java 21** feature and is important for a Senior Engineer interview.

### 1. The basic idea

Traditionally, when you create a Java thread:

```java
Thread thread = new Thread(() -> {
    // task
});
thread.start();
```

that Java thread is closely associated with an **OS/platform thread**.

Platform threads are relatively expensive resources. If your application creates thousands of them, you can run into memory and scheduling limitations.

**Virtual threads** are lightweight threads managed by the JVM rather than being permanently tied one-to-one to OS threads.

Think of it like:

```text
Traditional:

Java Thread 1 ─── OS Thread 1
Java Thread 2 ─── OS Thread 2
Java Thread 3 ─── OS Thread 3
...

Virtual Threads:

Virtual Thread 1 ─┐
Virtual Thread 2 ─┤
Virtual Thread 3 ─┤──> small number of OS/platform threads
Virtual Thread 4 ─┤
Virtual Thread 5 ─┘
```

So you can have **very large numbers of virtual threads** without requiring an equivalent number of OS threads. The uploaded material specifically emphasizes this as the key benefit of Java 21 virtual threads. Pasted markdown (2)

### 2. Why are they useful?

They're particularly useful for **I/O-bound workloads**.

For example, suppose your service receives 10,000 requests:

```text
Request
   ↓
Call PostgreSQL
   ↓
Wait...
   ↓
Call another service
   ↓
Wait...
   ↓
Return response
```

A platform thread may spend a significant amount of its lifetime **waiting for I/O**.

Virtual threads make it practical to have many concurrent tasks waiting on I/O while the underlying platform threads can execute other work.

Typical examples:

- REST API calls
- Database calls
- HTTP calls to downstream services
- File/network I/O
- Microservices handling many concurrent requests

The source material also specifically warns that virtual threads **do not make CPU-bound work faster**; they mainly improve scalability for workloads involving lots of waiting/I/O. Pasted markdown (2)

### 3. How do you create one?

Java 21 provides:

```java
Thread.startVirtualThread(() -> {
    System.out.println("Running in virtual thread");
});
```

or:

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {

    executor.submit(() -> {
        // task
    });
}
```

The second approach is especially interesting in backend applications because you can create a virtual thread **per task** rather than maintaining a traditional fixed-size thread pool.

### 4. Important interview distinction

Don't say:

> "Virtual threads make Java applications faster."

Better:

> **"Virtual threads primarily improve scalability for highly concurrent, I/O-bound workloads. They allow a large number of lightweight concurrent tasks without requiring one platform thread per task. They don't provide a fundamental performance advantage for CPU-bound computation."**

That's a much stronger Senior-level answer.

### One important trap

If the interviewer asks:

**"Should we replace every ExecutorService with virtual threads?"**

Answer:

> "Not necessarily. Virtual threads are particularly useful for high-concurrency I/O-bound workloads. For CPU-bound work, the number of concurrent tasks should still generally be controlled according to the available CPU resources. We also need to consider external resource limits such as database connection pools."

The source material explicitly discusses resource limits such as DB connections as an important consideration. Pasted markdown (2)

## Q9. What are sealed classes?

This one is much easier.

A **sealed class/interface restricts which classes are allowed to extend or implement it.**

Example:

```java
public sealed interface Payment
        permits CardPayment, UpiPayment {
}
```

Now only:

```java
final class CardPayment implements Payment {
}

final class UpiPayment implements Payment {
}
```

can implement `Payment`.

So conceptually:

```text
Payment
  ├── CardPayment
  └── UpiPayment

No other class can implement Payment
```

Sealed classes became a **final feature in Java 17**.

### Why use them?

Main reason:

> **Controlled inheritance.**

It is useful when you know the complete set of permitted implementations and want the compiler to enforce that restriction.

For example:

```java
sealed interface Result
    permits Success, Failure
```

You explicitly define the allowed hierarchy.

### Interview answer

> **"Sealed classes were finalized in Java 17. They allow us to restrict which classes or interfaces can extend or implement a particular type. We specify the permitted subclasses using the `permits` clause. This is useful when we want a controlled and well-defined inheritance hierarchy."**

You **haven't told me you've used sealed classes**, so we won't claim hands-on experience.
