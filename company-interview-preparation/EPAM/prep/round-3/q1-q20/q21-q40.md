# Q21. What is Lazy Evaluation?

### Simple definition

**Lazy evaluation means an operation is not executed immediately when it is defined. It is executed only when its result is actually needed.**

For Java Streams, this is particularly important.

Consider:

```java
List<String> names = List.of("Aryan", "Rahul", "Amit");

Stream<String> stream = names.stream()
        .filter(name -> {
            System.out.println("Checking " + name);
            return name.startsWith("A");
        });
```

At this point, you created the stream pipeline, but **nothing has actually been processed yet**.

The `filter()` is an **intermediate operation**, so it is lazy.

Now:

```java
stream.findFirst();
```

This is a **terminal operation**, so execution begins.

Conceptually:

```text
Create pipeline
      ↓
filter()       ← nothing executed yet
      ↓
findFirst()    ← triggers execution
      ↓
elements start flowing through pipeline
```

### Why is this useful?

Because Java doesn't necessarily process the entire collection unnecessarily.

For example:

```java
List<Integer> numbers = List.of(1, 2, 3, 4, 5);

Optional<Integer> result =
        numbers.stream()
               .filter(n -> n > 2)
               .findFirst();
```

Once `3` satisfies the filter and `findFirst()` has its answer, the stream can **stop processing further elements**.

It doesn't need to check `4` and `5`.

That's one of the important benefits of lazy stream processing.

### Very important distinction

Don't say:

> "Streams are lazy."

That's incomplete.

Better:

> **"Stream intermediate operations are lazy. The pipeline is evaluated when a terminal operation is invoked."**

### Interview answer

> **"Lazy evaluation means that an operation is not executed immediately when it is defined, but only when its result is required. In Java Streams, intermediate operations such as `filter`, `map`, and `sorted` are lazy. They build a pipeline, and execution starts when a terminal operation such as `collect`, `forEach`, `findFirst`, or `findAny` is invoked. This allows Streams to avoid unnecessary processing and can enable short-circuiting."**

### One small trap

If interviewer asks:

**"Is `filter()` executed when you call it?"**

Answer:

> **"No. `filter()` is an intermediate operation, so it only builds the stream pipeline. It is executed when a terminal operation triggers the pipeline."**

# Q22. How does Lazy Evaluation work?

The important thing is to understand **how the Stream pipeline actually executes**.

Consider:

```java
List<Integer> numbers = List.of(1, 2, 3, 4, 5);

Optional<Integer> result =
    numbers.stream()
           .filter(n -> n > 2)
           .map(n -> n * 10)
           .findFirst();
```

At first, Java doesn't process `1, 2, 3, 4, 5`.

It first builds a pipeline:

```text
Source
  ↓
filter(n > 2)
  ↓
map(n * 10)
  ↓
findFirst()
```

`filter()` and `map()` are **intermediate operations**, so they're lazy.

`findFirst()` is a **terminal operation**, which triggers the pipeline.

---

### What actually happens?

The processing is effectively **element by element through the pipeline**:

```text
1
 ↓
filter → false
 ↓
discard

2
 ↓
filter → false
 ↓
discard

3
 ↓
filter → true
 ↓
map → 30
 ↓
findFirst → 30
 ↓
STOP
```

It doesn't necessarily do:

```text
filter ALL elements
      ↓
map ALL filtered elements
      ↓
findFirst
```

Instead, the pipeline can process an element through multiple stages and stop once the terminal operation has enough information.

That's where lazy evaluation + **short-circuiting** becomes powerful.

### Another example

```java
numbers.stream()
       .filter(n -> n > 2)
       .map(n -> n * 10)
       .findFirst();
```

For:

```text
1, 2, 3, 4, 5
```

you don't need to process `4` and `5` once `3 → 30` satisfies `findFirst()`.

---

## The mental model

Think:

> **Intermediate operations build the recipe. The terminal operation starts cooking the recipe.**

```text
stream()
   ↓
filter()       → recipe
   ↓
map()          → recipe
   ↓
findFirst()    → START EXECUTION
   ↓
elements flow through pipeline
   ↓
result
```

### Interview answer

> **"Lazy evaluation in Streams works by building a pipeline of intermediate operations without immediately processing the data. When a terminal operation is invoked, the pipeline starts executing. Elements can flow through the different stages of the pipeline, and if the terminal operation is short-circuiting, processing can stop as soon as the required result is found."**

### One important distinction

**Lazy evaluation ≠ short-circuiting.**

They are related but different:

- **Lazy evaluation** → intermediate operations don't execute until a terminal operation triggers them.
- **Short-circuiting** → processing can stop before consuming the entire source when the terminal/intermediate operation allows it.

For example, `findFirst()` can short-circuit.

### Q24. What are intermediate and terminal operations in Streams?

This one is very important because **Q25 depends directly on it**.

**Intermediate operations** return another Stream:

```java
filter()
map()
sorted()
distinct()
limit()
skip()
```

They are generally **lazy**.

**Terminal operations** produce a final result or side effect:

```java
collect()

reduce()
count()
findFirst()
findAny()
```

They **trigger execution** of the stream pipeline.

Think:

```text
Intermediate → Intermediate → Intermediate → Terminal
    ↓               ↓              ↓             ↓
  filter           map          distinct       collect
                                                  ↓
                                             execution
```

### Interview answer

> **"Intermediate operations such as filter, map, and sorted return another Stream and are lazy. Terminal operations such as collect, reduce, findFirst, findAny, and forEach produce the final result or side effect and trigger execution of the pipeline."**

## Q25. When is a Stream operation actually executed?

The answer depends on **whether the operation is intermediate or terminal**.

### Intermediate operation

```java
stream
    .filter(...)
    .map(...);
```

These are **not executed immediately**.

They only build the pipeline.

```text
filter() → lazy
map()    → lazy
```

### Terminal operation

Execution begins when you invoke a terminal operation:

```java
stream
    .filter(...)
    .map(...)
    .collect(Collectors.toList());
```

Here:

```text
filter → build pipeline
map    → build pipeline
collect → triggers execution
```

So the clean interview statement is:

> **"Intermediate Stream operations are evaluated lazily. They are actually executed when a terminal operation is invoked, such as collect, forEach, reduce, findFirst, or findAny."**

### Important nuance

The **whole pipeline doesn't necessarily process every element**.

For example:

```java
numbers.stream()
       .filter(n -> n > 10)
       .findFirst();
```

`findFirst()` can stop processing once it finds the first matching element.

That's **short-circuiting**, which is separate from lazy evaluation.

# Q26. What does `findAny()` do?

`findAny()` is a **terminal operation** that returns an `Optional` containing **some element** from the Stream, if one exists.

Example:

```java
Optional<Integer> result =
        numbers.stream().findAny();
```

Possible result:

```text
Optional[1]
```

For a **sequential stream**, you'll commonly see the first element returned, but the API does **not guarantee** that `findAny()` must return the first element.

The important reason `findAny()` exists becomes clearer with **parallel streams**: it allows the implementation to return an available element without having to preserve encounter order.

### Interview answer

> **"`findAny()` is a terminal operation that returns an Optional containing any element from the Stream, if one exists. It doesn't guarantee which element will be returned, which makes it suitable when we don't care about encounter order, particularly with parallel streams."**

---

# Q27. What does `findFirst()` do?

`findFirst()` is also a **terminal operation**, but it respects the Stream's **encounter order**.

Example:

```java
List<Integer> numbers =
        List.of(10, 20, 30, 40);

Optional<Integer> result =
        numbers.stream().findFirst();
```

Result:

```text
Optional[10]
```

If the stream has a defined encounter order, `findFirst()` returns the **first element according to that order**.

### Interview answer

> **"`findFirst()` is a terminal operation that returns an Optional containing the first element according to the Stream's encounter order. Unlike `findAny()`, it guarantees the first element when an encounter order exists."**

### Interview answer

> **"`findFirst()` guarantees the first element according to encounter order, whereas `findAny()` can return any element. If I care about order, I would use `findFirst()`. If I don't care which matching element I get, `findAny()` can provide more flexibility, especially for parallel streams."**

## Q29. If Streams are lazily evaluated, why do we have both `findAny()` and `findFirst()`?

This is **not related to lazy evaluation**. That's the key point.

Lazy evaluation tells us **when the pipeline executes**.

`findFirst()` vs `findAny()` tells us **what result the terminal operation is allowed to return**.

### Example

```java
List<Integer> numbers = List.of(10, 20, 30, 40);
```

With:

```java
numbers.stream().findFirst();
```

The requirement is:

> Give me the **first element according to encounter order**.

So:

```text
10 → 20 → 30 → 40
↑
must return this
```

With:

```java
numbers.stream().findAny();
```

The requirement is:

> Give me **any available element**. I don't care about the order.

That distinction becomes particularly important with **parallel streams**.

```text
Parallel Stream

Partition 1 → 10 20
Partition 2 → 30 40

findAny()
    ↓
If partition 2 finds a valid element first,
it may be able to return 30
```

It doesn't have to coordinate everything just to determine which element was first in the original encounter order.

### So why both?

Because they express **different requirements**:

```text
findFirst()
→ "Order matters."

findAny()
→ "I only need one; order doesn't matter."
```

### Interview answer

> **"Lazy evaluation and findFirst/findAny solve different problems. Lazy evaluation determines when the Stream pipeline is executed, while findFirst and findAny define what result the terminal operation should return. findFirst preserves encounter order, whereas findAny allows any element to be returned. The distinction is particularly useful with parallel streams, where findAny can provide more flexibility because it doesn't need to preserve encounter order."**

# Q30. In a sequential Stream, will `findAny()` and `findFirst()` always return the same element?

For example:

List<Integer> numbers = List.of(10, 20, 30);

numbers.stream().findFirst(); // 10

For an **ordered sequential stream**, the current implementation commonly returns the first element for `findAny()`.

But the API contract for `findAny()` deliberately **doesn't guarantee that it must be the first element**.

That's why the correct interview answer is:

> **"For a sequential ordered stream, `findAny()` will commonly return the same element as `findFirst()`, but the API does not guarantee that `findAny()` returns the first element. `findFirst()` provides the ordering guarantee; `findAny()` does not."**

### Very important interview trap

Don't say:

> ❌ "`findAny()` always returns the first element in sequential streams."

Say:

> ✅ "`findAny()` often returns the first element in sequential streams, but that is not its contract."**

## Q31. Why is `findAny()` not guaranteed to return the first element?

Because **`findAny()` intentionally does not promise encounter-order semantics**.

This gives the Stream implementation more freedom, especially for **parallel processing**.

Imagine:

```text
Parallel Stream

             Source
          /          \
      Part A          Part B
     1  2  3          4  5  6
       ↓                ↓
   processing        processing
       ↓                ↓
    finds 2          finds 4
```

If the requirement is simply:

> "Give me any element."

there is no reason to wait and determine whether `2` is before `4` according to encounter order.

The implementation can return an available result.

### Interview answer

> **"`findAny()` doesn't guarantee the first element because it is designed to allow the Stream implementation to return any available element without preserving encounter order. This is especially useful with parallel streams, where enforcing order can require additional coordination."**

---

### Q32. How does `findFirst()` guarantee encounter order?

This is the next important piece.

**Encounter order** is the order in which elements are encountered by the Stream.

For example:

```java
List<Integer> list = List.of(10, 20, 30, 40);
```

The encounter order is:

```text
10 → 20 → 30 → 40
```

`findFirst()` must respect that order and return:

```text
10
```

Even when the Stream is parallel, `findFirst()` has to coordinate the processing so that an element that appears earlier in the encounter order is preferred over a later element.

That's why `findFirst()` can have more ordering overhead than `findAny()` in parallel processing.

### Interview answer

> **"`findFirst()` guarantees encounter order by requiring the Stream implementation to return the earliest element according to the stream's defined encounter order. With parallel streams, this may require coordination between partitions to ensure that a later element isn't returned when an earlier element exists."**

## Q33. How do parallel Streams work?

This is an important one for your EPAM interview because it connects **Streams + concurrency + ForkJoinPool**.

A parallel Stream divides the stream's data into **multiple portions**, processes those portions concurrently, and then combines the results when necessary.

For example:

```java
List<Integer> numbers =
        List.of(1, 2, 3, 4, 5, 6, 7, 8);

numbers.parallelStream()
       .map(n -> n * 2)
       .collect(Collectors.toList());
```

Conceptually:

```text
                Source
                  │
             split data
          ┌───────┴───────┐
          ↓               ↓
      Partition 1      Partition 2
      1  2  3  4       5  6  7  8
          ↓               ↓
      Worker thread     Worker thread
          ↓               ↓
          └───────┬───────┘
                  ↓
              combine
                  ↓
               result
```

### How does the splitting happen?

Parallel Streams use the **Spliterator** abstraction to split the source into smaller pieces.

Conceptually:

```text
Original data
     ↓
 Spliterator
     ↓
trySplit()
   /    \
  /      \
Part A   Part B
          ↓
       trySplit()
       /       \
    Part C     Part D
```

These partitions can then be processed concurrently.

### Important point

A parallel Stream **does NOT create one thread per element**.

If you have:

```text
1,000,000 elements
```

you don't get:

```text
1,000,000 threads ❌
```

Instead, a limited number of worker threads process different portions of the data.

We'll cover exactly which thread pool is used in **Q37**.

---

### Sequential vs Parallel

Sequential:

```java
numbers.stream()
```

Conceptually:

```text
one processing flow
      ↓
1 → 2 → 3 → 4 → 5
```

Parallel:

```java
numbers.parallelStream()
```

Conceptually:

```text
        split
       /     \
      ↓       ↓
   1 2 3     4 5 6
      ↓       ↓
   worker   worker
       \     /
        combine
```

### Interview answer

> **"A parallel Stream divides the source data into multiple partitions using the Stream's Spliterator mechanism. These partitions are processed concurrently by worker threads, and the results are combined when required. It doesn't create one thread per element; instead, a limited number of worker threads process the partitions concurrently."**

That's the core answer.

## Q36. Does a parallel Stream create one thread per element?

**No. Absolutely not.** This is a common interview trap.

If you have:

```java
List<Integer> numbers = ...; // 1 million elements

numbers.parallelStream()
       .map(...)
       .collect(...);
```

Java does **not** create:

```text
1,000,000 elements
        ↓
1,000,000 threads ❌
```

Instead, the Stream framework divides the data into **partitions**, and a limited number of worker threads process those partitions concurrently.

```text
1,000,000 elements
        ↓
   split into chunks
        ↓
 ┌──────┼──────┐
 ↓      ↓      ↓
Chunk  Chunk  Chunk
  ↓      ↓      ↓
Worker Worker Worker
 Thread  Thread  Thread
```

The number of worker threads is limited by the underlying execution mechanism rather than the number of elements.

### Interview answer

> **"No. A parallel Stream does not create one thread per element. The source is divided into partitions, and a limited number of worker threads process those partitions concurrently. The Stream framework manages the splitting and scheduling."**

## Q37. What thread pool/mechanism is used by parallel Streams?

By default, **parallel Streams use the common `ForkJoinPool`**.

Conceptually:

```java
list.parallelStream()
    .map(...)
    .collect(...);
```

uses:

```text
Parallel Stream
      ↓
ForkJoinPool.commonPool()
      ↓
Worker threads
      ↓
Process partitions
```

### What is ForkJoinPool?

`ForkJoinPool` is designed for tasks that can be **split into smaller tasks** and processed concurrently.

Parallel Streams fit this model very well:

```text
Large dataset
     ↓
   split
  /     \
Part A  Part B
 ↓        ↓
split    split
 ↓        ↓
tasks    tasks
   \      /
    combine
```

It uses a **work-stealing** mechanism, where idle worker threads can take tasks from other workers.

### Important interview point

By default:

```java
ForkJoinPool.commonPool()
```

is used.

So if an interviewer asks:

> **"Can I use my own ThreadPoolExecutor with `parallelStream()`?"**

Don't simply say yes. `parallelStream()` doesn't provide a normal API for directly supplying an arbitrary `ExecutorService`/`ThreadPoolExecutor`. There are ways to execute the stream within a custom `ForkJoinPool`, but that's a more advanced topic and usually not necessary unless they specifically ask.

### Interview answer

> **"By default, parallel Streams use the common ForkJoinPool. The Stream framework splits the source into tasks, and the ForkJoinPool executes those tasks using its worker threads. ForkJoinPool also uses work stealing to efficiently distribute tasks among workers."**

# Q38. Is a parallel Stream always faster?

**No. This is a very important interview question.**

Parallelism introduces overhead:

```text
Split data
   ↓
Create/manage tasks
   ↓
Schedule tasks
   ↓
Execute concurrently
   ↓
Combine results
```

For a small collection:

```java
list.stream()
```

may actually be faster than:

```java
list.parallelStream()
```

because the work isn't large enough to justify the parallelization overhead.

### Example

If you have:

```java
List<Integer> numbers = List.of(1, 2, 3, 4);
```

using a parallel Stream is usually unnecessary.

But if you have a **large dataset** and each operation is sufficiently expensive and independent, parallel processing may provide a benefit.

### Interview answer

> **"No. A parallel Stream is not always faster. Parallel processing introduces overhead for splitting, scheduling, synchronization and combining results. It tends to be beneficial when the dataset is sufficiently large, the operations are computationally significant and independent, and the workload can be effectively divided among available processors."**

And there's another major consideration:

> **I/O-bound work isn't automatically a good reason to use parallel Streams.**

For example, doing thousands of blocking database calls through a parallel Stream can simply overwhelm your database connection pool. For I/O-heavy concurrency, other approaches such as appropriately configured executors or virtual threads may be more suitable.

## Q39. What factors determine whether a parallel Stream performs better?

Think about **five things**:

### 1. Dataset size

Small:

```text
100 elements → parallel overhead may dominate
```

Large:

```text
1,000,000 elements → parallelism may help
```

### 2. Cost of each operation

Cheap operation:

```java
.map(x -> x + 1)
```

may not benefit much.

Expensive computation:

```java
.map(x -> expensiveCalculation(x))
```

has more potential for parallelism.

### 3. Whether operations are independent

Good:

```text
element A → independent
element B → independent
element C → independent
```

Bad:

```text
element A → must wait for B
element B → must wait for C
```

Parallelism becomes much harder to benefit from.

### 4. Splitting cost

Some data structures can be split efficiently; others aren't as efficient.

The Stream's `Spliterator` plays an important role here.

### 5. Combining/ordering overhead

Operations requiring significant coordination can reduce the benefit.

For example, preserving encounter order can introduce additional overhead compared with an operation where ordering doesn't matter.

### Interview answer

> **"The benefit of a parallel Stream depends on factors such as dataset size, the computational cost of each operation, whether operations are independent, how efficiently the source can be split, and the overhead of combining or maintaining ordering. If the work is small or heavily synchronized, sequential processing may be faster."**
