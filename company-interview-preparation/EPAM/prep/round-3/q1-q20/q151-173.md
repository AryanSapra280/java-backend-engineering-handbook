```text
       DB            DB            DB

Transactions:
Local transaction
       ↓

```

### Interview answer

> **"In a typical microservice architecture, clients communicate through an API Gateway, which routes requests to individual services. Service discovery helps locate service instances. Each service generally owns its data, and for business transactions spanning multiple services, patterns such as Saga or Outbox can be considered."**

# Q153. What is an API Gateway?

An **API Gateway** is an entry point between clients and backend microservices.

Instead of:

```text
Client → Service A
Client → Service B
Client → Service C
```

we have:

```text
Client
   ↓
API Gateway
   ↓
Service A / B / C
```

The gateway can handle things such as:

- Routing
- Authentication/authorization
- Rate limiting
- Request filtering
- TLS termination
- Sometimes aggregation
- Observability/correlation

### Interview answer

> **"An API Gateway provides a single entry point for clients into a microservice system. It handles concerns such as routing, authentication, rate limiting and request filtering, and forwards requests to the appropriate backend service."**

---

# Q154. Why do you need an API Gateway?

Without a gateway, clients may need to know about every backend service.

```text
Client
 ├── Service A
 ├── Service B
 ├── Service C
 └── Service D
```

That creates tight coupling.

With a gateway:

```text
Client
   ↓
Gateway
   ↓
Backend services
```

The client doesn't need to know the internal topology.

### Main benefits

- Single entry point
- Centralized cross-cutting concerns
- Hides internal service topology
- Routing
- Authentication
- Rate limiting
- API versioning/policies

### Important drawback

The gateway can become a **bottleneck or single point of failure** if poorly designed, so it should itself be highly available and scalable.

# Q155. What is Service Discovery?

In microservices, service instances can dynamically change.

For example:

```text
Payment Service

10.0.1.10
10.0.1.11
10.0.1.12
```

Instead of hardcoding an IP address, another service can discover:

```text
payment-service
```

and obtain an available instance.

### Interview answer

> **"Service discovery allows microservices to dynamically locate instances of another service instead of relying on hardcoded hostnames or IP addresses. A service registers itself and consumers can discover available instances through a service registry or platform-native discovery mechanism."**

---

# Q156. Why is Service Discovery needed?

Because in a distributed environment:

- Instances scale up/down.
- IP addresses can change.
- Pods can be recreated.
- Services may have multiple instances.

For example, Kubernetes already provides a service abstraction and DNS-based service discovery.

```text
payment-service
       ↓
Kubernetes Service
       ↓
Pod 1 / Pod 2 / Pod 3
```

So don't automatically assume you need Eureka.

### Interview answer

> **"Service discovery is needed because microservice instances are dynamic. Instances can be created, removed or rescheduled, so their network locations aren't necessarily stable. Service discovery allows consumers to find available instances without hardcoding individual instance addresses."**

# Q157. What is a Circuit Breaker?

Circuit Breaker prevents repeated calls to an unhealthy downstream service.

Think of an electrical circuit breaker.

Normally:

```text
Client → Service B
```

If Service B repeatedly fails:

```text
        failures
           ↓
Client → Circuit Breaker → Service B
                          ❌
```

The circuit opens:

```text
Client → Circuit Breaker
              ↓
          FAIL FAST
```

Instead of continuously calling the failing service.

### States

```text
CLOSED
  ↓ failures
OPEN
  ↓ after recovery timeout
HALF-OPEN
  ↓ successful test
CLOSED
```

### Interview answer

> **"A circuit breaker prevents an application from repeatedly calling an unhealthy downstream service. After failures exceed a configured threshold, the circuit opens and calls fail fast. After a recovery period it moves to half-open, allows limited test requests, and closes again if the downstream service recovers."**

# Q158. What is the Retry pattern?

Retry means:

> **Try the operation again when a failure may be temporary.**

Example:

```text
Request
   ↓
Service B
   ↓
Temporary failure
   ↓
Retry
   ↓
Service B
   ↓
Success
```

Typical transient failures:

- Temporary network failure
- Connection reset
- Temporary downstream unavailability

### Important trap ⚠️

**Don't retry everything.**

If the request is non-idempotent:

```text
POST /payment
```

blindly retrying could potentially create duplicate operations.

That's why retries often need:

- Idempotency
- Backoff
- Maximum retry count
- Sometimes jitter

### Interview answer

> **"Retry is used when a failure is likely to be transient. We retry a failed operation a limited number of times, usually with backoff. We need to be careful with non-idempotent operations because blindly retrying them can create duplicate side effects."**

# Q159. What is the Timeout pattern?

A timeout puts an upper limit on how long we wait for a downstream operation.

Without timeout:

```text
Service A
   ↓
Service B
   ↓
hangs...
   ↓
A keeps waiting
```

Enough of these requests can exhaust:

- Threads
- Connection pools
- Memory
- Request capacity

With timeout:

```text
Service A
   ↓
Service B
   ↓
timeout after 2 seconds
   ↓
fail / fallback
```

### Interview answer

> **"A timeout prevents a service from waiting indefinitely for a downstream operation. If the downstream call doesn't complete within a configured time, the caller stops waiting and handles the failure. Timeouts are important because otherwise slow downstream services can consume threads and connection-pool resources and cause cascading failures."**

# Q160. What is the Saga pattern?

Saga addresses **distributed business transactions**.

Suppose:

```text
Order Service
     ↓
Payment Service
     ↓
Inventory Service
```

We can't simply use one normal database transaction across all three independent databases.

Saga breaks the overall transaction into **local transactions**.

Example:

```text
Create Order
    ↓
Payment succeeds
    ↓
Reserve Inventory
```

If inventory fails:

```text
Compensating action
        ↓
Refund Payment
        ↓
Cancel Order
```

### Two common Saga styles

**Choreography**

Services communicate through events.

```text
Order → event
          ↓
Payment → event
          ↓
Inventory
```

**Orchestration**

A central Saga orchestrator tells services what to do.

```text
          Saga Orchestrator
          /       |       \
         ↓        ↓        ↓
      Order    Payment   Inventory
```

### Interview answer

> **"Saga is a pattern for managing business transactions that span multiple microservices. Instead of one distributed database transaction, the overall operation is divided into local transactions, with compensating actions used when a later step fails. Saga can be implemented through choreography using events or orchestration using a central coordinator."**

# Q161. What is a Config Server?

A Config Server provides **centralized external configuration** for multiple services.

Instead of:

```text
Service A → application.properties
Service B → application.properties
Service C → application.properties
```

you can have:

```text
             Config Server
              /    |    \
             ↓     ↓     ↓
          Service A B   C
```

Configuration could include:

- Database configuration
- Feature flags
- Service URLs
- Environment-specific properties

---

# Q162. Why is centralized configuration needed?

Because otherwise configuration becomes duplicated across services and environments.

For example:

```text
dev
test
prod
```

Each service needs different values.

Centralized configuration gives:

- Consistency
- Environment-specific configuration
- Reduced duplication
- Easier management
- Separation of configuration from application code

### Important production consideration

Don't store secrets casually in a plain config repository.

For sensitive values, use a **secret-management mechanism** such as Kubernetes Secrets or a dedicated secret manager.

### Interview answer

> **"Centralized configuration allows multiple services to obtain environment-specific configuration from a managed source rather than maintaining duplicated configuration independently in every service. It improves consistency and operational management. Sensitive credentials should still be handled through an appropriate secret-management mechanism."**

# Q168. How do you manage transactions in microservices?

The first principle:

> **Keep normal transactions local to a service/database whenever possible.**

For example:

```text
Payment Service
     ↓
DB Transaction
     ↓
Payment updated
```

Inside Spring:

```java id="3jcc3u"
@Transactional
public void processPayment() {
    ...
}
```

But:

```text
Service A DB
      +
Service B DB
```

cannot normally be handled with one simple local transaction.

That's where distributed transaction patterns come in.

### Interview answer

> **"I prefer keeping transactions local to a microservice and its database. Within a service, Spring's `@Transactional` can provide atomicity for the local database operation. If a business transaction spans multiple services, I would avoid trying to maintain one tightly coupled database transaction and instead consider patterns such as Saga or transactional messaging depending on the use case."**

# Q169. How do you handle distributed transactions?

There are several approaches, but in modern microservice architectures the common approach is **eventual consistency with Saga**.

Example:

```text
Order created
     ↓
Payment processed
     ↓
Inventory reserved
```

If inventory fails:

```text
Inventory failure
       ↓
Compensation
       ↓
Refund payment
       ↓
Cancel order
```

Another important pattern:

### Outbox

Suppose you update DB and publish Kafka event.

You don't want:

```text
DB update → SUCCESS
Kafka publish → FAILURE
```

leaving the system inconsistent.

The **Outbox Pattern** stores the event in the same database transaction, then a separate process publishes it.

### Interview answer

> **"For distributed transactions, I would generally prefer eventual consistency rather than a tightly coupled distributed transaction. Saga can coordinate the business transaction across services using local transactions and compensating actions. When reliable database-to-event publishing is required, the Outbox pattern can help ensure that a database change and the corresponding event are persisted reliably."**

# Q170. How do microservices communicate with each other?

Two major approaches:

### Synchronous

```text
Service A
   ↓ REST/gRPC
Service B
```

Service A waits for Service B.

### Asynchronous

```text
Service A
   ↓
Kafka/NATS
   ↓
Service B
```

Service A doesn't need Service B to respond immediately.

### Interview answer

> **"Microservices can communicate synchronously using REST or gRPC, or asynchronously using messaging systems such as Kafka or NATS. I choose based on the business requirement. Synchronous communication is useful when an immediate response is required, while asynchronous messaging is useful for decoupling services and handling event-driven workflows."**

```text
                            |
                            ↓
                      API GATEWAY
                            |
                            ↓
                    SERVICE DISCOVERY

Synchronous resilience:
```
