# Q221. How did you deploy your microservices?

```text id="2qgq3f"

    ↓

    ↓

    ↓

    ↓
```

### What happens?

1. Code is committed.
2. Jenkins pipeline is triggered.
3. Application is built and tested.
4. Docker image is created.
5. Image is pushed to a registry.
6. Kubernetes deployment references the image.
7. Kubernetes creates/updates Pods.
8. Kubernetes Service exposes the application internally or externally depending on configuration.

### Interview answer

> **"Our services are containerized using Docker and deployed on Kubernetes. The CI/CD pipeline uses Jenkins to build and test the application, create the Docker image and deploy the required version to the Kubernetes environment. Kubernetes then manages the Pods and their lifecycle."**

# Q224. How do you scale microservices?

There are two broad approaches:

### Horizontal scaling

Add more instances:

```text id="k5pk1n"
Before:

Payment
  ↓
Pod 1


After:

Payment
  ├── Pod 1
  ├── Pod 2
  └── Pod 3
```

### Vertical scaling

Give an instance more resources:

```text id="75ad2r"
Before:
2 CPU
4 GB RAM

After:
4 CPU
8 GB RAM
```

In Kubernetes, **horizontal scaling is commonly used for stateless microservices**.

### Interview answer

> **"Microservices can be scaled horizontally by increasing the number of running instances, or vertically by increasing the CPU and memory available to an instance. In Kubernetes, horizontal scaling is commonly used for stateless services because multiple Pods can serve requests concurrently."**

# Q225. Difference between scaling up and scaling down?

⚠️ One terminology trap here.

Usually:

**Scale up** can mean **increase resources**, while **scale down** means decrease resources.

But in Kubernetes discussions, people often use:

- **Scale out** → increase number of instances
- **Scale in** → decrease number of instances

So I'd answer carefully.

### Vertical scaling

```text id="z24rjv"
Scale UP:
2 CPU → 4 CPU

Scale DOWN:
4 CPU → 2 CPU
```

### Horizontal scaling

```text id="1n4w3b"
Scale OUT:
3 Pods → 6 Pods

Scale IN:
6 Pods → 3 Pods
```

### Interview answer

> **"Strictly speaking, scaling up and down usually refer to increasing or decreasing the resources of an instance, such as CPU or memory. For changing the number of instances, the more precise terms are scale out and scale in. In Kubernetes, for example, changing replicas from 3 to 6 is scaling out, while reducing them from 6 to 3 is scaling in."**

That's a **nice senior-level clarification**.

# Q226. How do you scale up a microservice?

If they mean **horizontal scaling**:

Increase replicas.

For example:

```yaml id="1j8r5s"
spec:
  replicas: 3
```

Change to:

```yaml id="kjl9a2"
spec:
  replicas: 6
```

Or:

```bash id="lkvh5b"
kubectl scale deployment payment \
  --replicas=6
```

Kubernetes creates additional Pods.

```text id="p9qqpr"
Deployment
    |
    ├── Pod 1
    ├── Pod 2
    ├── Pod 3
    ├── Pod 4
    ├── Pod 5
    └── Pod 6
```

### Interview answer

> **"For horizontal scaling, I increase the desired replica count of the Kubernetes Deployment. Kubernetes then creates additional Pods and distributes workloads across the available instances. This can also be automated using mechanisms such as Horizontal Pod Autoscaler when appropriate metrics and resource configuration are available."**

# Q227. How do you scale down a microservice?

Simply reduce replicas.

For example:

```yaml id="w5i1e4"
replicas: 6
```

to:

```yaml id="r5r7z4"
replicas: 3
```

or:

```bash id="p0knkn"
kubectl scale deployment payment \
  --replicas=3
```

Kubernetes terminates the excess Pods while maintaining the desired state.

### Interview answer

> **"For horizontal scale-in, I reduce the desired replica count of the Kubernetes Deployment. Kubernetes then terminates the excess Pods and maintains the configured desired number of replicas."**

# Q228. How do you increase/decrease Kubernetes replicas?

Three common ways you should know.

### 1. Deployment YAML

```yaml id="qpn5b8"
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 5
```

Change:

```text id="wdg5e8"
3 → 5
```

### 2. kubectl

```bash id="e1xj5q"
kubectl scale deployment payment --replicas=5
```

### 3. Horizontal Pod Autoscaler

Instead of manually changing replicas:

```text id="46yr87"
CPU / memory / custom metrics
             ↓
           HPA
             ↓
       replicas change
```

For example:

```text id="9n98kq"
High load
   ↓
HPA
   ↓
3 Pods → 6 Pods
```

When load drops:

```text id="f1vl9q"
6 Pods → 3 Pods
```

### Interview answer

> **"Replicas can be changed directly in the Deployment configuration, through `kubectl scale`, or automatically using a Horizontal Pod Autoscaler. HPA adjusts the desired replica count based on configured metrics such as CPU utilization or other supported/custom metrics."**

# Q229. How does Kubernetes help in microservice deployment and scaling?

This is the **big-picture question**.

Kubernetes provides:

### Deployment management

```text
Deployment
   ↓
Desired state
   ↓
Pods
```

### Self-healing

If a Pod crashes:

```text id="z5qk2n"
Pod dies
  ↓
Kubernetes detects difference
  ↓
New Pod
```

### Scaling

```text
3 replicas → 6 replicas
```

### Service discovery/load distribution

Kubernetes Services provide a stable network endpoint for a set of Pods.

```text id="s6v6lc"
Client
  ↓
Kubernetes Service
  ├── Pod 1
  ├── Pod 2
  └── Pod 3
```

### Rolling deployments

Kubernetes can gradually replace old Pods with new ones rather than taking the entire service down.

### Interview answer

> **"Kubernetes provides the runtime orchestration layer for microservices. It manages deployments and Pod lifecycles, maintains the desired number of replicas, restarts or replaces failed Pods, supports horizontal scaling, provides service discovery through Services, and supports controlled rollout of new versions. This allows microservices to be deployed and scaled without manually managing individual servers or processes."**
