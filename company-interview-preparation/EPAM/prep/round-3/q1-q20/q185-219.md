## Q185. What is Spring Batch?

Spring Batch is a framework for developing **robust batch-processing applications**.

It provides infrastructure for processing large volumes of data with features such as:

- Chunk processing
- Transaction management
- Retry
- Skip
- Restartability
- Job/step execution tracking
- Partitioning
- Parallel processing

The basic structure is:

```text
Job
 └── Step
      ├── ItemReader
      ├── ItemProcessor
      └── ItemWriter
```

### Interview answer

> **"Spring Batch is a framework for developing and executing batch-processing jobs. It provides features such as chunk-oriented processing, transaction management, restartability, skip and retry handling, job execution metadata, and partitioning for parallel processing."**

# Q187. What are the main components of Spring Batch?

The core components you should know are:

```text
Job
 ↓
Step
 ↓
Reader → Processor → Writer
```

### 1. Job

Represents the overall batch process.

Example:

```text
PF Ledger Migration Job
```

### 2. Step

A job consists of one or more steps.

```text
Job
 ├── Step 1: Read staging data
 ├── Step 2: Transform
 └── Step 3: Write output
```

### 3. ItemReader

Reads input data.

Examples:

```text
JdbcCursorItemReader
JdbcPagingItemReader
JpaPagingItemReader
```

### 4. ItemProcessor

Transforms or validates the data.

```java
public Output process(Input input) {
    ...
}
```

### 5. ItemWriter

Writes processed data.

```text
Database
File
Kafka
etc.
```

### 6. JobRepository

Stores Spring Batch execution metadata.

For example:

```text
JobInstance
JobExecution
StepExecution
JobParameters
```

### Interview answer

> **"The main components are Job, Step, ItemReader, ItemProcessor and ItemWriter. A Job consists of one or more Steps. A Step can use a reader to read data, a processor to transform or validate it, and a writer to persist or publish the result. Spring Batch also uses a JobRepository to store job and step execution metadata."**

# Q188. How does a Spring Batch job execute?

The basic lifecycle is:

```text
JobLauncher
    ↓
Job
    ↓
Step
    ↓
Reader
    ↓
Processor
    ↓
Writer
    ↓
Next chunk
    ↓
...
    ↓
Job completed
```

For chunk processing, suppose:

```text
chunk size = 100
```

Spring Batch conceptually does:

```text
Read 100
   ↓
Process 100
   ↓
Write 100
   ↓
Commit transaction
```

Then:

```text
Read next 100
   ↓
Process
   ↓
Write
   ↓
Commit
```

### Why chunks matter

You don't need to load millions of records into memory.

For example:

```text
10 million records
       ↓
chunk = 1000
       ↓
process a manageable amount
       ↓
commit
       ↓
next chunk
```

### Interview answer

> **"A batch job is launched through a JobLauncher. The job consists of steps, and a chunk-oriented step repeatedly reads a configured number of items, processes them, and writes them. Each chunk normally represents a transaction boundary, so after a successful write the transaction is committed and processing continues with the next chunk. Spring Batch also records execution metadata so the job can be monitored and restarted when required."**

# Q189. How do you handle failures and retries in Spring Batch?

This is **very important** because your resume explicitly mentions fault handling.

Spring Batch provides:

### Retry

For a transient failure:

```text
Process item
   ↓
Failure
   ↓
Retry
   ↓
Retry
   ↓
Success
```

For example:

```java
.faultTolerant()
.retry(SomeTransientException.class)
.retryLimit(3)
```

### Skip

If a particular record is invalid and shouldn't stop the entire batch:

```java
.faultTolerant()
.skip(SomeBadRecordException.class)
.skipLimit(100)
```

Conceptually:

```text
Record 1 → success
Record 2 → success
Record 3 → invalid → skip
Record 4 → success
```

### Restartability

If a job fails after processing part of the data, Spring Batch maintains execution metadata so the job can potentially restart from the appropriate point rather than blindly starting from zero.

### Interview answer

> **"For transient failures, I use retry with a controlled retry limit. For known bad records that shouldn't stop the entire batch, skip logic can be used with a configured skip limit. Spring Batch also maintains job and step execution metadata, which supports restartability. In production, I would also make sure failures are observable and that permanently failed records can be identified and handled separately rather than silently lost."**

### Important distinction

**Retry ≠ Skip.**

```text
Retry → "Maybe this will succeed if I try again."

Skip  → "This record is invalid/unprocessable, so continue with the next one."
```

# Q190. Why is PostgreSQL being used for Spring Batch metadata?

This question is particularly relevant to your project.

Spring Batch needs to maintain metadata about execution.

For example:

```text
BATCH_JOB_INSTANCE
BATCH_JOB_EXECUTION
BATCH_STEP_EXECUTION
BATCH_JOB_EXECUTION_PARAMS
...
```

This metadata allows Spring Batch to know things such as:

- Which job ran
- Which parameters were used
- Whether execution succeeded/failed
- Which steps completed
- Execution statistics
- Restart information

### Why PostgreSQL?

If your application already uses PostgreSQL as its transactional database, using PostgreSQL for Spring Batch metadata gives you a reliable persistent relational store without introducing another database just for batch metadata.

### Interview answer

> **"Spring Batch requires a persistent JobRepository to maintain job and step execution metadata. We use PostgreSQL for this metadata because it provides reliable transactional persistence and integrates well with our existing application infrastructure. The metadata is important for tracking executions, failures, restartability and job parameters."**

### Important distinction

Don't say:

> "Spring Batch stores the actual business data in these tables."

No.

There are two different things:

```text
Business data
     ↓
Your application tables

Spring Batch metadata
     ↓
BATCH_* tables
```

## Q213. What is a Security Filter Chain?

Spring Security processes incoming HTTP requests through a **chain of security filters**.

Conceptually:

```text
HTTP Request
     ↓
Security Filter Chain
     ↓
Authentication
     ↓
Authorization
     ↓
Controller
```

Different filters handle different security responsibilities.

For example, depending on configuration:

```text
Request
 ↓
CORS / CSRF related processing
 ↓
Authentication filter
 ↓
SecurityContext
 ↓
Authorization
 ↓
Controller
```

### Interview answer

> **"The Spring Security Filter Chain is a sequence of security filters that process an incoming HTTP request before it reaches the controller. Depending on the configuration, these filters handle authentication, security context management, authorization and other security-related concerns. If the request passes the required security checks, it can proceed to the controller."**

---

# Q214. How do you implement a Security Filter Chain?

In modern Spring Security, we typically define a `SecurityFilterChain` bean.

For example:

```java
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        );

    return http.build();
}
```

The important part is:

```java
@Bean
SecurityFilterChain
```

and configuring:

```java
HttpSecurity
```

### Interview answer

> **"I implement the security configuration by defining a `SecurityFilterChain` bean and configuring `HttpSecurity`. In that configuration I specify which endpoints are public, which require authentication, and how authentication mechanisms such as JWT or Basic Authentication should be handled."**

# Q215. How do you protect APIs using Spring Security?

For example:

```java
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/health").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        );

    return http.build();
}
```

Conceptually:

```text
/health
   ↓
Public

/api/payment
   ↓
Authenticated users

/admin/**
   ↓
ADMIN role required
```

### Interview answer

> **"I protect APIs by configuring authorization rules in the Security Filter Chain. Public endpoints can be permitted explicitly, while other endpoints can require authentication or specific roles/authorities. The authentication mechanism, such as JWT, then establishes the authenticated principal that Spring Security uses for authorization."**

# Q216. How do you configure publicly accessible APIs?

Use:

```java
.requestMatchers("/public/**").permitAll()
```

For example:

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers(
        "/actuator/health",
        "/public/**"
    ).permitAll()
    .anyRequest().authenticated()
)
```

The key idea is:

> **Explicitly permit only the endpoints that should be public.**

Don't do:

```java
.anyRequest().permitAll()
```

unless the application is intentionally completely public.

# Q217. How do you configure JWT authentication in the Security Filter Chain?

For a typical Spring Security **OAuth2 Resource Server** setup:

```java
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http) throws Exception {

    http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2ResourceServer(
            oauth -> oauth.jwt()
        );

    return http.build();
}
```

The conceptual flow is:

```text
Client
  |
  | Authorization: Bearer <JWT>
  ↓
Spring Security
  |
  ↓
JWT authentication
  |
  ↓
Validate token
  |
  ↓
Create Authentication
  |
  ↓
Authorization
  |
  ↓
Controller
```

### What does Spring validate?

Depending on configuration:

- Signature
- Issuer
- Expiration
- Claims
- Other configured validation rules

Then authorities/claims can be used for authorization.

### Interview answer

> **"For JWT-based authentication, I configure the application as an OAuth2 Resource Server and enable JWT authentication in the Security Filter Chain. The client sends the JWT as a Bearer token. Spring Security validates the token and creates an authenticated security context. The authorization rules then use the authenticated user's authorities or claims to determine whether the request can access the endpoint."**

# Q218. How would you configure Basic Authentication?

Conceptually:

```java
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        )
        .httpBasic(Customizer.withDefaults());

    return http.build();
}
```

Client sends:

```text
Authorization: Basic <base64(username:password)>
```

Spring Security authenticates the supplied credentials.

### Interview answer

> **"For Basic Authentication, I enable `httpBasic()` in the Security Filter Chain and configure the required authorization rules. The client sends username and password credentials using the HTTP Basic Authorization header. In production, Basic Authentication should be protected by HTTPS because credentials are only Base64-encoded, not encrypted by Basic Authentication itself."**

# Q219. How does Spring Security authenticate and authorize a request?

This is the **most important question in this section**.

Understand these as two separate concepts:

### Authentication

> **Who are you?**

### Authorization

> **What are you allowed to access?**

Flow:

```text
HTTP Request
     |
     ↓
Security Filter Chain
     |
     ↓
Authentication
     |
     ↓
SecurityContext
     |
     ↓
Authorization
     |
     ↓
Controller
```

For JWT:

```text
Request
  ↓
Bearer JWT
  ↓
JWT validation
  ↓
Authenticated principal
  ↓
Authorities / roles
  ↓
Authorization rules
  ↓
Allow / Deny
```

Example:

```java
.requestMatchers("/admin/**")
.hasRole("ADMIN")
```

If authenticated user has:

```text
ROLE_ADMIN
```

→ allowed.

If user is authenticated but doesn't have the required authority:

```text
403 Forbidden
```

If the user isn't authenticated:

```text
401 Unauthorized
```

### Strong interview answer

> **"Spring Security processes the request through the Security Filter Chain. Authentication verifies the identity of the caller—for example, by validating a JWT—and creates an authenticated principal in the SecurityContext. Authorization then evaluates that authenticated principal against the configured endpoint rules, roles or authorities. If authentication fails, the request is unauthenticated; if authentication succeeds but the user lacks the required authority, access is denied."**
