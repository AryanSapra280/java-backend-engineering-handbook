# Q93. How does synchronization work in Java?

This is a **very important Senior-level question**.

Suppose:

```java
class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }
}
```

Multiple threads executing:

```java
count++;
```

can cause a race condition.

Why?

Because:

```text
count++
```

is effectively:

```text
READ count
ADD 1
WRITE count
```

Two threads can interleave these operations.

### `synchronized`

```java
public synchronized void increment() {
    count++;
}
```

Now only one thread can execute the synchronized method on the same object monitor at a time.

You can also synchronize a block:

```java
public void increment() {

    synchronized (this) {
        count++;
    }
}
```

### What does synchronization provide?

Two important things:

**1. Mutual exclusion**

Only one thread can enter the protected critical section at a time for the same monitor.

**2. Visibility**

Changes made by one thread inside the synchronized region become visible to another thread that subsequently acquires the same monitor.

So a good answer is:

> **"Synchronization provides mutual exclusion and memory visibility when multiple threads access shared mutable state. The synchronized keyword uses an object's monitor lock. When one thread enters a synchronized section, another thread cannot simultaneously enter a synchronized section guarded by the same monitor. Synchronization also establishes the required happens-before relationship for visibility."**

# Q94. What are the common problems in concurrent programming?

Know these very well:

### 1. Race condition

Multiple threads access shared state and the result depends on execution order.

```text
Thread A → read 10
Thread B → read 10
Thread A → write 11
Thread B → write 11

Expected: 12
Actual:   11
```

### 2. Deadlock

Two threads wait for each other's locks.

```text
Thread A → Lock A → waiting for Lock B

Thread B → Lock B → waiting for Lock A
```

Neither can proceed.

### 3. Starvation

A thread never gets enough CPU/lock access because other threads continuously get the resources.

### 4. Livelock

Threads aren't blocked, but keep responding to each other without making progress.

### 5. Visibility problems

One thread updates a variable but another thread doesn't necessarily observe the updated value without proper synchronization/visibility guarantees.

### Interview answer

> **"Common problems include race conditions, deadlocks, starvation, livelocks, and visibility issues. Race conditions happen when multiple threads concurrently modify shared state without proper synchronization. Deadlocks occur when threads wait indefinitely for locks held by each other. Starvation occurs when a thread doesn't get sufficient access to resources, while livelock occurs when threads remain active but make no real progress."**

## Q96. What is `this()`?

`this()` calls **another constructor of the same class**.

```java
class Employee {

    Employee() {
        this("Unknown");
    }

    Employee(String name) {
        System.out.println(name);
    }
}
```

Here:

```java
this("Unknown");
```

calls:

```java
Employee(String name)
```

of the **same class**.

### Interview answer

> **"`this()` is used to invoke another constructor of the same class. It is mainly used for constructor chaining and avoiding duplicate initialization logic."**

## Q97. What is `super()`?

`super()` invokes the **constructor of the immediate parent class**.

```java
class Parent {

    Parent() {
        System.out.println("Parent");
    }
}

class Child extends Parent {

    Child() {
        super();
        System.out.println("Child");
    }
}
```

Execution:

```text
Parent constructor
      ↓
Child constructor
```

### Interview answer

> **"`super()` is used to invoke the constructor of the immediate superclass. It is used when the child needs to explicitly initialize the parent portion of the object."**

# Q98. Difference between `this()` and `super()`

Very simple:

| `this()` | `super()` |
|---|---|
| Calls constructor in same class | Calls constructor in parent class |
| Constructor chaining within same class | Constructor chaining to superclass |
| Refers to current class constructor | Refers to immediate parent constructor |

Example:

```java
class Child extends Parent {

    Child() {
        this(10);
    }

    Child(int x) {
        super();
    }
}
```

Here:

```java
this(10);   // another Child constructor
super();    // Parent constructor
```

# Q99. Can `this()` and `super()` be used together?

**Not directly in the same constructor.**

Why?

Both must be the **first statement** in a constructor.

This is invalid:

```java
Child() {
    this(10);
    super();   // ❌
}
```

And:

```java
Child() {
    super();
    this(10);   // ❌
}
```

However, they **can participate in the same constructor chain**.

Example:

```java
class Child extends Parent {

    Child() {
        this(10);
    }

    Child(int x) {
        super();
    }
}
```

Execution:

```text
Child()
  ↓
this(10)
  ↓
Child(int)
  ↓
super()
  ↓
Parent()
```

That's a great interview trap.

# Q100. Restrictions / edge cases

Remember these four:

### 1. Must be first statement

```java
Child() {
    System.out.println("Hi");
    super();  // ❌
}
```

Invalid.

### 2. Cannot use both in the same constructor

Because both must be first.

### 3. Cannot use `this()` and `super()` from a static context

Constructors aren't static, and `this`/`super` are instance-related.

### 4. Constructor chaining eventually reaches `Object`

If you don't explicitly call a parent constructor, Java inserts an implicit:

```java
super();
```

provided the superclass has an accessible no-argument constructor.

So:

```java
class Parent {
}

class Child {
    Child() {
    }
}
```

is effectively:

```java
Child() {
    super();
}
```

assuming the normal inheritance relationship (`Child extends Parent`) exists.

# 101. What is an Interface?

An **interface** in Java defines a contract that a class can implement.

It specifies **what a class should do**, while the implementing class provides the actual implementation.

```java
interface PaymentService {
    void processPayment();
}

class CardPayment implements PaymentService {

    @Override
    public void processPayment() {
        System.out.println("Processing card payment");
    }
}
```

Here `PaymentService` defines the contract, and `CardPayment` provides the implementation.

### Interview answer

> **"An interface in Java defines a contract that implementing classes must follow. It is mainly used to achieve abstraction and loose coupling. A class can implement multiple interfaces, which also allows Java to achieve multiple inheritance of type."**

# 102. What are Abstract Methods in an Interface?

An **abstract method** is a method that has a declaration but **no implementation/body**.

```java
interface PaymentService {

    void processPayment();  // abstract method
}
```

The implementing class must provide the implementation:

```java
class CardPayment implements PaymentService {

    @Override
    public void processPayment() {
        System.out.println("Card payment");
    }
}
```

By default, methods declared in an interface without `default` or `static` are **public and abstract**.

So this:

```java
void processPayment();
```

is effectively:

```java
public abstract void processPayment();
```

### Interview answer

> **"An abstract method in an interface defines a method signature without providing an implementation. The implementing class is responsible for providing the implementation, unless the class itself is abstract."**

# 103. What are Default Methods?

**Default methods were introduced in Java 8.**

They allow an interface to provide a **method implementation** using the `default` keyword.

```java
interface PaymentService {

    default void validatePayment() {
        System.out.println("Default validation");
    }
}
```

An implementing class automatically gets this implementation:

```java
class CardPayment implements PaymentService {
}
```

So:

```java
CardPayment payment = new CardPayment();
payment.validatePayment();
```

works even though `CardPayment` didn't implement `validatePayment()`.

### Why were default methods introduced?

A major reason was **backward compatibility**.

Imagine Java has:

```java
interface PaymentService {
    void process();
}
```

and hundreds of classes implement it.

If Java adds a new abstract method:

```java
void validate();
```

all existing implementations would break because they would need to implement the new method.

A default method allows Java to add behavior to an existing interface without forcing every implementation to immediately implement the new method.

### Interview answer

> **"Default methods were introduced in Java 8 to allow interfaces to contain methods with implementations. One important use case is maintaining backward compatibility when adding new functionality to an existing interface."**

---

### Default


### Static



Not:

### Strong interview answer

> **"An abstract interface method only declares the contract and has no implementation, so the implementing class must provide one. ### One important trap ⚠️

If two interfaces provide the **same default method**, the implementing class has to resolve the conflict:

```java
interface A {
    default void show() {}
}

interface B {
    default void show() {}
}

class C implements A, B {
    @Override
    public void show() {
        // resolve conflict
    }
}
```

Java doesn't arbitrarily choose between the two defaults. The class must resolve the ambiguity.
# Extra
# What is **happens-before**? How do we decide the order if Thread B executes first?

### Answer

**Happens-before is a Java Memory Model rule that establishes ordering and visibility between actions performed by different threads.**

If **A happens-before B**, it means that the effects of A are guaranteed to be visible to B, and Java guarantees that A is ordered before B **from the memory-model perspective**.

However, **happens-before does not decide which thread the scheduler runs first**. The JVM/OS scheduler decides the actual execution order.

For example, without synchronization:

```java
int x = 0;

Thread A:
x = 10;

Thread B:
System.out.println(x);
```

Thread B could execute first:

```text
Thread B → reads x → 0
Thread A → writes x = 10
```

That's completely possible because there is **no happens-before relationship** between the two operations.

Now suppose we use `join()`:

```java
Thread A:
x = 10;

Thread B:
A.join();
System.out.println(x);
```

Here Java guarantees:

```text
Thread A:
x = 10
   ↓
Thread A finishes
   ↓
Thread B: A.join() returns
   ↓
Thread B reads x → 10
```

The actions performed by Thread A happen-before Thread B successfully returns from `join()`.

Similarly, synchronization can establish happens-before:

```java
Thread A:
synchronized(lock) {
    x = 10;
}

Thread B:
synchronized(lock) {
    System.out.println(x);
}
```

If B acquires the same lock **after A releases it**, A's actions before the unlock happen-before B's actions after acquiring the lock.

### The key distinction

> **The scheduler decides execution order; synchronization establishes happens-before relationships.**

So if the interviewer asks:

**"Does happens-before mean Thread A will always execute before Thread B?"**

Say:

> **"No. Happens-before doesn't control thread scheduling. It is a Java Memory Model guarantee about ordering and visibility. If Thread B executes first, it can execute first unless some synchronization mechanism establishes a required ordering. For example, `join()`, `synchronized`, and volatile operations can establish happens-before relationships that guarantee visibility and ordering between specific actions."**
