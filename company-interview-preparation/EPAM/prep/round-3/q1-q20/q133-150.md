## Q133. What is ORM?

**ORM = Object-Relational Mapping.**

It is a technique for mapping **objects in an object-oriented application** to **relational database tables**.

For example:

```java
@Entity
public class Payment {

    @Id
    private String id;

    private BigDecimal amount;
}
```

Could correspond to:

```text
payment
----------------
id
amount
```

ORM handles much of the conversion between:

```text
Java objects ↔ relational database records
```

### Interview answer

> **"ORM stands for Object-Relational Mapping. It is a technique that maps objects in an object-oriented application to relational database tables, allowing us to work with database data using objects instead of writing SQL for every basic CRUD operation."**

# Q135. How does ORM map Java objects to database tables?

We typically use annotations.

```java
@Entity
@Table(name = "payments")
public class Payment {

    @Id
    private String id;

    @Column(name = "amount")
    private BigDecimal amount;
}
```

Conceptually:

```text
Payment class
      ↓
payments table

id       → id
amount   → amount
```

Common annotations:

```text
@Entity
@Table
@Id
@Column
@OneToOne
@OneToMany
@ManyToOne
@ManyToMany
```

The ORM framework maintains the mapping and generates/executes SQL as required.

### Interview answer

> **"ORM maps a Java entity class to a database table and its fields to table columns. We define this mapping using annotations such as `@Entity`, `@Table`, `@Id`, and `@Column`. Relationships between entities can also be represented using annotations such as `@OneToMany` and `@ManyToOne`."**

# Q136. How are JPA and Hibernate related to ORM?

This distinction is **very important**.

### ORM

The **concept/technique**.

### JPA

A **Java specification/API** that defines how persistence should work.

### Hibernate

A popular **implementation of JPA**.

Think:

```text
ORM
 ↓
Concept

JPA
 ↓
Specification/API

Hibernate
 ↓
Implementation
```

For example:

```java
@Entity
public class Payment {
}
```

`@Entity` is part of the JPA API.

Hibernate can implement the behavior defined by JPA.

### Interview answer

> **"ORM is the general technique of mapping objects to relational data. JPA, or Jakarta Persistence, is a specification that defines APIs and standards for persistence in Java. Hibernate is a popular ORM framework and a JPA implementation. So JPA defines the contract, while Hibernate provides the implementation."**

### Important

Don't say:

> "JPA is a framework."

Better:

> **JPA is a specification/API.**

# Q137. What is a Criteria Query?

A **Criteria Query** allows you to construct a database query **programmatically using Java objects and APIs** instead of writing JPQL as a string.

For example, conceptually:

```java
CriteriaBuilder cb = entityManager.getCriteriaBuilder();

CriteriaQuery<Payment> query =
        cb.createQuery(Payment.class);

Root<Payment> payment =
        query.from(Payment.class);

query.select(payment)
     .where(cb.equal(payment.get("status"), "SUCCESS"));
```

Instead of:

```java
SELECT p
FROM Payment p
WHERE p.status = :status
```

### Interview answer

> **"A Criteria Query is a programmatic way of constructing JPA queries using the Criteria API. Instead of writing the query as a JPQL string, we build the query using Java objects such as `CriteriaBuilder`, `CriteriaQuery`, and `Root`."**

---

# Q138. What is the Criteria API?

The **Criteria API** is the JPA API used to construct type-safe, programmatic queries.

The important components are:

```text
CriteriaBuilder
       ↓
CriteriaQuery
       ↓
Root
       ↓
Predicates / conditions
```

Example:

```java
CriteriaBuilder cb =
        entityManager.getCriteriaBuilder();

CriteriaQuery<Payment> cq =
        cb.createQuery(Payment.class);

Root<Payment> root =
        cq.from(Payment.class);
```

### Interview answer

> **"The Criteria API is a JPA API for constructing queries programmatically. The main building blocks include `CriteriaBuilder` for creating expressions and predicates, `CriteriaQuery` for defining the query, and `Root` for defining the entity being queried."**

# Q139. Why would you use a Criteria Query?

The biggest reason is **dynamic queries**.

Imagine your API allows users to search payments using optional filters:

```text
status
amount
date
accountId
type
```

The user might provide:

```text
status = SUCCESS
accountId = 123
```

Another request might provide:

```text
status = SUCCESS
amount > 5000
date > 2026-01-01
```

Building one giant static query becomes difficult.

Criteria allows you to construct conditions dynamically.

### Interview answer

> **"I would mainly use Criteria queries when the query conditions are dynamic and depend on optional parameters. It allows us to build predicates programmatically instead of maintaining many different static queries."**

# Q140. Why do you need a CriteriaBuilder?

`CriteriaBuilder` is essentially the object used to **construct expressions and predicates** for Criteria queries.

For example:

```java
cb.equal(...)
cb.greaterThan(...)
cb.lessThan(...)
cb.and(...)
cb.or(...)
cb.like(...)
```

Example:

```java
Predicate status =
    cb.equal(root.get("status"), "SUCCESS");

Predicate amount =
    cb.greaterThan(root.get("amount"), 5000);

query.where(cb.and(status, amount));
```

### Interview answer

> **"`CriteriaBuilder` provides methods for constructing expressions, predicates and conditions used in a Criteria query. For example, we can use it to create `equal`, `greaterThan`, `like`, `and`, and `or` conditions."**

# Q141. Why not simply write your own query instead of using Criteria Query?

You absolutely **can** write JPQL or SQL.

Criteria isn't automatically better.

The advantage appears when queries are **highly dynamic**.

For example, suppose you have 10 optional filters.

With string-based query construction, you could end up managing:

```text
WHERE ...
AND ...
AND ...
```

and parameter handling manually.

Criteria lets you build predicates conditionally:

```java
List<Predicate> predicates = new ArrayList<>();

if (status != null) {
    predicates.add(
        cb.equal(root.get("status"), status)
    );
}

if (amount != null) {
    predicates.add(
        cb.greaterThan(root.get("amount"), amount)
    );
}
```

### Interview answer

> **"For a simple static query, I would generally prefer JPQL or a repository query because it is easier to read. Criteria becomes useful when the query structure is highly dynamic and different combinations of optional filters need to be added programmatically."**

That's a **much better answer** than saying Criteria is always superior.

# Q143. How does Criteria Query compare with JPQL?

This is a good comparison:

| JPQL | Criteria API |
|---|---|
| Query written as a string | Query built programmatically |
| Easier to read | More verbose |
| Good for static queries | Good for dynamic queries |
| Easier to write | More flexible for dynamic conditions |
| Runtime query parsing/validation concerns | More structured through Java API |

Example JPQL:

```java
@Query("""
    SELECT p FROM Payment p
    WHERE p.status = :status
""")
```

Criteria:

```java
cb.equal(root.get("status"), status)
```

### Interview answer

> **"JPQL is generally easier to read and is a good choice for static or relatively simple queries. Criteria API is more verbose but is useful when the query needs to be dynamically constructed based on runtime conditions. I would normally choose JPQL for straightforward fixed queries and Criteria for complex dynamic filtering."**

# Q144. How do you build dynamic queries using the Criteria API?

The typical process:

### Step 1 — Get CriteriaBuilder

```java
CriteriaBuilder cb =
    entityManager.getCriteriaBuilder();
```

### Step 2 — Create CriteriaQuery

```java
CriteriaQuery<Payment> cq =
    cb.createQuery(Payment.class);
```

### Step 3 — Define root

```java
Root<Payment> root =
    cq.from(Payment.class);
```

### Step 4 — Build predicates dynamically

```java
List<Predicate> predicates =
    new ArrayList<>();

if (status != null) {
    predicates.add(
        cb.equal(root.get("status"), status)
    );
}

if (minAmount != null) {
    predicates.add(
        cb.greaterThan(
            root.get("amount"),
            minAmount
        )
    );
}
```

### Step 5 — Apply predicates

```java
cq.where(
    cb.and(predicates.toArray(new Predicate[0]))
);
```

### Step 6 — Execute

```java
return entityManager
        .createQuery(cq)
        .getResultList();
```

### Interview answer

> **"I would create a `CriteriaBuilder`, then a `CriteriaQuery` and a `Root` for the entity. I would build a list of `Predicate` objects based on the filters supplied at runtime, combine those predicates, apply them to the query, and finally create and execute the JPA query through the EntityManager."**

# Q147. What is the N+1 Query Problem?

This is **very important for JPA/Hibernate interviews.**

Suppose we have:

```text
Department
    ↓
Employees
```

You query 10 departments:

```sql
SELECT * FROM department;
```

That's **1 query**.

Then Hibernate accesses employees for each department:

```text
SELECT * FROM employee WHERE department_id = 1;
SELECT * FROM employee WHERE department_id = 2;
SELECT * FROM employee WHERE department_id = 3;
...
```

That's another **10 queries**.

Total:

```text
1 + 10 = 11 queries
```

Hence:

> **N+1**

One query to retrieve N parent records, followed by N additional queries to retrieve their associated data.

---

# Q148. How does the N+1 Query Problem occur?

It commonly occurs because of **lazy-loaded relationships**.

Example:

```java
@Entity
class Department {

    @OneToMany(fetch = FetchType.LAZY)
    private List<Employee> employees;
}
```

You execute:

```java
List<Department> departments =
    repository.findAll();
```

Initially, Hibernate may execute:

```sql
SELECT * FROM department;
```

Then your code does:

```java
for (Department department : departments) {
    department.getEmployees().size();
}
```

Accessing the lazy collection causes Hibernate to execute another query for each department.

So:

```text
1 query → departments

N queries → employees for each department
```

Total:

```text
N + 1
```

### Important

**Lazy loading itself isn't bad.**

The problem is when your access pattern unintentionally causes many database round trips.

# Q149. How do you resolve the N+1 Query Problem?

Several approaches exist, depending on the use case.

### 1. `JOIN FETCH`

Fetch parent and required relationship in one query.

```jpql
SELECT d
FROM Department d
JOIN FETCH d.employees
```

### 2. Entity Graph

Use JPA `@EntityGraph` to specify what associations should be fetched for a particular query.

### 3. DTO projection

Fetch only the data actually required by the API.

### 4. Batch fetching

Hibernate can batch the loading of related entities rather than issuing one query per parent.

### Interview answer

> **"I would first identify the N+1 issue using SQL logs or monitoring. Depending on the use case, I could resolve it using `JOIN FETCH`, an entity graph, DTO projections, or Hibernate batch fetching. I wouldn't blindly change everything to eager loading because that can create unnecessary data loading and memory usage."**

That last sentence is **important**.

# Q150. What is `JOIN FETCH` and how can it solve N+1?

`JOIN FETCH` is a **JPQL feature** that tells JPA/Hibernate to fetch an association as part of the query rather than loading it separately later.

Without it:

```jpql
SELECT d
FROM Department d
```

Hibernate may later load employees individually.

With:

```jpql
SELECT d
FROM Department d
JOIN FETCH d.employees
```

Hibernate can fetch the departments and employees together.

Conceptually:

```text
Without JOIN FETCH:

SELECT departments
       ↓
N additional employee queries


With JOIN FETCH:

SELECT departments + employees
       ↓
single database query
```

### Interview answer

> **"`JOIN FETCH` is used in JPQL to fetch an associated entity or collection as part of the main query. It can prevent the N+1 problem by retrieving the required association in the same database query instead of triggering separate lazy-loading queries for each parent entity."**

### Important follow-up: Can JOIN FETCH cause duplicates?

**Yes**, especially with collection relationships.

For example:

```jpql
SELECT d
FROM Department d
JOIN FETCH d.employees
```

A department with 5 employees can appear across 5 joined rows at the SQL level.

Depending on the query/use case, you may use:

```jpql
SELECT DISTINCT d
FROM Department d
JOIN FETCH d.employees
```

Also, fetching **multiple collection relationships** with joins can create a Cartesian-product-like explosion and huge result sets.

### ⭐ For EPAM, I'd especially prepare these follow-ups:

**"Why not always use EAGER?"**

> Because eager loading can retrieve data that isn't needed, increase memory usage, and create expensive queries. Fetch strategy should depend on the specific use case.

**"How do you identify N+1?"**

> Enable SQL/query logging, inspect the number of queries, and use application/database monitoring or profiling.

**"Is N+1 only caused by lazy loading?"**

> No. Lazy loading is a common cause, but the broader issue is an access pattern that causes one query for the parent data and additional queries per parent.

**"Would JOIN FETCH always be the solution?"**

> No. It depends on the data and relationship. DTO projections, entity graphs, or batch fetching may be more appropriate, especially for large collections.
