# 10. REST API / Spring MVC — Q117–132

These are very practical questions. For EPAM, don't just memorize annotations—the interviewer may ask you to **design a small REST API and explain the request flow**.

---

## Q117. Suppose you are creating a REST service. How would you implement it?

I'd structure it roughly like this:

```text
HTTP Request
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
```

For example, a payment API:

```java
@RestController
@RequestMapping("/payments")
public class PaymentController {

    private final PaymentService paymentService;

    public PaymentController(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    @PostMapping
    public PaymentResponse create(
            @RequestBody PaymentRequest request) {

        return paymentService.createPayment(request);
    }
}
```

Then:

```java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }

    public PaymentResponse createPayment(PaymentRequest request) {
        // business logic
        // repository interaction
        return ...;
    }
}
```

And:

```java
@Repository
public interface PaymentRepository
        extends JpaRepository<Payment, String> {
}
```

### Interview answer

> **"I would typically structure the REST service into Controller, Service and Repository layers. The Controller handles HTTP requests and responses, the Service contains business logic, and the Repository handles database interaction. I would use DTOs for the API contract, constructor-based dependency injection, validation, and centralized exception handling."**

# Q118. What annotations would you use while creating a REST API?

The commonly used ones are:

### Controller

```java
@RestController
@RequestMapping
```

### HTTP methods

```java
@GetMapping
@PostMapping
@PutMapping
@PatchMapping
@DeleteMapping
```

### Request data

```java
@RequestBody
@RequestParam
@PathVariable
```

### Dependency injection

```java
@Autowired
```

although preferably we use **constructor injection**, so explicit `@Autowired` is often unnecessary.

### Validation

```java
@Valid
@NotNull
@NotBlank
@Size
```

### Exception handling

```java
@RestControllerAdvice
@ExceptionHandler
```

### Interview answer

> **"The main annotations I would use are `@RestController`, `@RequestMapping`, the HTTP method mappings such as `@GetMapping` and `@PostMapping`, and request-binding annotations such as `@RequestBody`, `@RequestParam` and `@PathVariable`. For validation I'd use Bean Validation annotations with `@Valid`, and for centralized exception handling I'd use `@RestControllerAdvice` and `@ExceptionHandler`."**

# Q119. How would you structure a REST API using Controller, Service, and Repository layers?

Think about **responsibility separation**.

```text
Controller
    ↓
Handles HTTP concerns

Service
    ↓
Handles business logic

Repository
    ↓
Handles persistence
```

### Controller

Shouldn't contain complex business logic.

```java
@PostMapping
public PaymentResponse create(
        @RequestBody PaymentRequest request) {

    return paymentService.create(request);
}
```

### Service

Business rules:

```java
@Service
class PaymentService {

    public PaymentResponse create(PaymentRequest request) {

        // validation/business rules
        // persistence
        // transformation

    }
}
```

### Repository

Database interaction:

```java
@Repository
interface PaymentRepository
        extends JpaRepository<Payment, String> {
}
```

### Interview answer

> **"The Controller is responsible for the HTTP layer, such as request mapping, extracting request data and returning responses. The Service contains business logic and orchestrates the operation. The Repository abstracts database access. This separation keeps responsibilities clear and makes the code easier to test and maintain."**

# Q120. What is the purpose of `@RestController`?

`@RestController` tells Spring:

> **This class handles REST requests and its methods return response data directly.**

It is effectively:

```java
@Controller
@ResponseBody
```

So:

```java
@RestController
public class PaymentController {

    @GetMapping("/payments")
    public List<Payment> getPayments() {
        return payments;
    }
}
```

The returned object is serialized, typically to JSON.

### Interview answer

> **"`@RestController` is used to define a REST controller. It combines `@Controller` and `@ResponseBody`, so the return value of handler methods is written directly to the HTTP response body, typically serialized as JSON."**

# Q121. What is the purpose of `@RequestMapping`?

It maps HTTP requests to a controller or method based on things such as:

- URL path
- HTTP method
- headers
- parameters
- content type

Most commonly:

```java
@RestController
@RequestMapping("/payments")
class PaymentController {
}
```

Then:

```java
@GetMapping("/{id}")
```

results in:

```text
GET /payments/123
```

### Interview answer

> **"`@RequestMapping` maps HTTP requests to controller classes or methods. It can define the URL path and can also be used to specify HTTP methods, headers, parameters and media types. It's commonly used at the class level to define a common base path."**

# Q122. Difference/use of `@GetMapping`, `@PostMapping`, `@DeleteMapping`, `@PatchMapping`?

They are specialized request mappings for specific HTTP methods.

| Annotation | HTTP | Typical use |
|---|---|---|
| `@GetMapping` | GET | Retrieve resource |
| `@PostMapping` | POST | Create/process resource |
| `@PatchMapping` | PATCH | Partial update |
| `@DeleteMapping` | DELETE | Delete resource |

Example:

```java
@GetMapping("/{id}")
public Payment get(@PathVariable String id) { ... }

@PostMapping
public Payment create(@RequestBody PaymentRequest request) { ... }

@PatchMapping("/{id}")
public Payment update(...) { ... }

@DeleteMapping("/{id}")
public void delete(@PathVariable String id) { ... }
```

### Interview trap

Don't say:

> "PATCH is for updating and PUT is also updating, so they're the same."

A useful distinction:

- **PUT** generally represents replacing/updating the resource representation.
- **PATCH** represents a partial modification.

# Q123. How do you accept JSON request data in a REST API?

Typically using:

```java
@RequestBody
```

For example:

```java
@PostMapping
public PaymentResponse create(
        @RequestBody PaymentRequest request) {
    
    return paymentService.create(request);
}
```

If the request is:

```json
{
    "amount": 5000,
    "currency": "INR"
}
```

Spring uses its HTTP message conversion mechanism—commonly Jackson—to deserialize the JSON into `PaymentRequest`.

### Interview answer

> **"I use `@RequestBody` to bind the HTTP request body to a Java object. For JSON requests, Spring's HTTP message converters, typically using Jackson, deserialize the JSON into the target DTO."**

# Q124. What is `@RequestBody` used for?

It tells Spring to take the **HTTP request body** and convert it into the specified Java object.

```java
@PostMapping
public Payment create(
        @RequestBody PaymentRequest request) {
}
```

Conceptually:

```text
JSON
 ↓
HTTP Request Body
 ↓
@RequestBody
 ↓
PaymentRequest
```

It's commonly used with:

```text
POST
PUT
PATCH
```

# Q125. How do you fetch data from query parameters?

Use:

```java
@RequestParam
```

Example request:

```text
GET /payments?status=SUCCESS&page=0&size=20
```

Controller:

```java
@GetMapping
public List<Payment> getPayments(
        @RequestParam String status,
        @RequestParam int page,
        @RequestParam int size) {
    
    ...
}
```

You can also make parameters optional:

```java
@RequestParam(required = false)
String status
```

or provide a default:

```java
@RequestParam(defaultValue = "0")
int page
```

### Interview answer

> **"I use `@RequestParam` to extract query parameters from the URL. For example, for `/payments?status=SUCCESS&page=0`, I can bind `status` and `page` using `@RequestParam`. Parameters can also be optional or have default values."**

# Q126. How do you handle path variables?

Use:

```java
@PathVariable
```

Example:

```text
GET /payments/123
```

Controller:

```java
@GetMapping("/{id}")
public Payment getPayment(
        @PathVariable String id) {

    return paymentService.getPayment(id);
}
```

Here:

```text
{id}
```

is the path variable.

### Difference from `@RequestParam`

```text
/payments/123
          ↑
     @PathVariable
```

versus:

```text
/payments?id=123
          ↑
     @RequestParam
```

# Q127. How do you implement Dependency Injection in Spring?

Spring's IoC container manages objects called **beans** and injects their dependencies.

The preferred approach is constructor injection:

```java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }
}
```

Spring sees that `PaymentService` requires `PaymentRepository` and injects the appropriate bean.

### Interview answer

> **"I use Spring's dependency injection by defining components such as `@Service`, `@Repository` and `@Component` and injecting their dependencies through constructors. Spring's IoC container creates and manages these beans and resolves their dependencies."**

---

# Q128. What is constructor-based dependency injection?

Instead of injecting a dependency into a field or setter, we provide it through the constructor.

```java
@Service
public class PaymentService {

    private final PaymentRepository repository;

    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }
}
```

Spring automatically injects `PaymentRepository`.

If there is only **one constructor**, modern Spring can use it without requiring `@Autowired`.

```java
public PaymentService(PaymentRepository repository) {
    this.repository = repository;
}
```

No:

```java
@Autowired
```

is required.

# Q129. Why is constructor injection preferred?

This is a **very common Spring interview question**.

### 1. Dependency is explicit

You can immediately see what the class requires.

### 2. Supports immutability

You can use:

```java
private final PaymentRepository repository;
```

### 3. Easier unit testing

You can directly create the object:

```java
PaymentService service =
        new PaymentService(mockRepository);
```

### 4. Prevents partially initialized objects

Required dependencies must be provided when constructing the object.

### Interview answer

> **"I prefer constructor injection because dependencies are explicit, required dependencies can be made immutable using `final`, and the class becomes easier to unit test because dependencies can be passed directly through the constructor. It also avoids partially initialized objects that can occur with field injection."**

# Q130. How do you handle exceptions in a REST API?

Don't put:

```java
try {
   ...
} catch(Exception e) {
   ...
}
```

around every controller method.

Instead, use centralized exception handling.

For example:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(PaymentNotFoundException.class)
    public ResponseEntity<ErrorResponse> handle(
            PaymentNotFoundException ex) {

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse(ex.getMessage()));
    }
}
```

Then the controller/service can throw:

```java
throw new PaymentNotFoundException("Payment not found");
```

and the centralized handler converts it into the appropriate HTTP response.

---

# Q131. Where would you implement exception handling?

For REST APIs, I'd generally implement **global exception handling** using:

```java
@RestControllerAdvice
```

and:

```java
@ExceptionHandler
```

You can also have local exception handling inside a controller if a particular exception is specific to that controller, but common application-wide REST exceptions are better handled centrally.

### Interview answer

> **"For common REST API exceptions, I would implement centralized handling using `@RestControllerAdvice` with `@ExceptionHandler` methods. Controller-specific handling can still be implemented locally when there is a specific reason to do so."**

# Q132. How would you implement centralized exception handling?

I'd create a class like:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(PaymentNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            PaymentNotFoundException ex) {

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse(ex.getMessage()));
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ErrorResponse> handleBadRequest(
            IllegalArgumentException ex) {

        return ResponseEntity
                .badRequest()
                .body(new ErrorResponse(ex.getMessage()));
    }
}
```

And a response DTO/record:

```java
public record ErrorResponse(
        String message
) {}
```

So the flow becomes:

```text
Client
   ↓
Controller
   ↓
Service
   ↓
Exception occurs
   ↓
@RestControllerAdvice
   ↓
@ExceptionHandler
   ↓
HTTP status + structured error response
```

### Strong interview answer

> **"I would create a `@RestControllerAdvice` class containing `@ExceptionHandler` methods for application-specific exceptions and common validation or bad-request scenarios. Each handler maps the exception to an appropriate HTTP status and a consistent error response DTO. This keeps exception handling out of individual controllers and provides a consistent API contract."**

If EPAM asks you to explain the whole thing:

```text
POST /payments
        ↓
@RestController
        ↓
@RequestBody PaymentRequest
        ↓
@Service
        ↓
Business logic
        ↓
@Repository
        ↓
Database
        ↓
PaymentResponse
        ↓
JSON response
```

If something fails:

```text
Exception
    ↓
@RestControllerAdvice
    ↓
@ExceptionHandler
    ↓
HTTP status + ErrorResponse
```

And for request data:

```text
/path/{id}       → @PathVariable
?status=SUCCESS  → @RequestParam
JSON body        → @RequestBody
```

**Those three mappings are especially worth memorizing**, because they're extremely common interview follow-ups.
