# Q78. What are Generics?

**Generics allow us to define classes, interfaces, and methods that work with a specified type while providing compile-time type safety.**

For example, without Generics:

```java
List list = new ArrayList();

list.add("Java");
list.add(100);
```

Now the list can contain different types.

With Generics:

```java
List<String> list = new ArrayList<>();

list.add("Java");
list.add(100);  // ❌ compile-time error
```

We're telling Java:

> "This List is intended to contain Strings."

### Another example

```java
Map<String, Integer> scores = new HashMap<>();
```

Here:

```text
String  → key type
Integer → value type
```

So:

```java
scores.put("Aryan", 90);     // ✅
scores.put(100, "Java");     // ❌
```

### Generic class example

```java
class Box<T> {

    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

Then:

```java
Box<String> box = new Box<>();
box.set("Java");

String value = box.get();
```

`T` is a **type parameter**.

### Interview answer

> **"Generics allow us to parameterize classes, interfaces, and methods with types. They provide compile-time type safety and allow us to write reusable code without repeatedly performing explicit casts. Common examples are `List<String>`, `Map<String, Integer>`, and generic classes or methods."**

# Q79. Why do we need Generics?

There are two major reasons:

### 1. Type safety

Without Generics:

```java
List list = new ArrayList();
list.add("Java");
list.add(100);
```

You can accidentally put different types into the collection.

With:

```java
List<String> list = new ArrayList<>();
```

the compiler prevents:

```java
list.add(100); // ❌
```

### 2. Avoid explicit casting

Without Generics:

```java
List list = new ArrayList();
list.add("Java");

String value = (String) list.get(0);
```

With Generics:

```java
List<String> list = new ArrayList<>();
list.add("Java");

String value = list.get(0);
```

No explicit cast is needed.

### Interview answer

> **"We use Generics primarily for type safety and code reusability. They allow the compiler to detect incompatible types early and eliminate many explicit casts when retrieving values from generic collections."**

### 2. Less casting

# Q81. How do Generics provide type safety?

The compiler checks the type parameter wherever possible.

For:

```java
List<String> names = new ArrayList<>();
```

this is rejected:

```java
names.add(100);
```

because `100` is an `Integer`, not a `String`.

And when retrieving:

```java
String name = names.get(0);
```

the compiler already knows the returned type is `String`.

So the compiler catches many mistakes **before the program runs**.

### Interview answer

> **"Generics provide type safety by allowing the compiler to enforce the declared type parameter. For example, with `List<String>`, the compiler prevents adding an Integer and knows that values retrieved from the list should be Strings, reducing the need for runtime casts."**

---

# Q82. Do Generics provide compile-time or runtime safety?

**Primarily compile-time type safety.**

This is a very direct interview question.

```text
Generics
   ↓
Compiler checks types
   ↓
Compile-time safety
```

They don't provide complete runtime type safety because of things such as **type erasure, raw types, unchecked casts, and legacy APIs**.

### Interview answer

> **"Generics primarily provide compile-time type safety. The compiler checks the type constraints during compilation. They don't guarantee that every possible type-related problem is impossible at runtime."**

---

# Q83. If Generics provide compile-time safety, can you still face issues at runtime?

**Yes.**

This connects directly to the question we discussed earlier.

For example, raw types can bypass generic checks:

```java
List<String> names = new ArrayList<>();

List raw = names;
raw.add(100);
```

The compiler gives a warning for the raw operation, but it can still happen.

Later:

```java
String name = names.get(0);
```

can result in:

```text
ClassCastException
```

### Interview answer

> **"Yes. Generics provide compile-time safety, but that safety can be bypassed through raw types, unchecked operations, explicit casts, or legacy APIs. Because of this, type-related runtime exceptions such as ClassCastException can still occur."**

---

# Q84. How can runtime issues occur when using Generics?

The main things to mention are:

### Raw types

```java
List<String> list = new ArrayList<>();

List raw = list;
raw.add(100);
```

### Unchecked casts

```java
Object obj = 100;

String value = (String) obj;
```

### Legacy APIs

Older APIs may work with raw types and therefore bypass generic compile-time checks.

### Type erasure

Java implements Generics using **type erasure**, meaning generic type parameters aren't retained in the same way at runtime.

So you shouldn't think:

> "`List<String>` is a completely different runtime type from `List<Integer>`."

At runtime, both are essentially `List`.

### Interview answer

> **"Runtime issues can occur when generic type safety is bypassed, for example through raw types, unchecked casts, or legacy APIs. Java also uses type erasure for Generics, so generic type parameters aren't fully available at runtime. These situations can eventually result in exceptions such as ClassCastException."**

# Q87. When should you use Generics?

Use Generics when you have **reusable code that should work with different types while maintaining compile-time type safety**.

For example, instead of:

```java
class StringBox
class IntegerBox
class EmployeeBox
```

you can have:

```java
class Box<T>
```

and use:

```java
Box<String>
Box<Integer>
Box<Employee>
```

### Interview answer

> **"I would use Generics when I need reusable, type-safe code that can operate on different types. They're especially useful for collections, reusable data structures, generic methods and framework APIs. I would avoid raw types because they remove much of the compile-time type safety that Generics provide."**
