# 1. Lambda Expressions ⭐⭐⭐

### What problem did Lambda solve?

Before Java 8, if you wanted to pass behavior as an argument, you often needed an anonymous class.

For example:

```java
Runnable r = new Runnable() {
    @Override
    public void run() {
        System.out.println("Hello");
    }
};
```

Java 8:

```java
Runnable r = () -> System.out.println("Hello");
```

So the basic idea is:

> **Lambda allows us to represent behavior/function as a value and pass it around.**

Syntax:

```java
(parameters) -> expression
```

or

```java
(parameters) -> {
    // statements
}
```

Example:

```java
(a, b) -> a + b
```

### Important point

A lambda **doesn't exist independently**. It needs a **target functional interface**.

```java
Calculator c = (a, b) -> a + b;
```

Here:

```text
(a,b) -> a+b
       ↓
Calculator
       ↓
calculate()
```

Your document correctly highlights this target-type concept. Pasted markdown

### Interview answer

> "Lambda expressions were introduced in Java 8 to represent behavior more concisely. They are mainly used with functional interfaces and are heavily used with Streams and asynchronous programming."

# 2. Functional Interface ⭐⭐⭐

A functional interface is an interface having:

> **Exactly one abstract method.**

Example:

```java
@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);
}
```

Then:

```java
Calculator add = (a, b) -> a + b;
```

### Can it have default/static methods?

YES.

```java
@FunctionalInterface
interface Calculator {

    int calculate(int a, int b);

    default void log() {
        System.out.println("logging");
    }

    static void print() {
        System.out.println("printing");
    }
}
```

Why is it still functional?

Because only:

```java
calculate()
```

is abstract.

Default/static methods don't count.

Your document covers this exact distinction. Pasted markdown

### Important built-in interfaces

You should know these extremely well:

| Interface | Method | Meaning |
|---|---|---|
| `Predicate<T>` | `boolean test(T)` | takes input → condition |
| `Function<T,R>` | `R apply(T)` | input → output |
| `Consumer<T>` | `void accept(T)` | consumes input |
| `Supplier<T>` | `T get()` | supplies output |
| `UnaryOperator<T>` | `T apply(T)` | T → T |
| `BinaryOperator<T>` | `T apply(T,T)` | T,T → T |

For example:

```java
Predicate<Integer> even = n -> n % 2 == 0;

Function<String, Integer> length = s -> s.length();

Consumer<String> print = s -> System.out.println(s);

Supplier<Double> random = () -> Math.random();
```

# 7. Lazy Evaluation ⭐⭐⭐⭐⭐

This is VERY important because your EPAM question bank explicitly contains lazy evaluation.

Consider:

```java
Stream<Integer> stream =
    numbers.stream()
           .filter(n -> {
               System.out.println(n);
               return n > 3;
           });
```

Has filtering happened?

**No.**

Why?

Because `filter()` is an **intermediate operation**.

Execution begins when we invoke a terminal operation:

```java
stream.count();
```

So:

```text
stream()
   ↓
filter()
   ↓
map()
```

doesn't necessarily execute immediately.

Then:

```text
count()
```

triggers the pipeline.

### Why lazy?

Because Java can avoid unnecessary processing.

For example:

```java
numbers.stream()
       .filter(...)
       .map(...)
       .findFirst();
```

Once the required element is found, the entire collection doesn't necessarily need to be processed. Pasted markdown

### Interview answer

> "Stream intermediate operations are lazily evaluated. They build a pipeline, but actual traversal starts when a terminal operation is invoked. This allows Streams to avoid unnecessary processing and supports operations like short-circuiting with findFirst, anyMatch, etc."

# 14. `toMap()` duplicate key trap ⭐⭐⭐

Suppose:

```java

    .collect(Collectors.toMap(
        Employee::getDepartment,
        Employee::getName
```




# 15. Optional ⭐⭐⭐

`Optional<T>` is used to explicitly represent:

> **A value may or may not be present.**

Instead of:

```java
Employee employee = findEmployee(id);

if (employee != null) {
    ...
}
```

you could have:

```java
Optional<Employee> employee = findEmployee(id);
```

And:

```java
employee.ifPresent(...);
```

or:

```java
employee.orElse(defaultEmployee);
```

### Important trap

```java
orElse()
```

is generally **eager**.

```java
orElseGet()
```

is **lazy**.

```java
name.orElse(getDefault());
```

`getDefault()` can execute even when value exists.

Whereas:

```java
name.orElseGet(() -> getDefault());
```

only invokes it when necessary. Pasted markdown

# 16. `Comparable` vs `Comparator` ⭐⭐⭐

### Comparable

Class defines its **natural ordering**.

```java

    public int compareTo(Employee other) {
        return Integer.compare(this.salary, other.salary);
    }
}
```

### Comparator

Ordering is defined externally.

```java
Comparator<Employee> byName =
    Comparator.comparing(Employee::getName);
```

Memory:

```text
Comparable
    ↓
"How does this object naturally compare?"

Comparator
    ↓
"How do I want to compare these objects here?"
```

# 21. Default methods in interfaces ⭐⭐⭐

Java 8 allowed:

```java
interface Payment {

    void pay();

    default void log() {
        System.out.println("payment");
    }
}
```

### Why?

Before Java 8, adding a new method to an interface could break all existing implementations.

Default methods allowed interfaces to evolve while providing a default implementation.

### Important trap

If two interfaces have the same default method:

```java
interface A {
    default void test() {}
}

interface B {
    default void test() {}
}
```

and:

```java
class C implements A, B
```

`C` must resolve the conflict.

```java
@Override
public void test() {
    A.super.test();
}
```

# 🟡 Java 9

There are a few things worth knowing.

## 1. Java Module System ⭐⭐⭐

This was the **biggest Java 9 feature**.

Before Java 9, a Java application essentially had:

```text
Application
   ↓
JAR files
   ↓
Classes
```

Java 9 introduced the **Java Platform Module System (JPMS)**.

Now you could organize code into modules:

```text
Application
   ↓
Module A
   ↓
Module B
```

A module can explicitly declare:

- what it **requires**
- what it **exports**

Example:

```java
module payment.service {

    requires java.sql;

    exports com.example.payment;
}
```

Meaning:

```text
payment.service
      │
      ├── requires java.sql
      │
      └── exports com.example.payment
```

### Interview answer

> "Java 9 introduced the module system, which allows applications and the JDK itself to be organized into modules with explicit dependencies and exported packages."

You don't need to go extremely deep into JPMS for your interview unless they specifically ask.


# 4. Try-with-resources improvement

This is an important correction because you mentioned earlier that you use try-with-resources.

**Try-with-resources itself is NOT a Java 11 feature.**

It was introduced in **Java 7**.

Java 9 improved it.

Before Java 9:

```java
BufferedReader br =
    new BufferedReader(new FileReader("file.txt"));

try (BufferedReader reader = br) {
    ...
}
```

Java 9 allows:

```java
BufferedReader br =
    new BufferedReader(new FileReader("file.txt"));

try (br) {
    ...
}
```

provided `br` is effectively final.

So in an interview:

❌ Don't say:

> "Try-with-resources was introduced in Java 11."

Better:

> "Try-with-resources was introduced in Java 7, and Java 9 enhanced it so an effectively final existing resource can be used directly."

# 🟠 Java 10

There's really **one feature you should definitely remember**.

## `var` ⭐⭐⭐⭐

Java 10 introduced **local variable type inference**.

Instead of:

```java
String name = "Aryan";
```

you can write:

```java
var name = "Aryan";
```

The compiler determines:

```text
var name = "Aryan";
          ↓
String
```

But `var` is **still statically typed**.

This:

```java
var name = "Aryan";
```

does NOT mean:

```text
name can become Integer later
```

You cannot do:

```java
var name = "Aryan";

name = 100; // compilation error
```

Because `name` is inferred as `String`.

### Where can `var` be used?

Local variables:

```java
var list = new ArrayList<String>();
```

Loop variables:

```java
for (var name : names) {
    ...
}
```

Try-with-resources:

```java
try (var input = new FileInputStream(file)) {
    ...
}
```

### Where can't you use it?

You cannot do:

```java
class Employee {
    var name; // ❌
}
```

or:

```java
var method() { } // ❌
```

or:

```java
void test(var value) { } // ❌
```

### Interview answer

> "`var` was introduced in Java 10 for local variable type inference. The compiler infers the type at compile time, so Java remains statically typed. It can be used for local variables, loop variables and resources, but not for fields or method parameters."

# 1. Records ⭐⭐⭐⭐⭐

A **record** is a compact way of declaring a class whose primary purpose is to carry data.

Without a record:

```java
public class Employee {

    private final Long id;
    private final String name;

    public Employee(Long id, String name) {
        this.id = id;
        this.name = name;
    }

    public Long id() {
        return id;
    }

    public String name() {
        return name;
    }

    // equals()
    // hashCode()
    // toString()
}
```

With a record:

```java
public record Employee(Long id, String name) {
}
```

The compiler provides the components, canonical constructor, accessors, `equals()`, `hashCode()` and `toString()`. [Oracle Docs](https://docs.oracle.com/en/java/javase/17/language/java-language-changes-release.html?utm_source=chatgpt.com)

So:

```java
record Employee(Long id, String name) {}
```

gives you:

```text
private final fields
constructor
id()
name()
equals()
hashCode()
toString()
```

Notice:

```java
employee.name()
```

not:

```java
employee.getName()
```

---

# 2. Why were records introduced?

Imagine you're creating DTOs.

You might have:

```java
EmployeeResponse
PaymentResponse
AccountResponse
TransactionResponse
```

Many of these classes are simply:

> "Here is some data."

Before records, there was a lot of boilerplate.

Record:

```java
record PaymentResponse(
    String transactionId,
    String status,
    BigDecimal amount
) {}
```

Much cleaner.

### Interview answer

> "Records provide a concise syntax for classes that primarily act as data carriers. They automatically provide components, a canonical constructor, accessors, equals, hashCode and toString, reducing boilerplate."

# 3. Are records immutable? ⭐⭐⭐⭐⭐

This is a **very good senior-level trap**.

People often say:

> "Records are immutable."

That's not completely correct.

Consider:

```java
record Employee(
    String name,
    List<String> skills
) {}
```

The record component reference is final, but:

```java
employee.skills().add("Java");
```

can still modify the underlying list.

So records provide **shallow immutability**, not deep immutability.

Your document explicitly highlights this trap. Pasted markdown (2)

If you want defensive immutability:

```java
record Employee(
    String name,
    List<String> skills
) {
    public Employee {
        skills = List.copyOf(skills);
    }
}
```

Now you're protecting the collection from modification.

# 4. Can a record extend another class?

No.

A record implicitly extends:

```java
java.lang.Record
```

So:

```java
record Employee(...) extends Person // ❌
```

is not allowed.

But records **can implement interfaces**:

```java
record Employee(Long id, String name)
        implements Comparable<Employee> {

    @Override
    public int compareTo(Employee other) {
        return name.compareTo(other.name);
    }
}
```

Pasted markdown (2)

# 5. Can a record contain methods?

Absolutely.

```java
record Employee(
    Long id,
    String name,
    double salary
) {

    public boolean isHighEarner() {
        return salary > 100000;
    }
}
```

You can also validate through a compact constructor:

```java
record Employee(Long id, String name) {

    public Employee {
        if (id == null) {
            throw new IllegalArgumentException("id required");
        }
    }
}
```

Pasted markdown (2)

So don't think:

> Record = dumb object with no behavior.

It can have methods, constructors, static members, etc.

# 11. Pattern Matching for `instanceof` ⭐⭐⭐⭐

This actually became permanent in **Java 16**, not Java 17. [Oracle Docs](https://docs.oracle.com/en/java/javase/17/language/java-language-changes-release.html?utm_source=chatgpt.com)

```java
if (obj instanceof String) {

    System.out.println(s.length());

```

You had to:

```text
check type
   ↓
cast
   ↓
use object
```

Modern:

```java
if (obj instanceof String s) {

}
```

Java performs the cast automatically.

So:

```text
instanceof
    +
cast
```

becomes:

```text
instanceof String s
```

Much cleaner.

# 15. What are Virtual Threads?

Traditional Java threads are **platform threads**.

They have relatively significant resource costs because they are associated with OS-level threads.

Virtual threads are:

> **Lightweight threads managed by the JVM.**

Example:

```java
Thread.startVirtualThread(() -> {
    callDatabase();
});
```

Or:

```java
try (var executor =
         Executors.newVirtualThreadPerTaskExecutor()) {

    executor.submit(() -> callService());
    executor.submit(() -> callDatabase());
}
```

The important idea isn't:

> "Virtual threads are faster threads."

It's:

> **"Virtual threads allow us to support much higher concurrency for tasks that spend significant time waiting."**

---

# 16. Why are Virtual Threads useful?

Imagine your microservice receives:

```text
10,000 requests
```

Each request does:

```text
HTTP request
      ↓
Database
      ↓
Downstream service
      ↓
Response
```

A lot of time is spent **waiting**.

Traditional platform-thread model:

```text
Thread 1 → waiting DB
Thread 2 → waiting HTTP
Thread 3 → waiting DB
...
```

With virtual threads:

```text
Virtual Thread 1 → waiting
Virtual Thread 2 → waiting
Virtual Thread 3 → CPU work
Virtual Thread 4 → waiting

           ↓

Carrier/platform threads
execute available work
```

When a virtual thread is blocked on supported blocking operations, it can be parked while the underlying carrier thread can do other work.

Your document explains this model. Pasted markdown (2)

---

# 17. Do Virtual Threads make CPU work faster?

**NO.** ❌

This is probably the most important trap.

Suppose:

```java
calculateHugePrimeNumber();
```

Virtual threads don't magically create more CPU cores.

So:

```text
CPU-bound workload
        ↓
Virtual thread
        ↓
Not magically faster
```

But:

```text
I/O-bound / blocking workload
        ↓
Virtual threads
        ↓
Much higher concurrency
```

Strong interview answer:

> "Virtual threads don't increase CPU capacity. Their main benefit is improving concurrency and throughput for workloads with many blocking operations such as HTTP, database or network I/O."

Pasted markdown (2)

# 18. Are Virtual Threads unlimited?

Technically you can create huge numbers of them, but your **resources aren't unlimited**.

Imagine:

```text
100,000 virtual threads
        ↓
100,000 DB requests
        ↓
DB connection pool = 50
```

Your DB becomes the bottleneck.

Virtual threads don't remove:

```text
CPU limits
Memory limits
DB connection limits
Downstream capacity
Rate limits
Network limits
```

So you still need:

```text
timeouts
backpressure
concurrency limits
resource pools
rate limiting
```

# 19. Virtual Threads vs Fixed Thread Pool

Traditional:

```java
ExecutorService executor =
    Executors.newFixedThreadPool(100);
```

You deliberately maintain a limited number of platform threads.

Virtual threads:

```java

    Executors.newVirtualThreadPerTaskExecutor();
```

The conceptual model is:

```text
Traditional:
tasks → bounded platform thread pool

Virtual:
tasks → cheap virtual thread per task
```

And importantly:

> **You generally don't pool virtual threads just to save thread creation cost.**

They are designed to be cheap.

But you still control external resources.
