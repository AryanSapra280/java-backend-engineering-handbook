## Q62. What is the use case for a Set?

A `Set` is used when you need a collection where **duplicate elements aren't allowed**.

Conceptually:

   ↓

### Q65 is where things get more interesting:

The key concept is **interface vs implementation**.

## Q65. What is the difference and use case between `List` and `ArrayList`?

This is mainly an **interface vs implementation** question.

### `List`

`List` is an **interface**.

It defines the contract for an ordered collection that allows duplicates.

```java
List<String> names;
```

It doesn't tell you exactly **how** the data is stored.

---

### `ArrayList`

`ArrayList` is a **concrete implementation of `List`**.

```java
ArrayList<String> names =
        new ArrayList<>();
```

Internally, it uses a **resizable array**.

So the relationship is:

```text
List
 ↑
ArrayList
```

### Why usually write this?

```java
List<String> names = new ArrayList<>();
```

rather than:

```java
ArrayList<String> names = new ArrayList<>();
```

Because you generally want to **program to the interface**.

It gives you flexibility to change the implementation later:

```java
List<String> names = new LinkedList<>();
```

without changing code that only depends on the `List` contract.

### When would you specifically choose `ArrayList`?

When you want a general-purpose `List` with:

- Fast random/index-based access
- Frequent reads
- Usually good iteration performance
- Elements stored in a dynamically growing array

Example:

```java
List<String> names = new ArrayList<>();

names.add("Aryan");
names.add("Rahul");

String first = names.get(0);
```

### Interview answer

> **"`List` is an interface that defines the contract for an ordered collection, whereas `ArrayList` is a concrete implementation backed by a resizable array. I would normally declare the variable using the interface, such as `List<String> list = new ArrayList<>();`, because it keeps the code flexible and allows me to change the implementation if required."**

### Likely follow-up

**"When would you use `LinkedList` instead?"**

Don't automatically say *"LinkedList is faster for insertion/deletion."* That's too simplistic.

The actual performance depends on **where** the insertion/deletion happens and whether you already have the relevant node/iterator position.

For most general-purpose list usage, `ArrayList` is usually the default choice.

## Q66. What is the difference and use case between `Set` and `HashSet`?

Same pattern:

For example:

If you need insertion order, you could consider:

If you need sorted order:

```java

So:

Set

├── LinkedHashSet    → uniqueness + insertion order
└── TreeSet          → uniqueness + sorted order
```

### Interview answer

> **"`Set` is an interface representing a collection that doesn't allow duplicate elements. `HashSet` is an implementation of Set that uses hashing and provides generally efficient lookup, insertion and removal. I would use `HashSet` when I need uniqueness and don't need to maintain insertion or sorted order."**

## Q68. When would you use `ConcurrentHashMap`?

This is an important **Senior-level concurrency question**.

I'd use `ConcurrentHashMap` when:

> **Multiple threads need to access and modify a Map concurrently, and I need thread-safe operations without synchronizing the entire map myself.**

Example:

```java
Map<String, Integer> counts =
        new ConcurrentHashMap<>();
```

Multiple threads can safely perform operations on it.

It is particularly useful in concurrent applications such as:

```text
Multiple threads
      ↓
ConcurrentHashMap
      ↓
shared state/cache/counters
```

### Important distinction

Don't say:

> "`ConcurrentHashMap` makes every sequence of operations automatically atomic."

For example:

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

The **combination** of `containsKey()` + `put()` isn't automatically one atomic operation.

Instead, use atomic/concurrent APIs when appropriate:

```java
map.putIfAbsent(key, value);
```

or:

```java
map.computeIfAbsent(key, k -> createValue());
```

### Interview answer

> **"I would use `ConcurrentHashMap` when a Map is shared across multiple threads and concurrent reads and updates are required. It provides thread-safe access with better concurrency characteristics than synchronizing an entire HashMap. For compound operations, I would use atomic methods such as `putIfAbsent` or `computeIfAbsent` rather than assuming multiple individual operations are atomic."**

That last sentence is especially useful for you because you've already worked with `computeIfAbsent`.

# Q72. Does `HashMap` allow duplicate keys?

**No.**

A `HashMap` can contain **only one mapping for a given key**.

If you do:

```java
Map<String, Integer> map = new HashMap<>();

map.put("Aryan", 90);
map.put("Aryan", 95);
```

The second `put()` **replaces the existing value**:

```text
Aryan → 95
```

It does **not** create:

```text
Aryan → 90
Aryan → 95
```

### Interview answer

> **"No. HashMap doesn't allow duplicate keys. If I insert another value with an existing key, the new value replaces the previous value associated with that key."**

One useful nuance:

```java
Integer old = map.put("Aryan", 95);
```

`put()` returns the **previous value** associated with the key, or `null` if there wasn't one.

# Q73. Does `HashMap` allow duplicate values?

**Yes.**

Keys must be unique, but multiple keys can map to the same value.

```java
Map<String, String> map = new HashMap<>();

map.put("Aryan", "Java");
map.put("Rahul", "Java");
map.put("Amit", "Spring");
```

This is perfectly valid:

```text
Aryan → Java
Rahul → Java
Amit  → Spring
```

`Java` appears as a value twice.

### Interview answer

> **"Yes. HashMap allows duplicate values. The uniqueness constraint applies to keys, not values. Multiple different keys can map to the same value."**

Both values could conceptually be similar, but the keys are different.

# Q77. When would you choose `HashMap` versus `ConcurrentHashMap`?

This is the **most important question in this group** because it connects directly to your concurrency preparation.

### `HashMap`

Use when:

```text
Single-threaded
        OR
externally synchronized access
```

and you don't need concurrent modification support.

```java
Map<String, Integer> map = new HashMap<>();
```

Example:

```text
Request-local data
Local processing
Non-shared collection
```

---

### `ConcurrentHashMap`

Use when:

```text
Multiple threads
       ↓
Shared Map
       ↓
Concurrent reads/writes
```

Example:

```java
Map<String, Integer> map =
        new ConcurrentHashMap<>();
```

It provides thread-safe concurrent operations without requiring you to synchronize the entire map yourself.

### Example

Imagine multiple worker threads maintaining a shared cache:

```text
Thread 1 ─┐
Thread 2 ─┤
Thread 3 ─┼──> ConcurrentHashMap
Thread 4 ─┘
```

That's a good candidate for `ConcurrentHashMap`.

### Important difference

Don't simplify it to:

> "`ConcurrentHashMap` is just a synchronized HashMap."

That's not accurate.

`ConcurrentHashMap` is designed specifically for **concurrent access** and provides much better concurrency characteristics than putting a single lock around an entire `HashMap`.

Also remember:

```java
map.putIfAbsent(key, value);
```

and:

```java
map.computeIfAbsent(key, k -> createValue());
```

are useful when you need atomic compound operations.

### Interview answer

> **"I'd use HashMap when the map isn't being concurrently modified by multiple threads, such as local or single-threaded processing. I'd use ConcurrentHashMap when the map is shared across multiple threads and concurrent reads and updates are required. ConcurrentHashMap provides thread-safe operations with better concurrency than synchronizing an entire HashMap. For compound operations, I'd use its atomic methods such as `putIfAbsent` or `computeIfAbsent`."**
