# 9. Spring Boot — Q106–116

These questions are closely related, so the best way to prepare is to understand the **Spring → Spring Boot → Auto-configuration → Starters → Embedded Server → Actuator** flow.

---

## Q106. Why did you use Spring Boot?

### Interview answer

> **"I use Spring Boot because it simplifies building and deploying production-ready Spring applications. It provides auto-configuration, starter dependencies, embedded servers, and production features such as Actuator. This reduces configuration and boilerplate compared to configuring a Spring application manually."**

For your experience, you can make it more practical:

> **"I've primarily used Spring Boot for developing REST-based microservices. It makes it easier to set up the application, configure dependencies, expose REST APIs, connect to databases, and package the application as a deployable service."**

### Follow-up: Why not plain Spring?

Because with traditional Spring, you typically need significantly more explicit configuration. Spring Boot gives sensible defaults and convention-over-configuration.

# Q109. How is Spring Boot different from Spring Framework?

Don't say **"Spring is old and Spring Boot is new."** 😄

Spring Boot is **built on top of Spring Framework**.

| Spring Framework | Spring Boot |
|---|---|
| Core framework | Built on Spring |
| More explicit configuration traditionally | Convention/auto-configuration |
| Dependency setup is more manual | Starters simplify dependencies |
| Traditionally external server configuration | Embedded server support |
| Production features need more setup | Actuator provides production features |

### Interview answer

> **"Spring Framework provides the fundamental capabilities for building Java applications, whereas Spring Boot simplifies the setup and configuration of Spring applications. Spring Boot doesn't replace Spring; it uses Spring underneath and adds features such as auto-configuration, starters, embedded servers and production-ready tooling."**

# Q111. What is Auto-Configuration?

This is **very important**.

Auto-configuration means Spring Boot automatically configures parts of your application based on:

1. Dependencies present on the classpath
2. Existing beans
3. Configuration properties
4. Conditions defined by Spring Boot

For example, if you have:

```xml
spring-boot-starter-web
```

Spring Boot detects the relevant web dependencies and automatically configures much of the web application infrastructure.

You don't manually configure everything.

### Interview answer

> **"Spring Boot auto-configuration automatically configures application components based on the dependencies available on the classpath, existing beans, and configuration properties. It uses conditional configuration so that configuration is applied only when the required conditions are satisfied."**

# Q112. How does Spring Boot Auto-Configuration work?

This is where the interviewer may go deeper.

The basic flow is:

```text
@SpringBootApplication
        ↓
@EnableAutoConfiguration
        ↓
Spring Boot discovers auto-configuration classes
        ↓
Checks conditions
        ↓
Creates/configures beans when conditions match
```

`@SpringBootApplication` includes:

```java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
```

The important part here is:

```java
@EnableAutoConfiguration
```

It tells Spring Boot to enable its auto-configuration mechanism.

### Conditions

Spring Boot uses conditional annotations such as:

```java
@ConditionalOnClass
@ConditionalOnMissingBean
@ConditionalOnProperty
```

For example, conceptually:

```java
@Configuration
@ConditionalOnClass(SomeLibrary.class)
@ConditionalOnMissingBean(SomeService.class)
class SomeAutoConfiguration {

    @Bean
    SomeService someService() {
        return new SomeService();
    }
}
```

Meaning:

> "If the required class exists and the application hasn't already provided this bean, configure it automatically."

### Strong interview answer

> **"Spring Boot's auto-configuration is enabled through `@EnableAutoConfiguration`, which is included in `@SpringBootApplication`. Spring Boot discovers auto-configuration classes and evaluates conditions such as whether a particular class is present, whether a bean already exists, or whether a property is enabled. If the conditions match, Spring Boot creates the required beans using the configured defaults. If we define our own bean, conditions such as `@ConditionalOnMissingBean` can cause the default configuration to back off."**

### ⭐ Very important follow-up

**"Does auto-configuration always override our configuration?"**

**No.**

Typically Spring Boot provides a default **only when appropriate**, and application-defined beans can cause auto-configuration to back off.

That's the meaning behind:

```text
@ConditionalOnMissingBean
```

# Q113. What are Spring Boot Starter Dependencies?

Starters are convenient dependency bundles for a particular capability.

For example:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

Instead of manually adding every dependency needed for a typical web application, the starter brings the required set of dependencies.

Other examples:

```text
spring-boot-starter-data-jpa
spring-boot-starter-security
spring-boot-starter-test
spring-boot-starter-actuator
```

### Interview answer

> **"Spring Boot starters are curated dependency descriptors that group the dependencies commonly required for a particular functionality. For example, `spring-boot-starter-web` provides the dependencies required for building web applications. They simplify dependency management and help avoid manually adding compatible libraries one by one."**

### Important distinction

A starter doesn't magically implement the feature.

It mainly simplifies **dependency management**.

# Q114. What are Embedded Servers in Spring Boot?

Traditionally, a Java web application could be packaged as a WAR and deployed to an externally managed application server.

Spring Boot commonly allows you to package the application with an **embedded web server**.

For example:

```text
Spring Boot application
        |
        +--- Application code
        +--- Spring
        +--- Embedded server
```

Common servers include:

- Tomcat
- Jetty
- Undertow

For example, with Spring MVC and the standard web starter, Tomcat is commonly used by default.

You can then run:

```bash
java -jar application.jar
```

without separately installing and configuring a web server for that application.

### Interview answer

> **"An embedded server means the web server is packaged as part of the Spring Boot application rather than requiring a separately deployed application server. For example, Spring Boot commonly uses embedded Tomcat. This allows us to package the application as a JAR and run it directly using `java -jar`, which simplifies deployment."**

# Q115. What is Spring Boot Actuator?

Actuator provides **production-ready monitoring and management capabilities** for Spring Boot applications.

It exposes endpoints that provide information about the running application.

Common examples:

```text
/actuator/health
/actuator/metrics
/actuator/info
```

For example:

```text
GET /actuator/health
```

might tell you:

```json
{
  "status": "UP"
}
```

It can also expose application metrics and other operational information.

### Interview answer

> **"Spring Boot Actuator provides production-ready endpoints and metrics for monitoring and managing a Spring Boot application. Common endpoints include health, metrics and info. It helps us understand whether the application and its dependencies are healthy and provides operational information for monitoring systems."**

# Q116. How is Actuator used for production monitoring?

This is where you should connect it to **Kubernetes + observability**, because that is relevant to your interview.

A typical flow:

```text
Spring Boot Application
        |
        +---- Actuator /health
        |
        +---- Actuator /metrics
        |
        ↓
Monitoring / Kubernetes / Observability
```

### Health checks

Kubernetes can use health endpoints for things such as:

```text
Liveness
Readiness
```

For example:

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
```

Conceptually:

**Liveness:**  
"Is my application alive?"

**Readiness:**  
"Can this application currently receive traffic?"

### Metrics

Actuator can expose metrics that can be collected by monitoring systems.

You can monitor things like:

- Request counts
- Request latency
- JVM metrics
- Memory usage
- CPU-related metrics
- Thread information
- Connection pool metrics
- Application-specific metrics

### Your interview answer

> **"In production, Actuator can be used to expose health and metrics endpoints. For example, Kubernetes can use liveness and readiness health endpoints to determine whether a pod is alive and whether it should receive traffic. Metrics can also be integrated with our monitoring stack to track things such as request latency, JVM memory, threads and connection pools. This helps us detect failures and performance problems without adding custom monitoring code to every service."**
