# HashSet — Deep Dive: Internals

Now we go one level deeper into the part that interviewers love: **what actually happens inside `HashSet.add()`?**

The important thing is to understand the chain:

```text
HashSet
   ↓
HashMap
   ↓
hashCode()
   ↓
hash spreading
   ↓
bucket index
   ↓
collision handling
   ↓
equals()
   ↓
insert / reject
```

---

## 1. HashSet → HashMap

Start with:

```java
Set<String> set = new HashSet<>();

set.add("Java");
```

The important internal design is approximately:

```text
HashSet
   |
   | internally owns
   ↓
HashMap
```

Conceptually:

```text
HashSet<String>

"Java" ───────────────→ PRESENT
"Spring" ─────────────→ PRESENT
"Kafka" ──────────────→ PRESENT
```

The actual HashMap doesn't need a meaningful value.

The key is the Set element.

So conceptually:

```java
map.put(element, PRESENT);
```

Therefore:

> **HashSet uniqueness is fundamentally HashMap key uniqueness.**

That's an extremely useful mental shortcut.

---

# 2. What happens when we call `add()`?

Suppose:

```java
Set<String> set = new HashSet<>();

set.add("Java");
```

Think through these steps:

```text
"Java"
   ↓
hashCode()
   ↓
hash transformation
   ↓
bucket index
   ↓
look at bucket
   ↓
is it empty?
   ├── yes → insert
   └── no
        ↓
     compare candidate entries
        ↓
      equals()
        ├── true  → duplicate → don't insert
        └── false → collision → continue
```

That's the entire mechanism at a high level.

# 3. What is a bucket?

Imagine the HashMap backing table as:

```text
index

0   → bucket
1   → bucket
2   → bucket
3   → bucket
4   → bucket
5   → bucket
6   → bucket
7   → bucket
```

A hash determines which bucket an object belongs to.

For example:

```text
"Java"
   ↓
hash
   ↓
bucket 5
```

So instead of searching every element:

```text
A
B
C
D
E
F
...
```

we go directly to the relevant region.

---

# 4. Why not simply use `hashCode()` as the array index?

Because `hashCode()` returns an `int`.

That's potentially:

```text
-2,147,483,648
        ...
2,147,483,647
```

But our backing array might have only:

```text
16 buckets
```

We need to map a potentially huge integer into:

```text
0 → 15
```

So we need a bucket-index calculation.

Conceptually:

```text
hash
 ↓
transform
 ↓
index
```

---

# 5. Why HashMap capacity is typically a power of 2

This is a classic HashMap interview question.

Typical capacities are:

```text
16
32
64
128
256
...
```

Why?

Because when capacity is a power of 2, the bucket index can efficiently be calculated using a bitwise operation.

Conceptually:

```java
index = (n - 1) & hash;
```

where:

```text
n = table length
```

For:

```text
n = 16
```

we have:

```text
n - 1 = 15

15 in binary:

1111
```

Then:

```text
hash
&
1111
```

effectively extracts the lower bits needed for the bucket index.

This is much cheaper than a general modulo operation and works neatly with power-of-two capacities.

---

# 6. But there's a problem with using only lower bits

Suppose several hash values differ mainly in their upper bits.

If we only use the lower bits:

```text
hash A
hash B
hash C
```

we might get poor bucket distribution.

That's why modern HashMap performs a **hash spreading/mixing step** before calculating the bucket.

Conceptually:

```text
key.hashCode()
      ↓
mix/spread hash bits
      ↓
bucket index
```

A commonly discussed Java implementation form is:

```java
static final int hash(Object key) {
    int h;
    return (key == null)
        ? 0
        : (h = key.hashCode()) ^ (h >>> 16);
}
```

The idea is not that this creates a completely new hash.

It mixes higher bits into lower bits so that when the lower bits are used for bucket selection, more information from the original hash participates.

---

# 7. Example of the idea

Imagine a hash has useful information in:

```text
upper bits
```

but poor variation in:

```text
lower bits
```

Without spreading:

```text
bucket calculation
       ↓
mostly lower bits
```

With spreading:

```text
upper bits
     ↓
mix into lower bits
     ↓
better bucket distribution
```

You don't need to memorize the exact bit manipulation before understanding the purpose.

Remember:

> **Hash spreading tries to improve distribution when the bucket index uses only part of the hash.**

---

# 8. Collision

Now suppose:

```text
Employee A → bucket 5
Employee B → bucket 5
```

That is a collision.

It does **not** mean:

```text
A.equals(B)
```

It simply means they ended up in the same bucket.

Conceptually:

```text
Bucket 5

[A] → [B] → [C]
```

HashMap needs another mechanism to distinguish them.

That's where `equals()` comes in.

---

# 9. Hash collision vs equality

This distinction is critical.

### Same hash

```text
a.hashCode() == b.hashCode()
```

does **not** guarantee:

```text
a.equals(b)
```

### Equality

If:

```java
a.equals(b)
```

is `true`, then Java requires:

```java
a.hashCode() == b.hashCode()
```

So:

```text
same hash
   ↓
possibly same logical object

equals()
   ↓
confirms logical equality
```

---

# 10. Collision handling in older Java

Historically, a bucket could look like:

```text
bucket 5

[A] → [B] → [C] → [D]
```

This is a linked list.

If many objects collide into the same bucket, lookup could degrade toward:

```text
O(n)
```

because you may need to walk the chain.

This was particularly important in older Java implementations.

---

# 11. Java 8+ improvement — treeification

Modern HashMap implementations introduced an important optimization.

If a bucket becomes sufficiently crowded, the linked structure can be transformed into a tree structure under appropriate conditions.

Conceptually:

```text
Before:

bucket
  ↓
A → B → C → D → E → F
```

can become conceptually:

```text
bucket
   ↓
      C
     / \
    A   E
       / \
      D   F
```

The exact implementation uses a specialized tree node structure.

The point is:

> A heavily collided bucket can become tree-based rather than remaining a long linked list.

This can improve lookup behavior for pathological collision patterns.

---

# 12. Important: When does treeification happen?

Don't oversimplify this to:

> "At 8 elements it becomes a tree."

That's incomplete.

HashMap has thresholds related to:

- bucket size
- minimum table capacity

The commonly discussed constants in modern OpenJDK implementations include:

```text
TREEIFY_THRESHOLD     = 8
UNTREEIFY_THRESHOLD   = 6
MIN_TREEIFY_CAPACITY  = 64
```

The important nuance:

> If a bucket becomes sufficiently crowded but the table itself is still too small, HashMap may resize instead of immediately treeifying the bucket.

So the mental model is:

```text
collision-heavy bucket
        ↓
is table large enough?
   /              \
 no                yes
 ↓                  ↓
resize          potentially treeify
```

That distinction is a good senior-level interview point.

---

# 13. Why resize before treeify?

Imagine:

```text
capacity = 16
```

and you have many collisions.

Maybe the problem isn't that the hash function is terrible.

Maybe the table is simply too small.

Resizing increases the number of buckets:

```text
16
 ↓
32
 ↓
64
```

which can distribute entries more widely.

So HashMap doesn't immediately assume:

> "This bucket must become a tree."

It first considers whether expanding the table can improve distribution.

---

# 14. Load factor

Now we need another important concept.

Suppose:

```text
capacity = 16
```

and load factor:

```text
0.75
```

The approximate resize threshold is:

```text
16 × 0.75 = 12
```

So after enough entries accumulate, HashMap resizes.

Conceptually:

```text
capacity = 16
threshold = 12

entries > threshold
       ↓
resize
```

---

# 15. Why not wait until 100% full?

Because then many elements could be packed into too few buckets.

That means more collisions.

Instead, HashMap accepts some unused capacity to maintain reasonable distribution.

So:

```text
lower load factor
    ↓
more memory
    ↓
potentially fewer collisions

higher load factor
    ↓
less memory
    ↓
potentially more collisions
```

This is a classic memory-vs-performance trade-off.

---

# 16. Resizing

Suppose:

```text
capacity = 16
```

and it needs to grow.

Conceptually:

```text
16
 ↓
32
```

The table becomes larger and entries are redistributed according to the new capacity.

This operation isn't free.

It requires work proportional to the number of existing entries.

So an individual insertion can occasionally trigger:

```text
O(n)
```

work.

But across many operations, average insertion remains approximately:

```text
O(1)
```

under normal assumptions.

This is the same **amortized complexity idea** we discussed with ArrayList.

---

# 17. A complete `HashSet.add()` mental trace

Let's put everything together.

We execute:

```java
set.add(employee);
```

### Step 1

Get:

```java
employee.hashCode()
```

### Step 2

HashMap applies its hash transformation/spreading.

### Step 3

Calculate:

```text
bucket index
```

using the table size.

### Step 4

Check that bucket.

### Step 5

If empty:

```text
insert
```

### Step 6

If occupied:

```text
compare candidate entries
```

using hash/equality checks.

### Step 7

If an equal key exists:

```text
duplicate
→ don't add
→ return false
```

### Step 8

If no equal key exists:

```text
collision
→ add another entry to bucket structure
```

### Step 9

If size crosses resize threshold:

```text
resize table
```

### Step 10

If a bucket becomes sufficiently collision-heavy and table is sufficiently large:

```text
potential treeification
```

That's the complete story.

# 18. Let's implement a simplified HashSet

We won't implement all of Java's production-level optimizations.

We want to understand the core mechanism.

```java
class MyHashSet<E> {

    private static class Node<E> {
        E value;
        Node<E> next;

        Node(E value) {
            this.value = value;
        }
    }

    private Node<E>[] buckets;

    public MyHashSet(int capacity) {
        buckets = new Node[capacity];
    }

    public boolean add(E value) {

        int hash = value.hashCode();

        int index =
            Math.abs(hash) % buckets.length;

        Node<E> current = buckets[index];

        while (current != null) {

            if (current.value.equals(value)) {
                return false;
            }

            current = current.next;
        }

        Node<E> newNode =
            new Node<>(value);

        newNode.next = buckets[index];

        buckets[index] = newNode;

        return true;
    }
}
```

---

# 19. What does our implementation demonstrate?

This tiny implementation captures the essential idea:

```text
value
  ↓
hashCode()
  ↓
bucket index
  ↓
bucket chain
  ↓
equals()
  ↓
duplicate?
```

For example:

```java
MyHashSet<String> set =
    new MyHashSet<>(10);

set.add("Java");
set.add("Spring");
set.add("Java");
```

The third operation finds:

```text
existing "Java"
```

and:

```java
current.value.equals(value)
```

returns true.

So:

```text
add("Java") → false
```

# 20. Why our implementation isn't production-ready

Excellent interviewer follow-up:

> "Why isn't this implementation equivalent to Java HashSet?"

Because we've omitted several important things:

### 1. Resizing

Our bucket array never grows.

### 2. Load factor

We don't monitor occupancy.

### 3. Hash spreading

We directly use:

```java
hashCode()
```

### 4. Better index calculation

We use:

```java
Math.abs(hash) % buckets.length
```

whereas modern HashMap uses optimized power-of-two table indexing.

### 5. Treeification

We only use linked lists.

### 6. Null handling

Java HashSet supports a null element.

### 7. Generic array creation issues

Java's generic arrays require careful handling.

### 8. Performance optimizations

The JDK implementation contains many optimizations we've intentionally omitted.

That's exactly how you should explain a coding interview implementation:

> "I'm implementing the core mechanism, not reproducing every JDK optimization."

# 21. A subtle bug in our implementation

Look at:

```java
int index = Math.abs(hash) % buckets.length;
```

What if:

```text
hash = Integer.MIN_VALUE
```

`Math.abs(Integer.MIN_VALUE)` is still negative due to integer overflow.

So this simplistic implementation can produce a negative index.

A safer simplified approach is:

```java
int index =
    (hash & 0x7fffffff) % buckets.length;
```

or use a proper unsigned/indexing strategy.

This is a nice reminder:

> Low-level implementations have edge cases that a simple whiteboard solution may ignore.

# 22. `equals()` and `hashCode()` — production example

Imagine a payment system.

```java
class Payment {

    private String paymentId;
    private String status;
}
```

Suppose business identity is:

```text
paymentId
```

Then:

```java
@Override
public boolean equals(Object o) {
    ...
}
```

should compare payment IDs.

And:

```java
@Override
public int hashCode() {
    return Objects.hash(paymentId);
}
```

should use the same identity fields.

Then:

```java
Set<String> processedPayments
```

or:

```java
Set<Payment>
```

can be used to prevent duplicate processing, provided the identity semantics are correct and immutable.

This is directly relevant to your **payment/idempotency** interview topics later.

# 23. A dangerous mistake

Suppose:

```java
@Override
public int hashCode() {
    return Objects.hash(paymentId, status);
}
```

and then:

```java
payment.setStatus("SUCCESS");
```

after putting the object in a HashSet.

Now:

```text
before:
hash(paymentId, PENDING)
       ↓
bucket 5

after:
hash(paymentId, SUCCESS)
       ↓
bucket 11
```

But the object is still physically stored according to the old placement.

Now:

```java
set.contains(payment)
```

may fail.

Therefore:

> **Don't use mutable fields in equality/hash identity when objects are stored in hash-based collections unless you can guarantee they won't change while stored.**

# 24. HashSet complexity

Under normal distribution:

```text
add       → average O(1)
contains  → average O(1)
remove    → average O(1)
```

But:

```text
resize
collision-heavy lookup
```

can require more work.

With modern treeified buckets, pathological collision behavior can be improved substantially compared with a simple linked-list implementation.

For interview purposes:

> **Average O(1), with implementation-dependent worst-case behavior.**

That is a much better answer than blindly saying "O(1)."

# 25. HashSet vs LinkedHashSet vs TreeSet

Now you can see why these three exist.

| Requirement | Implementation |
|---|---|
| Unique + no ordering guarantee | `HashSet` |
| Unique + insertion order | `LinkedHashSet` |
| Unique + sorted order | `TreeSet` |

Example:

```java
Set<Integer> a = new HashSet<>();
```

means:

```text
uniqueness
+
fast average lookup
```

---

```java
Set<Integer> b = new LinkedHashSet<>();
```

means:

```text
uniqueness
+
insertion order
```

---

```java
Set<Integer> c = new TreeSet<>();
```

means:

```text
uniqueness
+
sorted order
```

This is the decision framework.

# 26. Interview rapid-fire

### "Why does HashSet use HashMap?"

Because HashMap already provides hash-based key uniqueness. HashSet can store each element as a key with a dummy value.

### "Why do we need equals if we have hashCode?"

Because multiple different objects can map to the same hash/bucket. `equals()` determines whether they're logically equal.

### "Can equal objects have different hashCodes?"

No.

### "Can unequal objects have the same hashCode?"

Yes.

### "What is a collision?"

Different keys/elements mapping to the same bucket.

### "What happens when a bucket becomes too large?"

Modern HashMap can treeify sufficiently large collision-heavy buckets when the table is sufficiently large; otherwise resizing may happen first.

### "What is load factor?"

A threshold controlling how full the hash table can become before resizing.

### "Why 0.75?"

It represents a practical trade-off between memory usage and collision frequency; it's a common default, not a mathematical law.

### "Why power-of-two capacity?"

It enables efficient bucket-index calculation using bit operations and works well with HashMap's resizing strategy.

# 27. The senior-level answer to "Explain HashSet internally"

If EPAM asks:

> **"Explain HashSet internal implementation."**

Your answer should flow like this:

> "`HashSet` is backed by a `HashMap`. When we add an element, the element is effectively used as a HashMap key and a dummy value is associated with it. The key's hash code is transformed and used to determine a bucket. If the bucket is empty, the entry is inserted. If there are existing entries, HashMap uses hash comparisons followed by equality checks to determine whether the element already exists. If it's equal, the Set rejects the duplicate; otherwise it's a collision and the new entry is added to that bucket's structure. HashMap maintains a load-factor-based resize threshold, and in modern Java sufficiently collision-heavy buckets can be treeified when the table is large enough. Average add/contains/remove are O(1) under good hash distribution."

That is a **much stronger interview answer** than:

> "HashSet internally uses HashMap and gives O(1)."
