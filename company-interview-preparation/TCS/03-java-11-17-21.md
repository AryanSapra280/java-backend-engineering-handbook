## Java 11 → Java 17 → Java 21

### Java 11 — Q1. What important features were introduced in Java 11?

Java 11 is an LTS release. The most interview-relevant additions are:

* New `HttpClient`
* `String.isBlank()`
* `String.lines()`
* `String.strip()`
* `String.stripLeading()`
* `String.stripTrailing()`
* `String.repeat()`
* `Files.readString()`
* `Files.writeString()`
* `var` allowed in lambda parameters

Example:

```java
String value = "   Hello   ";

System.out.println(value.isBlank());   // false
System.out.println(value.strip());     // Hello
System.out.println(value.repeat(2));   // "   Hello      Hello   "
```

### Follow-up: `trim()` vs `strip()`?

`trim()` is based on older ASCII-oriented whitespace rules.

`strip()` uses Unicode-aware whitespace handling.

So in modern applications, especially when handling international text, `strip()` is generally preferable.

# Java 11 — Q2. What is the new HTTP Client?

Java 11 standardized the `java.net.http.HttpClient`.

Before Java 11, developers commonly relied on libraries such as Apache HttpClient or `HttpURLConnection`.

Example:

```java
HttpClient client = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com"))
        .GET()
        .build();

HttpResponse<String> response =
        client.send(request, HttpResponse.BodyHandlers.ofString());

System.out.println(response.body());
```

It supports both:

* synchronous requests
* asynchronous requests

Async example:

```java
client.sendAsync(
        request,
        HttpResponse.BodyHandlers.ofString()
);
```

This returns:

```java
CompletableFuture<HttpResponse<String>>
```

### Interview connection

This is a nice opportunity to connect Java 11 with Java 8:

> Java 8 introduced `CompletableFuture`, and Java 11's HTTP Client provides asynchronous APIs that return `CompletableFuture`, allowing HTTP calls to be composed asynchronously.

# Java 11 — Q3. What is `var` in lambda parameters?

Java 10 introduced local-variable type inference using `var`.

Java 11 extended `var` to lambda parameters.

```java
(var a, var b) -> a + b
```

The important reason is that annotations can be applied consistently:

```java
(@NotNull var name) -> ...
```

You cannot mix:

```java
(var a, b) -> ... // invalid
```

Either use:

```java
(a, b) -> ...
```

or:

```java
(var a, var b) -> ...
```

# Java 17 — Q5. What is a Record?

A record is a concise way to create a class intended primarily to represent immutable data.

Instead of:

```java
class Employee {

    private final Long id;
    private final String name;

    public Employee(Long id, String name) {
        this.id = id;
        this.name = name;
    }

    public Long id() {
        return id;
    }

    public String name() {
        return name;
    }

    // equals
    // hashCode
    // toString
}
```

You can write:

```java
record Employee(Long id, String name) {}
```

The compiler provides:

* private final fields
* canonical constructor
* accessors
* `equals()`
* `hashCode()`
* `toString()`

Notice the accessor isn't:

```java
getName()
```

It's:

```java
name()
```

---

# Java 17 — Q6. Are records completely immutable?

This is a **very important trap**.

A record is not magically deeply immutable.

Example:

```java
record Employee(String name, List<String> skills) {}
```

The reference to `skills` is final, but the list itself can still be modified:

```java
employee.skills().add("Java");
```

So records provide **shallow immutability of their components**, assuming the component references themselves aren't mutable through other means.

If you need deep immutability, you must design the components accordingly.

For example:

```java
record Employee(
    String name,
    List<String> skills
) {
    public Employee {
        skills = List.copyOf(skills);
    }
}
```

Now the supplied list is defensively copied into an unmodifiable list.

# Java 17 — Q7. Can a record extend another class?

No.

A record implicitly extends `java.lang.Record`.

Java doesn't support multiple class inheritance.

But a record **can implement interfaces**.

```java
record Employee(Long id, String name)
        implements Comparable<Employee> {

    @Override
    public int compareTo(Employee other) {
        return this.name.compareTo(other.name);
    }
}
```

---

# Java 17 — Q8. Can you define methods inside a record?

Absolutely.

```java
record Employee(
    Long id,
    String name,
    double salary
) {

    public boolean isHighEarner() {
        return salary > 100000;
    }
}
```

You can also define validation in the compact constructor:

```java
record Employee(Long id, String name) {

    public Employee {
        if (id == null) {
            throw new IllegalArgumentException("id required");
        }
    }
}
```

# Java 17 — Q9. What are sealed classes?

This is one of the **most important Java 17 questions**.

A sealed class restricts which classes can extend it.

```java
sealed class Payment
        permits CardPayment, UpiPayment, CashPayment {
}
```

Then:

```java
final class CardPayment extends Payment {
}

final class UpiPayment extends Payment {
}

final class CashPayment extends Payment {
}
```

The compiler knows the complete set of permitted subclasses.

---

# Why would you use sealed classes?

Suppose you're designing a payment system.

Without sealed classes:

```text
Payment
 ├── CardPayment
 ├── UpiPayment
 ├── CashPayment
 └── SomeRandomPayment
```

Any code could extend `Payment`.

With sealed classes:

```text
Payment
 ├── CardPayment
 ├── UpiPayment
 └── CashPayment
```

You explicitly control the hierarchy.

This becomes particularly useful with **pattern matching for switch**.

---

# Java 17 — Q10. What are the rules for subclasses of a sealed class?

A permitted subclass must itself declare one of:

```java
final
sealed
non-sealed
```

Example:

```java
sealed class Payment
        permits CardPayment, UpiPayment {
}
```

Then:

```java
final class CardPayment extends Payment {
}
```

or:

```java
non-sealed class UpiPayment extends Payment {
}
```

`non-sealed` means the restriction is opened again below that point.

# Java 17 — Q11. What is pattern matching for `instanceof`?

Before:

```java
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}
```

Java 17 allows:

```java
if (obj instanceof String s) {
    System.out.println(s.length());
}
```

The variable is automatically cast.

Cleaner and less error-prone.

---

# Java 17 — Q12. What is the advantage beyond reducing code?

The variable has **pattern-match scope**.

```java
if (obj instanceof String s && !s.isEmpty()) {
    System.out.println(s);
}
```

The compiler understands where `s` is definitely available.

This is particularly useful when combined with modern `switch` pattern matching.

# Java 21 — Q14. What are virtual threads?

🔥 **This is probably the most important Java 21 topic for a backend developer.**

Traditional Java threads are relatively expensive because they map closely to operating-system threads.

Virtual threads are lightweight threads managed by the JVM.

Example:

```java
Thread.startVirtualThread(() -> {
    callDatabase();
});
```

Or:

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {

    executor.submit(() -> callService());
    executor.submit(() -> callDatabase());
}
```

The key idea:

```text
Platform threads
    ↓
expensive
    ↓
limited concurrency

Virtual threads
    ↓
very lightweight
    ↓
very high concurrency
```

---

# Java 21 — Q15. Do virtual threads make CPU operations faster?

**No.**

This is a major interview trap.

Virtual threads primarily improve scalability for workloads with lots of blocking/waiting, such as:

```text
HTTP calls
Database calls
File/network I/O
```

They don't magically make CPU calculations faster.

If you have:

```java
calculateHugePrimeNumber();
```

virtual threads don't give you free CPU.

You still have the same number of CPU cores.

### Strong interview answer:

> Virtual threads improve concurrency and throughput for applications that have many concurrent blocking operations. They don't increase CPU capacity and therefore don't inherently speed up CPU-bound workloads.

---

# Java 21 — Q16. Why are virtual threads useful for microservices?

Imagine your service receives:

```text
10,000 requests
```

Each request does:

```text
HTTP request
   ↓
DB query
   ↓
another HTTP call
   ↓
response
```

With traditional platform threads, thousands of blocked threads can consume substantial resources.

With virtual threads, blocked virtual threads can be parked while the underlying carrier thread can execute other work.

Conceptually:

```text
Virtual Thread 1 → waiting for DB
Virtual Thread 2 → waiting for HTTP
Virtual Thread 3 → CPU work
Virtual Thread 4 → waiting for DB

             ↓

Carrier threads execute available work
```

That's where virtual threads shine.

---

# Java 21 — Q17. Are virtual threads unlimited?

No.

This is another excellent follow-up.

You may create huge numbers of virtual threads, but your **resources are still limited**.

For example:

```text
100,000 virtual threads
        ↓
100,000 DB requests
        ↓
DB connection pool = 50
```

The database is still the bottleneck.

Virtual threads don't eliminate:

* DB connection limits
* downstream service limits
* CPU limits
* memory limits
* rate limits

So you still need appropriate **resource pools, backpressure, timeouts, and concurrency limits**.

---

# Java 21 — Q18. Virtual threads vs ExecutorService fixed thread pool?

Traditional:

```java
Executors.newFixedThreadPool(100);
```

You deliberately limit concurrent platform threads.

Virtual-thread approach:

```java
Executors.newVirtualThreadPerTaskExecutor();
```

The model becomes:

> Create a virtual thread per task rather than maintaining a small pool of reusable platform threads.

You generally **don't pool virtual threads** just to save thread-creation cost. They're designed to be cheap.

But you still limit **external resources**.

For example:

```text
Virtual threads: potentially very many
DB connections: 50
HTTP concurrency: maybe 200
Kafka processing: bounded
```

That's the important architecture distinction.

---

# Java 21 — Q19. What is pattern matching for switch?

Traditional:

```java
if (obj instanceof String s) {
    ...
} else if (obj instanceof Integer i) {
    ...
}
```

Modern switch can work with patterns:

```java
static String describe(Object obj) {
    return switch (obj) {
        case String s -> "String: " + s;
        case Integer i -> "Integer: " + i;
        default -> "Other";
    };
}
```

This works very nicely with sealed hierarchies.

---

# Java 21 — Q20. What are record patterns?

Suppose:

```java
record Employee(String name, int age) {}
```

Instead of:

```java
if (obj instanceof Employee employee) {
    String name = employee.name();
    int age = employee.age();
}
```

You can destructure:

```java
if (obj instanceof Employee(String name, int age)) {
    System.out.println(name);
    System.out.println(age);
}
```

This is called **record pattern matching**.

---

# Java 21 — Q21. What are Sequenced Collections?

Java 21 introduced APIs for collections where encounter order has a defined first/last concept.

The new interfaces include:

```text
SequencedCollection
SequencedSet
SequencedMap
```

They provide operations conceptually around:

```text
first
last
addFirst
addLast
reversed
```

This makes APIs more consistent across ordered collection types.

It's useful to know for a Java 21 feature question, but **don't spend half your interview preparing this**. Virtual threads are much more important for a backend role.
